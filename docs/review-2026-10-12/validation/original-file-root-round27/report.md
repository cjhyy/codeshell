# Round 27 author evidence — Files root identity after summary fork

Author/latest first authorized run confirms a narrow **P3 candidate**: after changing a multi-folder project's primary from A to B, a summary context package created from an old A-bound source opens Files with B's root ID and A's directory path. The actual Main filesystem gate correctly rejects that pair. Selecting A still works; B's real directory remains healthy and readable through a coherent request. This is one renderer root mapping defect, not file loss or a Main authorization bypass. Root's independent two-baseline runs and final formal decision are separate; this author report does not assign R86 or increment the prior 85 findings/250 tests.

## User trigger and production source

The supported sequence is: a live project P owns healthy, non-overlapping roots A and B, initially primary A; an ordinary persisted native source session S is bound to P/A and has completed selectable conversation content; the user makes B primary, then successfully creates an ordinary summary context package T from S and opens T's Files panel before its first ordinary send. Both roots remain registered, mounted and trusted. No permission failure, symlink replacement, corrupt state, racing navigation, removed root or special filesystem precision is required.

- Sidebar's actual folders dialog has Make primary (`packages/desktop/src/renderer/Sidebar.tsx:692–701`, action `:219–232`). Preload forwards the project/root ID; Main checks the live mounted root/trust and broadcasts after `ProjectStore.setPrimary` (`packages/desktop/src/main/project-authority-ipc.ts:140–148`). The real store changes primaryRootId while preserving old session metadata (`project-store.ts:471–484`). Renderer registry reconciliation derives current project.path from primary B (`renderer/projects.ts:223–254`).
- Ordinary context selection reaches MessageStream's actual summary fork request (`renderer/MessageStream.tsx:322–347`) and Core's summary-only publication (`core/protocol/server.ts:1806–1822`). `SessionManager.createSummaryFork` uses the source cwd/workspace but the explicit state whitelist omits binding (`core/session/session-manager.ts:2144–2184,2429–2458`). App registers/hydrates/selects that published target in the existing UI project (`renderer/App.tsx:2018–2072`). Opening its already materialized panel bucket does not send a run or lazily bind it (`App.tsx:669–672`).
- The actual Main workspace service reads the persisted unbound target, validates healthy registered A and returns workspace A with mainRootId null (`main/session-workspace-service.ts:143–151,209–241,383–388`). Actual `usePanelWorkspaceRoot` preserves that result and marks it ready (`renderer/panels/usePanelWorkspaceRoot.ts:92–120`). The small dynamically tested wrapper passes the same Files props as the statically inspected PanelArea/Registry path (`PanelArea.tsx:488–502`; `PanelRegistry.ts:118–122`).

The root cause is `packages/desktop/src/renderer/panels/FilesPanel.tsx:142–150`: with no sessionMainRootId, it selects project.primaryRootId B, then overwrites B.path with workspaceCwd A. The resulting root choices are B.id/A.path and A.id/A.path, so B's actual path is absent. Default selection uses B.id (`:153–176`), falls through to the project filesystem API because the session root ID is absent (`:177–194`), and the mounted DirNode passes A.path (`:345–347,461–474`).

Actual Main `fsRoot:readDir` resolves B.id to authoritative B.path and calls readDirectory(B.path,A.path), which rejects before readdir (`main/index.ts:6492–6495` latest / `:6486–6489` primary; `renderer-project-path.ts:73–83`; `fs-service.ts:30–32,52–54`). The original file tree does not show either root's unique file under that default. Re-selecting B repeats the wrong tuple. The swallowed-error empty-tree display (`FilesPanel.tsx:468–469`) is R65's known manifestation and is not counted again here.

The contemporary multi-folder contract explicitly preserves an old session's A main after Make primary B (`docs/todo/multi-folder-local-project-plan.md:175–176,261–276`). Its lazy binding for ordinary renderer forks is also explicit (`:186–188,217–221`), so missing binding itself is retained as legitimate behavior. The candidate concerns inconsistent rootId/path construction in a Files panel which is already enabled and already using project-root APIs. A possible fix is to keep registered root identity/path pairs together in the unbound fallback; only a matching authoritative session root should replace its registered path with the session workspace pointer. No Core fork-inheritance redesign is required to explain this finding.

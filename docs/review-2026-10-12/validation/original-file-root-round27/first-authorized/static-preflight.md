## Narrow candidate and legal prerequisites

Consider one live Main-owned project P with healthy, non-overlapping mounted roots A and B, initially primary A. An ordinary native source session S was run in A and has durable `{ projectId: P, mainRootId: A.id }`, `cwd=A.path`, and a main workspace at A.path. The source has at least one completed selectable turn. The user makes B primary through the supported folders UI, then successfully creates an ordinary summary context package T from S, remains on that target, and opens its Files panel before T's first ordinary send. Neither root was removed, retargeted, made unreadable, or untrusted; the summary operation must actually succeed. Choose normal sibling roots so A.path is outside B.path. This is not a fabricated timestamp, stale-response race, corrupt state, or renderer-forged root.

The source audit supports a deterministic identity mismatch on this sequence: Files initially labels/selects B.id but substitutes A.path into that option. It invokes `fsRoot:readDir(P, B.id, A.path)`. Main correctly authorizes B.path and rejects the request before reading A. Selecting A still works; B's actual path is absent from the options until identity is corrected. This is a conditional source result, **not a run receipt or confirmed finding**.

## Controls and recovery boundaries

- **Bound source after Make primary:** Main uses S.project.mainRootId=A.id, not P.primaryRootId (`session-workspace-service.ts:161–207`). Files puts A/workspaceA first and preserves B/B.path, then uses the Session API. Main returns A's main workspace for A or authorizes the registered B root for B (`session-workspace-service.ts:434–469`). Existing test source `FilesPanel.workspace.test.tsx:362–392` checks this stronger bound/worktree variant. It was read, not executed.
- **Selecting A on unbound target:** Files' remaining A option keeps A.id/A.path; project-mode Main containment accepts that coherent pair. The mismatch does not remove all roots or all file access. Any other secondary C also retains C.id/C.path.
- **Source main still equals current primary:** The old R26 fallback remains valid: A.id is replaced with the same A.path, and B remains coherent. Existing project fallback test source `FilesPanel.workspace.test.tsx:334–360` covers selector/readProjectDir with no engine/root ID. A summary target has an engine ID but no root ID; the same `&&` condition still falls through. Again, not a new dynamic receipt.
- **Blank draft B is only a qualified control:** The active conversation authority contract uses current primary B for a draft (`renderer/sessionUiAuthority.ts:53–58,165–175`) and Files props with cwd=B/no session ID produce coherent B.id/B.path. Do **not** claim this audit proved the complete blank-panel UI path: panel opening materializes a UI ID (`App.tsx:647–666`), the engine-ID resolver can fall back to that UI ID (`useRunController.ts:1000–1015`), and a still-absent disk session is rejected by the panel hook. That separate draft boundary was not expanded or executed. The target under review is already persisted and does not encounter it.
- **First ordinary send:** The current send supplies P but no rootId (`useRunController.ts:282–294,354–357`). Main's resolver recognizes a persisted unbound T and looks up A by exact stored cwd, preserving workspace A (`project-store.ts:655–659`; `agent-run-metadata.ts:123–150,298–320`; `agent-bridge.ts:664–678`). Engine supplies A's binding (`core/engine/engine.ts:1666–1671`), and resume persists it (`core/engine/run-session-open.ts:88–92`). This is normal durable recovery. The current mounted Files hook only reloads for its target key/workspace event, so this audit does not assert that every already-mounted panel immediately re-reads the newly saved binding after send. Reload/remount or a genuine authority refresh can observe it. No claim of permanent loss, wrong cwd, run failure, or a required paid-model repair is justified.
- Refreshing the directory before identity repair reruns the same incoherent default B pair; choosing A is a local normal alternative. Neither establishes that B's actual Files root is reachable in the unbound target before repair.

## Contract, dedupe, and later validation feasibility

The multi-folder contract deliberately allows old session main to differ from current project primary: `docs/todo/multi-folder-local-project-plan.md:154–176,261–276`. It specifies file panel `(projectId,rootId,path)` authorization at `:589–595`. Summary inherits source cwd/workspace and becomes a normal sidebar session (`docs/nightly-2026-07-10/session-fork-and-context-transfer-design.md:41–52`). At the same time, project-binding persistence at first run and lazy lookup for ordinary renderer forks are explicit (`multi-folder-local-project-plan.md:186–188,217–221`). Therefore **missing binding itself is not promoted**. The narrower question is whether Files may display B while issuing an A-path request rejected by the exact existing Main authority.

R26 already retained this boundary as unverified and rejected a broader Review-scope claim. R58 concerns managed-worktree image/terminal authority adaptation and R65 concerns rejection feedback; neither is re-counted. No broader Review/fork design finding is proposed.

A later explicitly authorized validation can keep real temporary ProjectStore addRoot/setPrimary, actual SessionManager summary target publication, actual workspace authority and Files React rendering, plus the actual Main fsRoot callback and fs-service. A narrowly owned Git probe adapter and supplied summary output can avoid Git subprocess/model execution; transport/trust/window ownership adapters must be labeled. It should challenge the legal sequence above and compare bound source/A selection/current-primary-aligned source, rather than inventing a rootId/path mismatch directly as the only trigger. **This note adds no fixture or executable plan and runs nothing.**

The exact seams matter if that later work is authorized:

- Do not import Desktop Main index as an application. Extract the `fsRoot:readDir` function node from the frozen index via AST (as the existing R14 source helper does), or capture that exact function from an explicitly isolated IPC registration. Bind its `requireRendererProjectRoot` and `readDirectory` dependencies to their real implementations. Calling a handwritten callback or returning a canned directory Promise is insufficient evidence of this Main path.
- `getProjectStore()` is a lazy default singleton (`main/project-store.ts:1226–1235`) with **reset only**, not an injectable store setter. The workspace service does have `__setSessionWorkspaceServiceSessionManagerForTests` and `__setSessionWorkspaceServiceProjectStoreForTests` (`session-workspace-service.ts:102–127`). A coherent later validation must make renderer-root authorization and workspace authority consume the same actual temporary registry, rather than silently setting only the workspace service's instance while Main reads a different singleton. Options are an owned isolated HOME/default singleton, or a labeled validator DI wrapper around the real `requireRendererProjectRoot` with the actual store's `list()` snapshot (its existing `options.projects` seam). Neither may synthesize B's path from a hand-maintained test map.
- ProjectStore's public constructor has `options.resolveProjectRoot` (`project-store.ts:155–166`) for a strictly owned A/B folding adapter. The default singleton instead consumes `resolveProjectRoot` from `@cjhyy/code-shell-capability-coding/git` (`:26,:166`), so that export also needs an exact owned adapter if using the singleton without Git. `session-workspace-service.ts:13,:266–272` separately imports and calls `findMainWorktreeRoot`. Its seam has no public DI: a later adapter must match the exact coding Git export, accept only the two owned roots, and either return the declared owned main root or throw the standard not-a-git-repository error for declared ordinary non-Git roots, which the real helper already treats as normal. All other path arguments and unused Git/worktree exports must fail closed. This would test authority flow and Files identity, not real Git discovery/status.
- Feed the actual rendered FilesPanel project from actual `trackedProjectFromRegistry`/Main snapshot and its cwd/root ID from actual workspace authority/hook. Obtain the P/B.id/A.path tuple from the real rootOptions/render/default-selection/readDir flow. It must not be manufactured as the fixture's only trigger. Direct `SessionManager.createSummaryFork` with declared supplied summary output would cover state publication, not the model, complete RPC transport, or TopBar clicks; those upstream entry points remain source evidence unless separately covered.

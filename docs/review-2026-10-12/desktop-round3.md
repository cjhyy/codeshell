## D11 [P2] Plugin switches erase unrelated disable entries before authoritative settings initialization finishes

- **Primary location:** `packages/desktop/src/renderer/extensions/ManagePage.tsx:104–120`; initial state/refresh at `70–83`.
- **Actual entry / trigger:** open Extensions → Plugins while the authoritative initial refresh (`Promise.all` of skills and settings) remains incomplete. PluginsTab has independently loaded rows and renders live switches first. 实际 mount IPC 顺序为 plugins:list、skills:list、settings:get；Main 的 skill scan 是同步的，不声称两个 Main 扫描并行。renderer 独立进程、IPC 交付和 settings:get 的真实 async fs.readFile 留有允许的未完成初始化窗口。 Existing user settings have `disabledPlugins: ["alpha"]` and `disabledSkills: ["alpha:skill"]`. Disable the unrelated plugin `beta` before that initial refresh completes.
- **Observed impact:** togglePlugin builds and persists both full arrays from the initial empty Sets and empty skill list: `{disabledPlugins: ["beta"], disabledSkills: []}`. This silently re-enables alpha and the previously disabled skill, including this user-level disable gate for alpha's hooks. 其他项目禁用、信任或权限保护仍可能阻止执行，未证明任意不受信任代码被执行。 Once the older initial refresh completes, the UI displays alpha disabled / beta enabled, opposite the newly persisted settings.
- **Cause:** getSettings is held behind Promise.all with the skill scan; no loaded guard disables the separate plugin controls. togglePlugin writes whole-array replacements without a current durable snapshot, and the refresh has no mutation/version fence.
- **Evidence:** `plugin-settings-race.test.tsx` mounts the actual ManagePage and DialogProvider, clicks the real Radix switch handler, delays only the skill scan, records the actual updateSettings payload and subsequent rendered switches. `plugin-settings-race.test.tsx.log`: 1 pass, 0 fail, 8 assertions.
- **Recovery:** reopening/reloading the page makes its display match the already damaged settings; the user must manually disable the unintentionally re-enabled plugin/skill again. Waiting for initial settings refresh before switching avoids the trigger. 第十轮用真实 Main writeSettings/readSettings 确认数组确已替换；正常完成初始化后禁用 beta 能保留 alpha 及 alpha:skill。
- **Confidence:** high. Limited to the initial/settings-refresh window; this is not a claim that all ordinary post-load toggles lose settings.
- **Fix direction:** initialize authoritative settings independently, keep switches unavailable until ready, and fence refresh snapshots against later user mutations; preserve other entries in durable array updates.

## D12 [P2] Completing startup project-bucket migration removes a subsequently added project from the live UI

- **Primary location:** `packages/desktop/src/renderer/app/useProjectRegistrySync.ts:57–62`; live onChanged projection at `32–43`.
- **Actual entry / trigger:** upgrade startup with a cached legacy renderer project id remapping to the existing V2 registry id, and a stored transcript requiring asynchronous copy into the new project bucket. While that copy is pending, use the normal Add Project picker to add and select another project.
- **Observed impact:** actual ProjectStore durably contains both projects and its onChanged callback updates the renderer correctly, but finishing the older initial migration unconditionally replaces projects with the old captured single-project snapshot. The added project's sidebar row and configuration authority disappear while activeProjectId remains that now-absent project's id.
- **Cause:** asynchronous migrateProjectSessionBucket is awaited after the initial registry snapshot. The concurrent live subscription applies later registry changes, but the startup continuation has only an alive flag, with no generation/fresh-snapshot reconciliation before setProjects(projects).
- **Evidence:** `project-initial-snapshot.test.tsx` uses actual ProjectStore, LegacyProjectMigrationService, SessionCatalogStore, SessionPersistence, useTrackedProjects, useProjectRegistrySync, and useSessionNavigation. It delays actual transcript-write completion at the IPC seam, then invokes handleAddProject against the real store. The final Main ids contain A+B, renderer ids contain only A, and activeProjectId is B. `project-initial-snapshot.test.tsx.log`: 1 pass, 0 fail, 6 assertions.
- **Recovery:** another native registry change or restart reloads the current project list; 已用实际 handleRenameProject 对仍可见的 A 重命名，触发真实 ProjectStore.rename 广播后恢复 A+B，且 active B 保留。Open Recent 也会重新协调持久注册表。 the added project is not deleted from disk. Until then the current UI lacks its selected project's authority. Trigger is specifically legacy project-id/transcript migration at startup, not an arbitrary reordered IPC response.
- **Confidence:** high.
- **Fix direction:** coordinate initialization with live subscription revisions, or re-read/reconcile the current registry after awaited migration before publishing the initial projection.

## D13 [P1] Repeated Enter while creating a worktree can delete the successful request's workspace and uncommitted files

- **Primary location:** `packages/coding/src/git/worktree/crud.ts:176–181`, rollback implementation `79–87`. Desktop entry: `packages/desktop/src/renderer/topbar/WorkspaceIndicator.tsx:629–633`, input Enter handler `842–844`, button guard `853–854`. Main parallel entry: `packages/desktop/src/main/project-authority-ipc.ts:286–309`.
- **Actual entry / trigger:** open the workspace switcher → New worktree, type a slug, and press Enter again while creation is pending. The Create button is disabled, but the input Enter handler and createNew/switchTo do not check busyAction. Both identical requests reach Main's async workspace:switch handler, which has no per-session/target serialization. Both creation prechecks can therefore observe the same branch/path as absent.
- **Observed impact:** one git worktree add succeeds; the other add fails with the real Git error that the branch already exists. The failed invocation nevertheless unconditionally calls cleanupAbortedWorktree on that shared path and branch. Its `git worktree remove --force` removes the winner's worktree, including a newly written uncommitted file, and `git branch -D` deletes the winner's branch. The successful IPC already broadcast workspace:changed, and the Session remains persisted to the now-deleted worktree root. Depending on process timing, the unscheduled exploratory run instead saw both add calls fail because rollback removed the checkout while its winning Git process was still running.
- **Evidence:** `worktree-duplicate-create.test.tsx` test 1 mounts the actual WorkspaceIndicator (only presentation Popover/Dialog wrappers replaced), presses the actual input's Enter handler twice across React renders, and confirms Create is already disabled while two equal native API calls are emitted. Test 2 registers the actual registerProjectAuthorityIpc handler and invokes its two same-session requests concurrently against an actual SessionManager and temporary Git repository. Every git operation uses real Git. A temporary PATH executable imposes only an allowed completion schedule: both add invocations arrive after prechecks; the winner completes; the real losing Git error is delivered later. It does not forge command output/results or invoke cleanup itself. Before the failure reaches JS, explicit assertions and the log establish worktree directory, uncommitted file and branch all exist. After failure, all are absent, while Session.workspace still points there and only the successful workspace change was broadcast. `worktree-duplicate-create.test.tsx.log`: 2 pass, 0 fail, 15 assertions.
- **Reachability / limits:** two live UI Enter events are demonstrated separately from the native race; the actual Main IPC accepts both requests, without an Engine/model/provider call. The barrier makes an already permitted async process ordering deterministic. Loss of new uncommitted work requires it to be written after the successful creation and before the losing completion; it is not claimed for every ordinary duplicate Enter timing. No existing-worktree switch is needed to trigger the unsafe rollback.
- **Recovery:** switch the Session back to main and recreate the worktree; deleted uncommitted files cannot be recovered by that workflow. Branch recovery through Git reflog does not restore uncommitted content.
- **Confidence:** high.
- **Fix direction:** synchronously reject/serialize duplicate UI and Main workspace mutations, and make creation rollback prove ownership of the specific worktree/branch created by that invocation before removing either. A preexisting-path Boolean taken before concurrent creation is not sufficient ownership proof.

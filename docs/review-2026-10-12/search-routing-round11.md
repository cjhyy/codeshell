## R56 / W22 [P3] Content search silently omits sessions older than its 500-candidate band

- **Primary location:** `packages/pet/src/disclosure/search.ts:85–89`, where capped candidates are accepted and `truncated` starts false. Cap definition **:19**. The catalog sorts by transcript mtime and slices at `packages/pet/src/disclosure/catalog.ts:47–54`.
- **Production entry/defaults:** App's normal Cmd/Ctrl+P opens SessionSearchModal (`renderer/App.tsx:1386–1388,2687–2695`), user chooses “对话内容” and enters two or more characters. The actual hook calls preload searchSessionContent; `preload/index.ts:1031–1032` invokes `session:content-search`. Main handler `main/index.ts:4886–4891` trims/validates length 2–128 and calls `searchSessionTranscripts(sessionsRoot(), trimmed, {budgetMs:5000})`. **500 candidates is a hard-coded CANDIDATE_LIMIT**, not a user setting or an optional maxCandidates parameter. Main changes the time budget only; result cap defaults separately to 20 and snippet cap to 3 (`disclosure/search.ts:16–19,80–85`).
- **No prior UI scope notice:** SessionSearchModal's content toggle/placeholder/hint say “对话内容”, “搜索对话中的内容…” and “输入至少 2 个字符搜索会话内容” (`renderer/i18n/ns/panels.ts:248–260`). Its content-result header and empty state do not say “only the most recent 500”. The title-mode “近期对话” default is a separate mode and is not displayed as a content-search scope. The only incompleteness notice is conditional on result.truncated at `SessionSearchModal.tsx:179–187`, using “结果不完整（已达搜索上限）” from i18n :262.
- **Stable reproduction:** create 500 valid recent ordinary work sessions with unique transcript mtimes `1700000000+i` seconds, plus one valid older session whose transcript has a distinctive query and mtime `1600000000`. Actual listWorkSessionsOnDisk(limit:501) returns 501 and places older-target at exact index 500; explicit assertions exclude directory iteration/timestamp tie uncertainty. The real search with the **production 5000ms budget** scans exactly 500 newer transcripts, returns no matches and **truncated:false**, despite that known older match. The target also exists in the rendered session index, so inability to map a disk-only result is not the explanation.
- **Visible impact:** actual SessionSearchModal/useSessionContentSearch displays “未找到匹配内容” and no incompleteness warning. Narrowing the query or pressing retry does not expand the hard-coded candidate band. The user may conclude a known older conversation lacks the text. Nothing is deleted and unrelated recent search still works.
- **What truncated already means:** it is not merely “more than 20 matching rows.” The worker sets it on elapsed **time budget** or match cap (`search.ts:94–95`) and on skipped **oversized transcript candidates** (:110–112). Its UI wording is generic incomplete results. The missing candidate-cutoff signal is therefore inconsistent with existing time/coverage semantics, not a request for unbounded scanning or a new feature.
- **Counterexamples/recovery:** same old transcript is found normally in a two-session catalog, with truncated:false. The test's deterministic expired-deadline control (`budgetMs:-1`, test-only) returns truncated:true and the actual modal displays the existing incomplete-results message. Updating only the older target's mtime moves it into the selected candidate band, and the same unmodified query/content is then found. That filesystem control demonstrates the candidate cutoff cause; it is **not** recommended that users edit transcript files to recover. Practical current workaround is title search or manual opening of known older history; content retry alone cannot find an excluded old candidate.
- **Evidence:** `search-cap-ui.test.tsx` / `search-cap-ui.log`, 2 tests / 14 assertions. Exact emitted defective reply: `{"matches":[],"scannedSessions":500,"truncated":false}` for a verified catalog of 501, followed by successful same-text lookup when the candidate band changes. No time-budget expiration, large/unreadable file, archived/subagent/ephemeral exclusion or missing UI-index condition is needed.
- **Independence:** unlike R23, this does not fail all project/session resolution on an offline root; all owned files are healthy. Unlike R29, it does not change project state. Unlike R49, it does not query Collection packages or swallow stale-source errors. Its root cause is lost candidate-pagination/coverage information in Pet's shared transcript search.
- **Confidence:** high. Suggested correction: obtain an overflow indicator (e.g. at least one extra eligible candidate or paged catalog) and mark truncated when more candidates exist, or page within the existing time budget. Keep bounded resource use and the current UI warning.

Widget native open requests eventually use the same target navigator; W21 remains scoped to the independently reproduced renderer intent ordering, not a multi-window ownership bypass.
- Second-instance focus skips destroyed windows, restores a minimized live candidate and focuses it (`main/quick-chat-startup-cleanup.ts:34–48`). Selection of a first live window is an explicit fallback policy; no additional failure was established.

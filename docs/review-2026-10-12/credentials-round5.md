# Desktop credential review, round 5

Baseline: `84740d56e55517b004948a0a0e07649ad6fbf998` in `/Users/admin/.codex/worktrees/server-desktop-review-20261012/codeshell`. No product files were edited or rebuilt. This report describes two new findings; the two Cookie collision examples below share one root cause and count as one finding.

## C1 [P2] Adding another Cookie account silently replaces an existing account

- **Production entry:** Settings → Credentials → Cookie → “弹窗登录并保存”, or “抓全部” followed by an account-name prompt. `packages/desktop/src/renderer/credentials/CookieTab.tsx:102–109` generates the ID, `171–189` saves a newly captured login, and `239–245` saves a browser capture. Both call the real preload/IPC `credentials:save`, whose handler is `packages/desktop/src/main/index.ts:4023–4029`. `CredentialStore.save` at `packages/core/src/credentials/store.ts:368–384` replaces the whole same-ID record.
- **Reachable sequence A, no races:** add an account for an ordinary site that has no username extraction script, such as `accounts.example.test`. The actual login controller returns no `suggestedLabel` for that domain: `credentials-login/index.ts:291–301` only attempts extraction when `usernameScriptFor` supplies a script; `login-state.ts:86–113` supports only YouTube, Bilibili, X, and Twitter. CookieTab therefore uses the localized default name “账号”, producing `example__account`. Rename that first account and set its permissions, then use the same ordinary *new account* flow for a second identity on that site. The new record is again `example__account`; renaming the first account leaves its ID unchanged, so it does not avoid the collision.
- **Reachable sequence B, no races:** click “抓全部”, name the saved identity “工作账号”; repeat with “个人账号”. Their names are different, but ASCII-only slug normalization strips all Chinese characters and uses `account` for both, yielding `browser__account` both times. These are ordinary values supported by the Chinese UI.
- **Observed result:** the first scenario ends with exactly one record. Its old Cookie jar is replaced by the second synthetic jar; its renamed label returns to “账号”; both `autoUseByAI` and `autoInjectByAI` disappear (read as off); `meta.switchMode` changes from `clear` to the new-account default `merge`; and a pre-existing synthetic `meta.note` marker is absent. This demonstrates whole-record replacement, not an extra hidden card or a mere display label problem. The second scenario likewise ends with only “个人账号” and the second jar, using the first record's ID. Both additions present normal success feedback without a replacement review or confirmation.
- **Metadata boundary:** `meta.note` is only a synthetic stored marker used to prove replacement; the current Cookie UI does not expose a separate notes editor. Existing metadata fields are replaced with the new capture's metadata object. The original Cookie value is unavailable from the credential store after the second save; no claim is made that an already-open browser session is immediately cleared.
- **Evidence:** `credentials-e2e.mjs` drives the actual built Electron UI, real `credentials:save`, `list`, and `patchMeta` IPC and real on-disk CredentialStore. `observations.json` records the two scenarios and checks parsed synthetic jars on disk before/after. `cookie-overwrite.png` shows the surviving second account. `credentials-e2e.log` records completion with exit 0.
- **Recovery:** the missing first account must be captured/logged in again; renaming a saved account cannot prevent the collision. The impact is lost saved identity and its associated metadata/policy, not model execution or an attack.
- **Fix direction:** generate a unique stable ID for each new capture; only reuse an existing ID for an explicit update/relogin. If deliberate replacement is supported, review it explicitly before saving.

## C2 [P3] A failed Token save has no visible explanation

- **Production entry:** Settings → Credentials → Permission Token → fill ID, name, Token value → Save. `packages/desktop/src/renderer/credentials/TokenTab.tsx:61–82` awaits `window.codeshell.credentials.save` without `catch`; the button at `249–252` invokes it with `void save()`.
- **Reachable failure:** the existing credential store is unreadable/corrupt after the page loads. The actual `CredentialStore.mutate` refuses to replace it at `store.ts:349–356`, and `credentials:save` rejects through Main and preload. This is an intentional backend data-preservation guard whose failure must reach the user.
- **Observed result:** after a real store rejection, the page has zero alerts and no message containing the error; the only error is an unhandled renderer `pageerror`: `Error invoking remote method 'credentials:save': Error: refusing to modify an unreadable credential store; move the corrupt file aside to start a new one`. The ID/name/secret draft remains present. Restoring the test store and clicking the same Save succeeds and clears the form, so this is a failure-feedback/recovery-guidance defect, not lost Token input or a permanently broken save button.
- **Evidence:** `credentials-e2e.mjs` temporarily writes invalid JSON only to its own synthetic `credentials.json`, clicks the actual Save button, checks the page and draft, immediately restores the file, and retries successfully. `observations.json`, `token-write-failure.png` (password field masked), and `credentials-e2e.log` capture the result.
- **Fix direction:** catch the rejected save, show a persistent/accessible error or toast, retain the draft, and let the user retry after fixing storage. Existing metadata/delete handlers with similar missing catches were inspected but are not separately counted without their own reproductions.

## Validation and fixture limits

Run:

```sh
node scripts/run-isolated-node-smoke.mjs /tmp/codeshell-review-20261012-credentials-round5/credentials-e2e.mjs
```

The executable is guarded by the repository's isolated Node runner. The actual Electron Main is bootstrapped using `prepareConfinedElectronFixture` with an exact dummy loopback origin and verifies its private HOME/network receipt. Renderer HTTP/HTTPS requests are aborted. Neither a model nor an external service is called. Only the login/capture handlers are replaced, to return minimal, fictional Cookie jars; `credentials:save`, `list`, and `patchMeta`, their IPC transport, CredentialStore mutations, and UI event paths are production code.

For this test, `safeStorage.isEncryptionAvailable()` returns false in Electron Main, selecting the existing production `SafeStorageCipher` plain fallback. The credential records are fictional and live only in the test's private HOME, which is removed on completion. This validates the UI/ID/store behavior and failure propagation; it does **not** validate native keychain encryption, real website login, or real Cookie extraction. The initial harness attempts hit the startup trust dialog and a native keyring interaction; those were harness limitations and are not product findings. The final script dismisses the trust dialog normally and selects the supported storage fallback before mutations.

Static exclusions: local/server Link actions already surface failures and reload their lists; the local authorization dialog has retry/cancel handling. Existing R28 plugin-initialization and R26 Skills conflict findings were not repeated. Optimistic plugin-toggle failure and project-scoped Token mutations remain unvalidated candidates and are not counted here.

## FILES-R7-01 — P2: single Edit interprets literal replacement text and reports the intended text as if it was written

- Source: `packages/core/src/tool-system/builtin/edit.ts:94`; persistence at `:98`; summary uses the unexpanded `newLf` at `:104–108`. The default `replace_all: false` branch calls JavaScript string `replace` with a string replacement. The all-occurrences branch uses split/join instead.
- Ordinary trigger: a unique `old_string` is replaced with code or prose containing `$&`, `$$`, `` $` `` or `$'`. For example, editing `before PLACEHOLDER after` with `new_string: "price = '$&';"` should write that exact text between the unchanged prefix/suffix.
- Observed: the real Edit returns success and a diff line `+ price = '$&';`, but persists `before price = 'PLACEHOLDER'; after`. The other tokens insert one dollar, the original prefix, or the original suffix. A subsequent real Read returns the altered bytes. These four token behaviors share one root cause and count as one bug.
- Control: an ordinary replacement and `$1` without a matching capture group stay literal; the identical `$&` replacement with explicit `replace_all: true` also stays literal. The input is schema-compatible and uniquely matches the file.
- Impact: normal text/code edits can silently write different content from the requested replacement; the success diff can obscure that difference. No code execution, real user file, model, approval path, full executor, or UI was exercised. All files were owned temporary fixtures and removed.
- Evidence: [fixture](evidence/files-edit-literal.test.ts), [first raw stdout/stderr](evidence/files-edit-literal.first.log), [first exit](evidence/files-edit-literal.first.exit.txt): **6 pass / 22 expect / exit 0**, guarded completion present.
- Suggested correction: use a replacement callback or literal slicing for a single replacement, preserving the exact `new_string` bytes after the documented EOL conversion.

## FILES-R7-02 — unconfirmed behavior candidate: Glob chooses the first 200 walked files before sorting by modification time

- Source: `packages/core/src/tool-system/builtin/glob.ts:90` truncates the walker result; `:101` sorts only that subset. The description at `:16` promises returned paths sorted by modification time, but does not explicitly require selecting the globally newest 200. The returned subset is sorted, so that description alone does not prove a violated contract.
- Ordinary trigger: a pattern matches more than 200 source files and the newest file lies outside the first 200 walker entries. A caller might expect the newest matching file to appear, but no explicit global-newest-page contract or consumer expectation was located. The 200-result cap itself is not treated as a defect.
- Observed: among 201 owned files, the first query displays 200 and explicitly reports one omitted file. The fixture makes the omitted file strictly newer than every displayed file, using fixed timestamps rather than a sleep. A second normal query still omits it. This avoids assuming any particular filesystem traversal order. A three-file control correctly sorts newest first.
- Conditional impact: a caller expecting globally newest results can miss the most recently modified matching file; narrower patterns can recover it. This remains a candidate and does not count toward confirmed findings. No pagination API, global platform ordering, Windows behavior, or UI behavior is claimed.
- Evidence: [fixture](evidence/files-glob-order.test.ts), [first raw stdout/stderr](evidence/files-glob-order.first.log), [first exit](evidence/files-glob-order.first.exit.txt): **2 pass / 8 expect / exit 0**, guarded completion present.
- Dedup: May 30's `findings.json` item 123 reports missing count headers/pluralization above 200; this finding concerns selecting the wrong time-ordered subset and requires a different change. No additional formatting finding is counted.
- Follow-up: clarify whether the contract requires globally newest results. If so, select the newest 200 across all matches before formatting; otherwise document that ordering applies only to the arbitrary capped subset. No further validation or product change was performed after this downgrade.

## FILES-R7-03 — P3: Node Grep fallback silently rejects directory-qualified globs

- Source: `packages/core/src/tool-system/builtin/grep.ts:384` tests only `entry.name`; `:389–394` builds an anchored regex from the complete glob. The single-file branch also tests only the basename at `:371`. The public input schema calls this an unrestricted string glob pattern used to filter files (`:105`). The ordinary ripgrep route forwards the complete `glob` to `--glob` at `:220`, while the fallback comment at `:268–270` intends equivalent filtering. No directory-qualified example was found in the public description; support is inferred from the generic glob contract, unchanged routing, and explicit equivalence intent.
- Ordinary trigger: both external search commands are unavailable and the caller searches `glob: "src/**/*.ts"` over a project containing `src/deep/answer.ts`. Expected: the built-in fallback finds the same directory-qualified source file, or explicitly reports an unsupported filter.
- Primary contract, read by root without executing the search programs: ripgrep's [official guide](https://raw.githubusercontent.com/BurntSushi/ripgrep/master/GUIDE.md) describes manual globs as using `.gitignore` syntax; Git's [official pattern documentation](https://git-scm.com/docs/gitignore) supports directory-qualified patterns and `/**/` spanning directories. This supports the ordinary pattern's meaning on the advertised ripgrep route; it does not establish that an actual external search ran in this audit.
- Observed: the actual Grep handler and recursive Node fallback find `src/deep/answer.ts:1:const needle = 42;` without the filter, but return `No matches found.` with that glob. The `*.ts` control finds both TypeScript files and omits Markdown. The test seam injects ENOENT for `rg` and `grep`, records the attempted command names, and never launches either command; this is the intended fallback trigger, not a fixture/environment failure.
- Impact: hosts using the built-in fallback can get a false negative for ordinary directory-scoped searches. This record does not claim actual `rg`/GNU grep execution, equality for every glob syntax, a real Windows installation, or permission behavior.
- Evidence: [fixture](evidence/files-grep-fallback.test.ts), [first raw stdout/stderr](evidence/files-grep-fallback.first.log), [first exit](evidence/files-grep-fallback.first.exit.txt): **2 pass / 7 expect / exit 0**, guarded completion present.
- Suggested correction: retain the original search root and match supported globs against the relative path with consistent glob semantics; reject unsupported syntax explicitly instead of returning a false absence.

## FILES-R7-04 — P3: oversized Read tells the caller to use paging that cannot pass its size gate

- Source: `packages/core/src/tool-system/builtin/read.ts:77–78` rejects text above 5 MiB before processing `offset`/`limit` at `:91–99`, yet recommends providing those arguments to read a portion.
- Ordinary trigger: Read an ordinary 6 MiB text file, then follow its error's recommendation with `offset: 1, limit: 2`. Expected: the suggested recovery works, or the message accurately states that this tool cannot page a file above the cap.
- Observed: both calls return the identical oversized-file error; the two-line page is never returned. An identical paging request over a small three-line text file works and excludes the third line.
- Impact and scope: inaccurate recovery guidance can lead the caller into repeated failed reads. The fixed size cap itself is not counted as a defect or proposed for removal. Grep is also recommended, so this is not a claim that all access to the content is blocked. No resource-exhaustion, binary, streamed model, or full engine behavior was tested.
- Evidence: [fixture](evidence/files-read-large.test.ts), [first raw stdout/stderr](evidence/files-read-large.first.log), [first exit](evidence/files-read-large.first.exit.txt): **2 pass / 6 expect / exit 0**, guarded completion present.
- Suggested correction: remove the impossible paging suggestion, or implement bounded text paging above the cap while preserving the resource limit.

## WEB-R8-01 [P3] A project rooted at `/` does not own its descendant cwd in the Web projection

- Source: `packages/web/src/lib/format.ts:20`, with normalization at `:12–14` and project/group consumers at `:39–42,62–63`.
- Contract: `projectForCwd` explicitly returns the project whose root owns the cwd, selecting the longest prefix. Existing `format.test.ts` establishes ordinary descendant grouping and V2 secondary-root support. `/` is a valid POSIX absolute directory value for this API; production `ProjectStore.resolvePickedRoot` (`packages/desktop/src/main/project-store.ts:743–760`) checks an existing absolute directory and contains no explicit filesystem-root exclusion. That registration observation is static; the fixture does not register or inspect the operator's filesystem root.
- Trigger: supplied project metadata contains primary root `/` (or V2 secondary root `/`) and a session cwd such as `/workspace`, with no more-specific matching registered root.
- Observed: normalization preserves `/`, then `isSameOrInside` checks the descendant against `//`. Exact `/` matches, but `/workspace` returns no project. Real `groupByProject` produces separate `Root project` and `workspace` groups, and the child group lacks `projectId`.
- Normal controls: a `/workspace` root owns `/workspace/pkg`, the longest `/workspace/child` root wins, a similarly named sibling does not match, and ordinary root/child sessions group together.
- Effect: the shared Web project projection loses the configured project name/identity for descendant sessions. `packages/desktop/src/mobile/components/SessionList.tsx:50–63` consumes this grouping and lookup; `packages/web/app/DesktopApp.tsx:117–121,315–320` also consumes the lookup. These UI effects are static wiring only; no actual rendered list, creation request, host authorization or filesystem operation is claimed.
- Direction: handle the filesystem-root boundary in ordinary prefix matching while preserving longest-root selection. This is a display/metadata defect; do not infer an authority bypass.
- Evidence: first three tests in [web-display-contracts.test.ts](evidence/web-display-contracts.test.ts); [first raw log](evidence/web-display-contracts.first.log). Those tests share the one successful shard with WEB-R8-02 below.
- Current main disposition (read-only): `main=34553b747f9a5b6acafe7ad1dd21905bcfa53cac` includes parallel commit `658b8c6fcdad0e9d4bfe8809c5adf6f95f19580d` (`fix(web): respect the remote Host project path case policy`). Its `isSameOrInside` now uses the existing slash when `base.endsWith("/")`, eliminating this `/`→`//` condition at source level. This is a source-diff observation, not runtime validation of the new implementation. The frozen finding and first raw evidence remain historical; do not treat WEB-R8-01 as a still-unfixed issue on this inspected main.

## WEB-R8-02 [P3] `image/jpg` normalization skips the client per-image size limit

- Source: `packages/web/src/lib/mobileAttachments.ts:78–82`; normal limit handling at `:84–90`, preparation at `:117–125,145`.
- Contract: this module advertises a 10 MiB per-image maximum. Supported ordinary images exceeding it enter conversion, while oversized GIFs fail rather than losing animation. `image/jpg` is explicitly recognized as a supported alias that becomes `image/jpeg`. The alias conversion must still obey the same per-image limit before preparing the upload metadata.
- Trigger: the selected `File` reports `type="image/jpg"` and has size in `(10 MiB,20 MiB]`, so the separate message-total limit does not reject it. This is conditional on that input MIME value; no claim is made that a particular browser or picker commonly returns it.
- Observed: `normalizeMobileImage` returns the same oversized byte count under MIME `image/jpeg`, bypassing both conversion and the later per-image check. `prepareMobileAttachments` forwards the oversized size into its injected `beginUpload` callback. When the fake ticket/fetch callbacks accept it, the production function emits an oversized upload descriptor.
- Normal controls: a small `image/jpg` becomes usable inline `image/jpeg`; an oversized GIF rejects before any upload callback. Existing normal JPEG/PNG, inline budgeting and upload-order tests also pass.
- Static production wiring: `packages/web/src/hooks/useRemoteApp.ts:1418–1431` calls this preparation function before sending. `DesktopApp.tsx:399–418` checks attachment count, total size and an image MIME prefix when adding files, so this size/MIME combination is not excluded there. `packages/server/src/mobile-remote/mobile-client-event-validator.ts:42–49` and `mobile-upload-service.ts:119–125` require the same 10 MiB limit for an upload-begin request. Their runtime rejection and UI recovery were not exercised.
- Limits: the fixture owns synthetic in-memory bytes and tests MIME/size handling, not JPEG decoding or a real uploaded image. Callback success is an explicit substitute, not evidence that the real service accepts oversized bytes. This finding is the client normalization/preparation inconsistency; no actual server rejection, timeout, data loss, limit bypass or platform behavior is claimed.
- Direction: normalize the alias before the ordinary size/conversion decision, then retain a per-image size check before preparing descriptors.
- Evidence: last three tests in [web-display-contracts.test.ts](evidence/web-display-contracts.test.ts); [first raw log](evidence/web-display-contracts.first.log).
- Current main disposition (read-only): `mobileAttachments.ts` is byte-identical between the frozen source and inspected main `34553b747f9a5b6acafe7ad1dd21905bcfa53cac`. There is no source fix for this finding in that comparison. No new-main execution was performed.

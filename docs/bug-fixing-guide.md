# CodeShell Bug 排查与修复 Guide

这份 guide 用于在 CodeShell monorepo 中持续排查、修复和验证 bug。判断依据以当前工作树、可复现行为和测试结果为准，不以过期 TODO 或历史评审结论代替验证。

## 1. 开始前保护现场

```bash
git status --short --branch
git diff --stat
git diff --check
```

- 先识别已有未提交改动；这些改动可能是正在进行的工作，不重置、不覆盖。
- 记录当前分支与相对远端的 ahead/behind 状态。
- `git diff --check` 先排除冲突标记、尾随空格等机械问题。

## 2. 建立基线

仓库统一使用 Bun。按“反馈快 → 覆盖广”的顺序执行：

```bash
# 改动附近的测试（把路径替换成实际受影响的测试文件）
bun test packages/<package>/src/<area>/*.test.ts

# 无需重新生成声明时的快速全仓类型检查
bun run typecheck:workspaces

# 静态规则与架构边界
bun run lint
bun run lint:engine-bypass
bun run lint:workflow-test-paths

# 全量测试
bun test

# 完整构建与 clean-checkout 类型门禁
bun run typecheck
```

如果基线已经失败，先判断失败是否由当前 diff 引入；不要为了“全绿”修改无关代码。

## 3. 定位 bug

对每个候选问题写清四件事：

1. **现象**：用户看到了什么错误行为。
2. **最小复现**：最少需要哪些输入、状态和操作。
3. **根因**：哪一层的哪个不变量被破坏，避免只描述报错位置。
4. **影响面**：是否涉及 core 公共契约、desktop IPC、renderer 状态、TUI 或外部运行时。

优先级建议：

- P0：安全、数据损坏、任意代码执行、凭据泄漏。
- P1：崩溃、主流程不可用、状态串线、不可恢复的数据丢失。
- P2：功能错误、竞态、边界条件错误，但有可靠绕过方式。
- P3：显示、文案或低概率非关键问题。

## 4. 修复原则

- 先补一个能在修复前失败的回归测试，再做最小但完整的根因修复。
- 保持包边界：core 不依赖 TUI；renderer 的运行时依赖必须保持 browser-safe。
- 涉及 session、workspace、权限和外部 agent 时，在入口与执行点都校验关键不变量。
- 异步流程同时检查成功、失败、取消、超时、重复事件与进程重启。
- 状态机更新应满足幂等性；迟到事件不能覆盖更新的终态。
- 不用扩大类型、吞异常或删除断言来掩盖问题。

### 持久化与并发检查清单

凡是 JSON、JSONL、日志、上传暂存或状态目录，都同时检查下面几项；只做原子 rename 并不等于安全：

- **读前限额**：先 `lstat/fstat` 校验文件类型与字节数，再读取；读取后才判断大小仍可能先耗尽内存。
- **无链接跟随**：拒绝符号链接的状态根目录、资源目录和目标文件；支持的平台用 `O_NOFOLLOW` 再校验已打开句柄。
- **写前限额**：序列化后按 UTF-8 字节数限制输出，并限制数组、Map、目录扫描和单条记录数量。
- **原子且私有**：唯一临时文件使用排他创建，写入后 rename，敏感状态保持 `0600`、目录保持 `0700`。
- **读改写加锁**：跨进程锁必须覆盖“重新读取当前版本 → 修改 → 原子保存”全过程；锁前读取仍会丢并发更新。
- **终态顺序**：队列/消息必须先持久化成功终态，再删除 payload；失败时保留可重试依据。
- **对象键语义**：外部键使用 null-prototype Map 或显式 own-property 判断，避免 `__proto__`、`constructor`、`toString` 进入原型链语义。

### 身份、路径与启动顺序检查清单

- IPC/网络请求里的路径、room、run、session、job 等标识只作为查找键；执行时从服务端权威状态重新解析并核对所有权。
- 先注册 owner、pending request、取消句柄和路由，再启动可能同步回调或立即退出的子进程/任务。
- 多文件操作先完成全部输入、权限、路径和配额预检，再产生二维码、凭据、状态文件或外部副作用。
- 不信任历史磁盘状态：反序列化时重新验证枚举、数字范围、时间戳、URL、路径归属和集合上限。

## 5. 分层验证

每次修复后按以下顺序验证：

1. 新增回归测试通过。
2. 同模块测试通过。
3. 受影响 package 的 typecheck/build 通过。
4. 根目录 lint 与架构 guard 通过。
5. 全量测试与完整 typecheck 通过。
6. UI 或跨进程问题补一次真实运行 smoke；无法自动验证时明确记录人工步骤。

测试通过只证明其覆盖的行为。若测试没有覆盖真实 IPC、进程生命周期或 UI 交互，不能把单元测试当作端到端完成证据。


## 7. 完成条件

一轮排障只有在以下条件都满足时才算完成：

- 已发现的问题均有明确结论：已修、非 bug、重复项或带证据的外部阻塞。
- 每个已修问题都有针对根因的回归测试，或说明无法自动化的原因。
- `git diff --check`、相关测试、lint、架构 guard、全量测试与完整 typecheck 均通过。
- 最终 diff 只包含本轮相关修改，没有覆盖用户既有工作。
- 交接说明包含改动文件、验证结果、残余风险与可复现步骤。

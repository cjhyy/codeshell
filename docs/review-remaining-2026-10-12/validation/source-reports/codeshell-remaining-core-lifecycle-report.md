## Findings for root adjudication

### CL1 — P2: a cold managed-run resume discards the supplied answer from actual execution

Primary location: `packages/core/src/run/RunManager.ts:298–303`; downstream: `packages/core/src/run/EngineRunner.ts:248–251`. Warm contrast: `RunManager.ts:263–270`.

When a persisted run is `waiting_input` and the process no longer holds its execution handle, `resume(runId, { userInput })` acknowledges the answer and writes it into a `run_resumed` event, then queues the unchanged snapshot. The built-in EngineRunner only receives that snapshot and calls `client.run(run.objective, { cwd, sessionId })`. Neither the snapshot nor execution context transports the answer; the runner does not read the event log. The model therefore receives the original objective again rather than the requested clarification. The run can finish successfully using the old objective while the supplied answer survives only as an event record.

Public reachability: the CLI `code-shell runs resume <id> --input <text>` constructs a new manager (`packages/tui/src/cli/commands/runs.ts:211–219`) and forwards `opts.input` at `:243–246`. It is inherently a fresh manager and takes the cold path for an existing waiting run. This is also reachable through the exported SDK RunManager (`packages/core/src/index.ts:570,618`). CLI execution itself was not run. Current Desktop production automation uses ordinary Sessions rather than RunManager (`packages/desktop/src/main/automation-host.ts:13–15`, `automation-service.ts:45–47`); its retained builder is documented as having no production consumer. No current Desktop input/approval resume failure is claimed. The finding is the generic SDK plus implemented TUI CLI managed-run path, with Desktop scope explicitly excluded.

Dynamic evidence: actual RunManager + FileRunStore + EngineRunner, with only Engine construction and in-process protocol client replaced by in-memory fakes. Seed persisted `waiting_input` snapshot objective `Original objective: prepare the report`, session `restored-session`; resume with `Use region EU and currency EUR`. Actual EngineRunner sends exactly the original objective and original sessionId. The actual event store contains the supplied answer, and the final snapshot is `completed`. This is an executed control-flow and persistence test, **not a real Engine/model/transcript recovery run**. Warm control uses the actual manager waiting hook and suspended handle; the exact answer is delivered once and the run completes. The per-run resume/cancel serialization is preserved and is not the defect.

Repair direction: durably hand off the accepted resume payload to the next attempt and consume it exactly once as new input, preserving the original objective separately. An append-only event alone does not make it an execution input. Avoid inferring that a cold approval grant can be reused for a different regenerated tool call; this finding is specifically user-answer delivery.

Dedup: distinct from earlier C3 (child role constraints lost from registry), R78 (paused Goal marked active without dispatch), R79 (Goal dispatch without bound WorkspaceContext), and R49 (collection error guidance). CL1 does dispatch and complete; its new user answer is missing from the request.

### CL2 — P3: concurrent auto-dream completions double-consume the cadence and lose a later session increment

Primary locations: `packages/core/src/services/memory-orchestrator.ts:406–426`, `packages/core/src/services/auto-dream.ts:171–180`.

The cadence mutation lock correctly serializes individual increments and subtractions. The longer read/execute/complete operation has no ownership claim, generation, high-water mark or shared in-flight guard. Two normal memory pipelines can both observe auto-dream due, capture overlapping counts, and each subtract its entire captured count on success. A session completing while both dreams run is then lost from the next cycle.

Executed trigger: seed five completed sessions and one ordinary manual preference memory (provides normal nonempty context). First pipeline increments to six and starts a pending dream. Second increments to seven and starts another dream. A third session increments to eight while both remain pending. Completing the first dream leaves two. Completing the second leaves zero, although the third session was outside both snapshots and should remain counted. Single-dream control preserves the corresponding later increment (six → seven → one).

Production reachability is more than two direct orchestrator calls. `packages/core/src/engine/run-finalize.ts:225–235` invokes the pipeline with `void` on each eligible non-ephemeral finalization, explicitly allowing it to outlive the foreground run. `AuxiliaryPipeline.runMemoryPipeline` (`packages/core/src/engine/auxiliary-pipeline.ts:148–198`) creates a new orchestrator each call once the transcript has eight messages; its only cached field is an auxiliary client, and it has no dream in-flight guard. Separate sessions/Engine instances sharing CODE_SHELL_HOME, or successive eligible finalizations before prior auxiliary work completes, can overlap. The normal manual Desktop Dream path was checked (`packages/desktop/src/main/dream-service.ts:96`): it calls `runDreamConsolidation` directly and does not subtract the cadence, so manual-plus-auto was **not** needed or claimed as the double-subtraction trigger.

Additional dynamic production-layer evidence: actual AuxiliaryPipeline, actual Transcript.inMemory (eight ordinary messages), actual runDreamConsolidation, actual MemoryOrchestrator and on-disk cadence/session summaries. Settings/model-pool/tool-registry dependencies are injected; the LLM is a pure in-memory object. Two successful summary calls and two pending dream calls produce captured counts `[6,7]` and the same eight → two → zero outcome. Dream replies have no tool calls. No real LLM, tool mutation, actual Engine finalization or multi-process host was executed; the finalization path is source evidence.

Impact is limited to duplicate auxiliary consolidation requests and incorrect next-cycle cadence. **No memory-body deletion/corruption, actual duplicate paid charge or permanent disablement was demonstrated.** The next cycle is delayed until enough later sessions accrue and the normal time threshold permits it. P3 is appropriate to the evidenced consequence. Root may retain only as a follow-up if this scope is considered too low impact.

Repair direction: atomically claim one consolidation per root and complete against a durable generation/high-water mark, preserving increments not included in that claim. Per-process guards alone do not cover multiple worker/host processes sharing the cadence file.

Dedup: the previous report has no auto-dream/cadence finding in its 86-item README/priority list; this is unrelated to provider retry accounting C4. The existing code already fixes unlocked increments and the single-dream mid-flight reset; CL2 is the remaining overlapping-consumption case.

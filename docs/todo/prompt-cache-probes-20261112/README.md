# 上下文账本方案的缓存探针（2026-11-12）

验证 `../prompt-cache-cross-run-context-ledger-20261112.md` 里的设计假设。全部请求经 OpenRouter，内容是合成文本。

- 脚本：`context_ledger_probe.py`
- 原始结果：`results-20261112.txt`、`results-followup-20261112.txt`
- 线路：`openai/gpt-6.1-sol`（承载方 OpenAI）、`anthropic/claude-sonnet-5`（承载方 Claude Platform on AWS）
- 用量：144 次请求，prompt 合计约 1.6M token，其中约 0.8M 未命中缓存

## 1. 测试方案

### 1.1 要回答的问题

| # | 假设 | 对应方案章节 |
|---|---|---|
| H1 | 现在的做法（新 run 拿走旧动态块）只能复用到旧动态块之前 | 2.1 |
| H2 | 旧动态块留在原位、只追加变化，能完整复用上一个 run | 3.1 |
| H3 | 回头折叠一份旧快照，会让其后的缓存全部失效 | 2.2 |
| H4 | 不折叠（攒批）就完整命中 | 3.3 |
| H5 | 在本 run 开始处放断点，run 内发生改写时之前的历史仍能命中 | 3.4 |
| H6 | 缓存读取只落在断点上，而不是"最长公共前缀" | 2.2、第 8 节 |

### 1.2 方法

每个变体用全新的随机标识发三次请求，间隔 8 秒：

1. `r1`：冷启动，写入缓存。
2. `r2`：在 `r1` 后追加一轮工具调用。对照，应读到 `r1` 的全部。
3. `r3`：被测的变体。

指标是 `r3` 的缓存读取量占 `r2` prompt 的比例。每个变体每条线路跑两遍。

请求形态照 CodeShell 的线上格式：

- GPT 线路：`prompt_cache_key`、`prompt_cache_options: {mode: "implicit", ttl: "30m"}`，断点用内容块上的 `prompt_cache_breakpoint`，位置为系统、稳定边界、上一次命中的边界。
- Claude 线路：内容块上的 `cache_control`，位置为系统、稳定边界、最后一条消息。
- "仅隐式"对照组：不带任何断点和 `prompt_cache_options`，只在 GPT 线路跑。

消息段：系统段约 3.6k token（GPT 口径），动态块、每份工具结果、每份快照各约 1.6k。

## 2. 结果

两遍结果一致，下表取整。

### 2.1 跨 run

| 变体 | r3 的布局 | GPT | Claude |
|---|---|---|---|
| X1 现状 | 拿走旧动态块，末尾放新块 | 43% | 45% |
| X1 仅隐式 | 同上，无断点 | 43% | — |
| X2 账本 | 旧块留原位，末尾追加一小段变化 | **100%** | 45% |
| X3 旧块留原位 + 整块重发 | 旧块留原位，末尾再放一份完整新块 | 100% | 45% |
| X2a 账本 + 内容统一用数组形式 | 同 X2，所有文本内容都以文本块数组发送 | 100% | **100%** |
| X2m 账本 + 旧用户消息保留断点 | 同 X2，上一个 run 的用户消息继续带断点 | 100% | **100%** |

43%–45% 正好是系统段加第一条用户消息的大小。

### 2.2 run 内改写旧快照

| 变体 | r3 的布局 | GPT | Claude |
|---|---|---|---|
| M1 现状 | 旧快照换占位符，动态块挪到末尾 | 36% | 37% |
| M1 仅隐式 | 同上，无断点 | 36% | — |
| M3 只换占位符 | 旧快照换占位符，动态块不动 | 36% | 37% |
| M2 攒批 | 不改写 | **100%** | **100%** |
| M4 改写点在"run 开始处断点"之后 | 改写本 run 内的一份结果，断点在动态块上 | 69% | 70% |
| M5 改写点很靠后、唯一断点很靠前 | 改写同一份结果，断点只在最早的用户消息上 | 36% | 38% |
| M5 仅隐式 | 同上，无断点 | 36% | — |

36%–38% 是系统段的大小；69%–70% 是到动态块为止的大小。

## 3. 结论

| 假设 | 结论 |
|---|---|
| H1 | 成立，两条线路都只复用到第一条用户消息 |
| H2 | GPT 成立。Claude 只在内容表示稳定时成立，见下 |
| H3 | 成立。M3 说明单是折叠旧快照就足以让缓存退到系统段，与动态块是否被挪动无关 |
| H4 | 成立，两条线路 100% |
| H5 | 成立，两条线路都能读到断点处（约 70%） |
| H6 | 成立。M5 里公共前缀到约 69% 处，但两条线路都只读到 36%–38%；GPT 的"仅隐式"也一样。读取只落在系统段末尾、显式断点、或上一次请求的完整前缀上 |

### 新发现：Claude 线路上，断点的有无会改变前缀

X2 在 Claude 上没有生效：上一个 run 的用户消息在 `r2` 带断点、在 `r3` 不带，缓存就从这条消息开始失效。两种做法都能恢复到 100%：

- 所有文本内容统一以文本块数组发送，不随是否带断点而在字符串和数组之间切换（X2a）。
- 该消息继续带断点（X2m）。

同样的切换发生在工具结果消息上时不影响命中（M2 里上一次的最后一条工具结果从带断点变为不带，仍是 100%）。受影响的是与另一条用户消息相邻的用户消息，推测与相邻用户消息在转换为 Anthropic 格式时被合并有关，这一点没有单独验证。

GPT 线路不受影响。

## 4. 局限

- 每个变体每条线路 2 遍；上下文只有 1–1.6 万 token，没有测 30 万 token 量级。
- 间隔固定 8 秒，没有测缓存有效期边界。
- 只测了两条线路，都经 OpenRouter；直连没测。
- 工具表只有两个简单工具，没有覆盖工具表冻结的部分（见 `../prompt-cache-probes-20261111/`）。

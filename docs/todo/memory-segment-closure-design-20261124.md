# 记忆写入重设计：按工作段收尾、有人说话才提取、自动记忆有试用期

日期：2026-11-24
状态：M0–M2 已实现，M3、M4 待做。实现时对 5.3 的调整见 5.3.1
基线：`origin/main` a2bcd3550
关联：`docs/todo/memory-final-design.md`（P2「背压 / 注入 cap」挂起项）、`docs/todo/external-runtime-memory-20261026.md`

## 1. 结论

1. **现在的后台记忆调用里，有一块是纯浪费，删掉就行。** 每次触发都会生成一份会话摘要，但仓库里没有任何代码读它。这一项约占流水线调用的四成。
2. **「空闲才跑」不够，要加「有人说话才跑」。** 用本机真实会话重放：只按空闲 5 分钟触发，次数只降三成；再要求这段时间里出现过人输入的消息，次数降到原来的三分之一。被挡掉的主要是后台任务提醒、自动续跑这类没有人参与的运行，它们恰好是噪音记忆的主要来源。
3. **记忆库要能收敛，不能只进不出。** 自动提取的条目每条都会进入每个会话的注入索引，而清理它们的 TTL 现在没有生效。给自动条目加一个试用期：一段时间内没被读过就不再注入，再久就进回收站。

分三步做，每步都能独立上线：M1 删浪费，M2 改触发，M3 加试用期。

外部 Claude Code / Codex 会话的提取保留，但现在是半截的：没选提取模型时 Codex 会话根本提取不了，提取出来的记忆外部会话自己也看不到索引。补齐的办法见 5.5，其中读的一侧单独排成 M4。

### 2.2 本机数据

样本是单机近三周的真实工作会话，量级有限，只用来判断方向。按仓库约定只列比例。

**提取产出**（来自 `memory.extraction_done` 日志）

- 46% 的提取没有产出任何候选。
- 有产出的部分，新增和更新的比例约 1.2 : 1：同一个主题在一个会话里被反复重写。
- 调用构成估算：每次触发约 2.6 次调用（提取 1、决策 0.6、摘要 1），摘要占约 38%。
- 触发次数最多的那个会话里，约八成的 user 消息是系统注入的（后台任务完成提醒、自动续跑等），不是人输入的。这一个会话贡献了近四成的新增记忆。

**记忆的使用情况**（「读过」指主代理调用 `MemoryRead` 读取全文）

| 来源           | 至少被读过一次 |
| -------------- | -------------- |
| 自动提取       | 36%            |
| 整合产出或晋升 | 76%            |
| 手动保存       | 82%            |

- 自动条目按类型：feedback 48%，reference 42%，project 24%。
- 当前项目的注入索引里，从未被读过的条目占体积约 44%。
- 历史上写入的自动条目，约三分之二最终进了回收站（包含 7 月那次批量清理）。

**缓存**（来自用量账本，近 30 天）

- 辅助摘要类请求约占全部模型请求数的 23%（其中包含 Mimi 等其它辅助调用）。
- 这类请求的缓存读取占输入不到一成。`memory-transcript.ts` 为「每轮触发」做的前缀缓存设计，在实际使用里基本没有命中。外部 CLI 的记忆调用缓存读取为 0。

**外部运行时会话**（近 30 天的 transcript 和日志；本机没有配置提取模型和辅助模型）

- 外部运行时承担了约四成的人输入消息、约六成的工具调用。关掉它们的提取，记忆就只能从一半左右的工作里学。
- 读过记忆的会话比例：原生（有注入索引）约 16%，外部 Codex（没有索引）约 11%，外部 Claude Code 为 0。读的路径是通的，但没有索引时用得少。
- 主代理很少主动保存：原生会话没有调用过 `MemorySave`，外部会话只有个别会话调用过。
- Codex 会话的记忆维护每次都失败，从未成功过（见 2.1 第 11 条），界面上没有任何提示。
- Claude Code 会话用会话自己的模型提取。它只占工作会话触发次数的约 16%，却贡献了约四成的新增条目：几乎每次触发都有写入（零产出约 4%，原生约 54%），每次触发的写入量接近原生的三倍。它写下的条目约七成是 project 类型（原生约一半），而 project 是历史读取率最低的类型。样本小，产出偏多是模型的原因还是会话内容的原因，还分不清。

## 3. 问题归因

1. **触发单位错了。** 流水线按「会话结束」设计（提示词、整合计数都这么假设），却按「每轮结束」执行。
2. **没有「值不值得跑」的判断。** 后台任务提醒、自动续跑、定时任务产生的运行，和人参与的对话一视同仁。
3. **流水线里有没人用的产物。** 会话摘要每次都生成，没有读取方。
4. **只进不出。** 自动条目写进去之后，每个会话都要为它付一行索引；清理只靠每天一次的整合循环。

## 4. 方案比较

| 方案                                | 做法                                               | 优点                           | 问题                                                                                            |
| ----------------------------------- | -------------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------------------------------- |
| A. 只降频                           | 流水线不变，改成空闲或收尾时触发，加增量游标       | 行为变化最小                   | 重放显示只按空闲触发只降三成到一半；没人读的摘要、只进不出的问题都还在                          |
| B. 会话只出摘要，长期记忆交给整合   | 会话结束只生成摘要，AutoDream 每天从摘要里批量提取 | 每会话成本固定                 | 摘要上限 500 字符，细节丢失后整合阶段提取不到；整合循环本身是多轮工具调用，不便宜               |
| **C. 按段收尾 + 人话门槛 + 试用期** | 见第 5 节                                          | 次数、单次成本、库的总量都有界 | 要动 core 的触发点，需要开关和重放验证                                                          |
| D. 关掉自动提取                     | 只靠主代理 `MemorySave` 和手动保存                 | 后台成本为零                   | 自动条目里约两成被读过 3 次以上，这部分价值会丢；主代理很少主动保存（见 2.2），实际等于不再积累 |

推荐 C。A 是 C 的子集，D 可以作为 C 上线后的对照实验（`memories.autoExtract: false` 已经支持）。

## 5. 设计

### 5.1 总览

```text
run 开始 ── 通知调度器：重置该会话的空闲计时；若上一段已空闲够久且游标落后，后台补一次收尾
run 结束 ── 通知调度器：启动空闲计时（热路径不调模型）

收尾（一个工作段一次）
  1. 取窗：游标之后的新消息
  2. 门槛：新消息里有没有人输入的消息；没有就跳过，游标不动
  3. 提取：1 次调用，只看新消息
  4. 写入决策：有候选才调用，逐条沿用现有守卫
  5. 推进游标
  6. 本地维护：整合门槛计数、试用期清扫（不调模型）
```

### 5.2 M1：删掉浪费

改动都在 `MemoryOrchestrator` 内部，原生和外部会话同时生效，不改触发、不改存储。

1. **删除会话摘要这一步**（`memory-orchestrator.ts` 的第 2 步）。`session-memories/` 下已有的文件不动，`session-memory.ts` 的读写函数先保留。`settings.memories.autoExtract: false` 的含义相应变成「不提取，只做整合计数」。
2. **整合门槛改为按「有变更的收尾」计数。** `recordSession` 只在这次提取对记忆库产生了新增、更新或删除时才调用。库没有变化就不会触发整合。状态文件的字段名不改。

预期：每次触发的调用数从约 2.6 降到约 1.6。

批量写入决策（把每条候选的决策合并成一次调用）不做：每次提取最多 2 条候选，只有同时出 2 条时才能省 1 次，收益很小，却要改提示词、解析和一批守卫测试。

### 5.3 M2：按工作段收尾

**游标**，存在会话 `state.json`：

```ts
memoryCursor?: {
  v: 1;
  eventId: string; // 已处理到的最后一条对话消息对应的 transcript 事件 id
  at: number; // 该事件的 timestamp，锚点失效时的退路
  closedAt: number;
};
```

取窗规则：

1. 在当前回放里找到 `eventId`，它之后的消息是新消息。
2. 找不到（被压缩、归档、分叉后 id 重映射）时，取事件时间晚于 `at` 的消息。
3. 没有游标的老会话，全部算新消息。
4. 新消息前面带最多 4 条已处理过的消息，标明「只用于理解上下文，不要从中提取」。
5. 仍受 `memory-transcript.ts` 现有的 3 万字符窗口约束。

为此 `Transcript` 需要一个新的只读方法，在现有回放的基础上给每条消息带上来源事件的 `id`、`timestamp` 和「是否人输入」。不改 `toMessages()`。

**门槛**，全部读结构化字段，不解析消息文本：

- 新消息里至少有 1 条人输入的 user 消息：`role` 为 user，没有 `injected` 和 `displayOnly`，`authority` 未设或为 `user`，没有 `source`。
- 会话的第一次收尾沿用现有的「对话消息至少 8 条」。
- 不满足门槛时不推进游标，内容留给下一次收尾。自动运行期间积累的内容，等人下次说话时一起处理。

**触发**：

| 触发     | 时机                                                                               | 说明                                                    |
| -------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 空闲计时 | run 结束后 30 分钟内，该会话没有新的 run 开始                                      | 进程内计时器，尽力而为                                  |
| 恢复时补 | run 开始时，发现游标落后且距上次活动已超过 30 分钟                                 | 后台执行，不阻塞本轮；处理的是本轮开始之前的内容        |
| 启动时补 | 进程启动后延迟执行，只看最近 7 天活跃且游标落后的会话，每次启动最多处理 5 个，串行 | 覆盖「聊完就退出、再也不打开」的会话                    |
| 一次运行 | 宿主没有注入调度器时（命令行单次运行、headless、测试）                             | Engine 保持现有行为：run 结束直接收尾一次，同样要过门槛 |

30 分钟与 Mimi 现有的 `PET_SEGMENT_DAILY_MIN_IDLE_MS` 一致。计时器只是加速器，后两种补偿保证不漏，所以这个值不敏感。

**组件边界**：

- `core/src/services/memory-closure.ts`（新）
  - `selectClosureWindow(messages, cursor)`：纯函数，输出新消息和上下文消息。
  - `closureGate(window, cursor)`：纯函数，输出执行或跳过及原因。
  - `MemoryClosureScheduler`：按会话计时、同一会话同时只跑一个、取消、销毁。P0 在 `ExternalRuntimeMemory` 里做的防抖逻辑搬到这里。
- `MemoryOrchestrator`：`run()` 拆成 `extract()`（提取加决策）和 `maintain()`（整合门槛、试用期清扫）。`run()` 保留给一次性运行使用。
- 宿主接线：桌面 worker、agent server、TUI repl 各构造一个调度器并注入 Engine。Engine 在 run 开始和结束时各通知一次。收尾执行时自己按设置创建模型客户端，不依赖发起它的 Engine 实例还活着。
- `ExternalRuntimeMemory`：复用同一套调度器、取窗和门槛，自己只保留 CLI 推理和归属校验。

**计费归属**：收尾发生在 run 之外。沿用外部会话已有的做法：用 `UsageLedger` 把调用记到原会话名下，用途仍是 `aux_summary`。

**取消**：会话关闭或删除、归属变化、项目信任撤销时，取消在跑的收尾（沿用 `assertCurrent`）。新一轮开始只重置计时器。原生会话在跑的收尾处理的是冻结快照，不必取消；外部会话的快照守卫目前要求「没有更新的 run」，这一期保持不变。

**失败处理**：

- 模型调用失败、超时或被取消：不推进游标。下一次触发（下一轮结束、恢复、启动）自然重试，不做循环重试。
- 记忆已写入但游标写入失败：下次会重复提取同一段，由现有的「完全相同则不写」守卫去重。
- 进程退出：计时器丢失，由恢复时补和启动时补覆盖。

#### 5.3.1 实现时的调整

实现计划见 `docs/superpowers/plans/2026-11-24-memory-m2a-segment-closure-native.md` 和 `…-m2b-segment-closure-external.md`。与上文不同的地方：

- **取窗读原始事件，不读回放。** 上下文压缩之后，回放会把旧消息换成合成 id 和同一个时间戳，游标会失效；原始事件只追加、id 稳定。手工选区功能（`Transcript.selectContextRange`）已经是这个做法。压缩摘要、会话交接、区间归档这三类事件不进窗口，它们是对别处内容的转述。
- **调度器挂在共享的 `EngineRuntime` 上**，宿主只传一个空闲时长。桌面 worker 是每个会话一个 Engine，`EngineRuntime` 是它们共享的那一层。
- **待收尾的会话不被空闲回收。** 会话的空闲回收也是 30 分钟，正好和收尾计时相撞。给它加上和后台任务同样的豁免之后，收尾可以继续走该会话的 Engine，复用现有的客户端解析、计费和整合循环，不必在 Engine 之外另造一套。
- **TUI 立即收尾**（每轮结束、过门槛、只看新消息）。终端里聊完就退出，30 分钟的计时器基本等不到。
- **启动时补没有做。** 它需要脱离 Engine 的独立执行器。恢复时补已经覆盖「下次再打开这个会话」；游标不动，漏掉的只有「聊完 30 分钟内退出应用、且再也不打开这个会话」。列为后续。
- **子代理和定时自动化的 Engine 整体不提取。** 它们的 user 消息来自父代理或定时任务，写进 transcript 时和人输入的消息没有区别，只能在 Engine 这一层按结构判断（`isSubAgent`、`origin: "automation"`）。
- **上下文消息合成一个条目**，角色是 `context`，开头写明不要从中提取，不逐条打标。
- **外部会话没有恢复时补。** 计时器丢了也不丢内容：游标没动，下一次收尾会连同之前那段一起读。

### 5.4 M3：自动条目的试用期

**定义**：dream 层、`origin: auto` 的条目，从 `createdAt` 起 14 天为试用期。

**注入规则**（改 `MemoryManager.buildInjectionIndexParts`）：

- user 层：全部注入，不变。
- dream 层：只注入满足任一条件的条目——不是自动提取的；还在试用期内；已经被读过至少一次。
- 其余条目不进索引，但仍在库里，`MemoryList` 能看到，提取时的去重目录里也在。

**清扫**：已经不再注入、且超过 60 天没被读过的自动条目，软删到回收站。在收尾完成后顺带执行，只做本地文件操作。

**与整合的分工**：整合循环的提示词不变。它本来就能看到每条的读取次数，负责合并和晋升。被晋升到 user 层的条目永久注入。

**现有的 `recallTtlDays`**：没有调用方，而且它清的是 user 层的 project 类型条目（会碰到手动条目）。建议删除这段不生效的代码，由上面的规则取代。

这样每条自动记忆的去向只有三种：被读过而留下，被整合晋升，或者到期退出。库的规模由「新增速度 × 试用期」决定，不再只增不减。

### 5.5 外部 CLI 会话

结论：保留提取，并把写和读两头补齐。

保留的理由有三条。外部运行时承担了一半左右的工作量（2.2）。Claude Code 和 Codex 各自的记忆只有它们自己读得到，CodeShell 的记忆库是原生、Codex、Claude Code 三种会话都能读到的唯一一层。读的路径已经存在（2.1 第 9 条），缺的只是索引。

现状有三个缺口，分别处理：

1. **写：规则与原生相同。** 按段收尾、人话门槛，不按运行时另设规则。产出偏多的问题先交给 M2 的降频和 M3 的试用期，上线后用 `memory.closure` 日志复查；仍然偏多就收紧提取提示词，而不是给外部会话单独加闸。
2. **模型：选了才跑，不回退到会话主模型。** 只用 `memories.extractionModel`，其次辅助模型。两者都没有时不调度、不抛错，设置页的记忆部分显示「外部会话的记忆提取未运行：未选择模型」并给出选择入口。两种运行时从此是同一条规则：Codex 不再每轮失败一次，Claude Code 不再用会话的主模型做后台提取。现有的约束保持不变：不会因为没选模型就改用别的账号的默认模型。
3. **读：外部会话启动时注入记忆索引（M4）。** 通道已有：宿主指引在会话启动时组装一次，Codex 作为 developer instructions、Claude Code 作为追加的系统提示（`external-runtime-service.ts:1054`）。内容用与原生相同的注入规则（M3 之后的规则），启动时取一次快照，会话中途不更新，这样不破坏 CLI 自己的提示缓存。排在 M3 之后：索引要先收敛，否则塞给外部会话的体积太大。

CLI 自带的记忆不读也不关（第 9 节）。两套记忆并存：CLI 的只服务它自己，CodeShell 的服务所有运行时。

## 6. 预期效果与验收

按 2.2 的重放数据估算：

| 指标             | 现状               | M1 后  | M2 后                   |
| ---------------- | ------------------ | ------ | ----------------------- |
| 触发次数         | 1.00               | 1.00   | 约 0.2–0.3              |
| 每次触发的调用数 | 约 2.6             | 约 1.6 | 约 1.6                  |
| 后台记忆调用总量 | 1.00               | 约 0.6 | 约 0.15–0.2             |
| 单次提取的输入   | 整个窗口，每次重读 | 同左   | 只有新消息加 4 条上下文 |

M3 不减少调用，它减少的是每个会话的注入体积：未读自动条目占的那部分（本机当前项目约四成）在试用期满后退出索引。

验收看三个现成的数据源，上线一周后对比：

1. 日志新增 `memory.closure` 事件（原因、新消息数、人输入消息数、候选数、是否跳过）。每会话收尾次数应不超过运行次数的三分之一。
2. 用量页里辅助摘要类请求的占比应明显下降。
3. 记忆库：试用期满的自动条目里，被读过的比例。这个数决定自动提取值不值得继续开。

## 9. 明确不做

- 滚动会话摘要。摘要没有读取方，等有需求再设计。
- 向量检索、图谱。沿用 `memory-final-design.md` 的原则。
- 改主代理的系统提示词去引导它主动存记忆。方向是对的，但会动到提示词前缀和既有评测，单独立项。
- 读取 Claude Code / Codex 自带的记忆文件作为来源。格式和开关都不受我们控制，先不做。
- 新增 transcript 事件类型。游标放在会话状态里，避免旧版本读不懂新事件。
- 积压上限（库满了就暂停新增）。试用期已经让规模有界，先不加第二道闸。

## 10. 待你决定

1. **空闲阈值**：已按 30 分钟实现（`MEMORY_CLOSURE_IDLE_MS`，与 Mimi 一致）。
2. **M3 的两个天数**：试用期 14 天、清扫 60 天，是否合适。
3. **外部会话没选提取模型时怎么办。** 已按「选了才跑」实现：不回退到会话主模型，设置页的记忆部分在没选后台任务模型时给出说明（5.5）。代价是没选模型的用户，Claude Code 会话的提取会停掉；Codex 会话本来就没有在跑。
4. **M1 是否跟 M0 一起提**。两者都很小，互不依赖；M0–M2 在同一个 PR 里，按阶段分成几个提交。
5. **M4 做不做。** 不做的话，外部会话提取出来的记忆主要由原生会话受益，外部会话只在模型主动调用 `MemoryList` 时才用得上。

## 11. 实现前要核对

1. 上下文压缩和区间归档之后，回放里消息的来源事件 id 是否还能对应上；对不上时退回时间戳的规则是否足够。
2. 原生路径在 run 之外计费时，`UsageLedger` 的归属与现有 `recordExternalBilledUsage` 的口径是否一致。
3. 注入索引的条目因试用期满而减少时，现有的「只告诉模型变了哪一条」的增量机制是否覆盖批量移除。
4. 启动时补需要枚举会话状态，不能在 Electron 主线程上做同步 IO。
5. M4：两个 CLI 对追加指引的长度上限；索引超出预算时的确定性截断顺序（手动条目优先，其次按最近使用时间）；注入后对它们各自提示缓存的影响。

# 外部运行时"用起来不顺"整体改造方案（2026-11-19，草案待评审）

问题清单见 [external-runtime-session-issues-20261119.md](external-runtime-session-issues-20261119.md)（T1–T10）。
本文不逐条打补丁，而是把十条归并成四个根因，各给一个改造方向，再排期。
代码位置以 `origin/main` 71ffe8702 为准。

## 1. 为什么不顺：四个根因

| 根因                          | 一句话                                                                                                                  | 覆盖           |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------- |
| R1 外部会话是二等公民         | 第一期"先隔离再说"的策略还在：独立浏览器桶、没有电脑操控、只放行一个工具桥。用户已经把它当主力用了，能力面却没跟上      | T1 T2          |
| R2 "在等什么"没有模型         | 等用户、等后台、等审批、等页面加载各管各的；Goal 只有会话级的"挂起/不挂起"，一条线在等，所有线都停；等的是什么也看不见  | T3 T5 T7 T10   |
| R3 "需要你"的入口太碎、没分级 | 提问卡、ask_user 卡、审批卡、面板授权、接管窗口各有各的 UI 和输入框；该问的（生产写入）和不该问的（工程小决定）一个待遇 | T6 T9，T4 一半 |
| R4 系统对自己的状态不说实话   | 全被拒绝仍报"完成"、没加载完就说"已跳转"、文档推断当线上事实、工具说明写的默认值和代码不一致                            | T4 T7 T8       |

## 2. 改造后应该是什么体验

1. **外部会话能做的事和原生会话一样多**：同一份浏览器登录、能接手用户已打开的标签页、能操控电脑。
2. **代理只在真的无事可做时才停**；停下来时，界面上一眼能看到它在等什么、等了多久、怎么解除。
3. **找用户只有一个地方、一个输入框**；小事自己定并说明，大事（不可逆/对外/生产/凭据）才问，而且必须得到明确同意。
4. **每个状态都是真的**：完成就是完成，被拦就显示被拦，不确定就说不确定。

## 3. 四个工作流

### W1 能力对齐（解决 R1）

**W1-a 浏览器：外部会话改用项目浏览器桶**

- 现状：`external-runtime-browser-bucket.ts` 把外部会话固定在 `external-runtime:<sessionId>`；`panel-access-request.ts` 只在这个桶里找面板标签页，所以永远找不到；每个新会话都是空 Cookie。
- 方案对比：
  - **甲（推荐）：取消这个特例，外部会话和原生会话一样绑定项目桶。** 登录共享、面板授权自然可用；"自动化不要碰用户正在看的标签页"这层保护由已有的标签页控制权（任务窗口 vs 面板标签需用户授权）承担，不靠分区。删代码多于加代码。
  - 乙：保留隔离，只让面板授权跨桶去找。授权能用了，但授权后驱动的是另一个分区的标签页，两套 Cookie 并存，"为什么这里登录了那里没登录"会一直困扰用户。
- 代价：已有的 `external-runtime:s-*` 分区作废，用户在外部会话里登过的站点需要重登一次；旧分区目录可在升级时清理。
- 改动点：`agent-bridge.ts:2353`、`agent-run-browser-registration.ts:57`、`renderer-browser-session-ipc-authority.ts:30`、`browser-session-ipc.ts:125`（去掉"忽略改绑"的特例）。

**W1-b 电脑操控：把 Host 自带的 cua-driver 挂给外部会话（已决定开放）**

- **推荐路线 A**：外部 CC 的 MCP 配置里除工具桥外再加一个 Host 的 cua-driver 条目（复用 `cua-driver-host.ts:204` `mcpDeclaration()`），`--allowed-tools` 同步放行；Codex 侧把它设为 enabled。现有的输入闸门、会话 lineage、光标/舞台、系统权限归属全部沿用，原生会话怎么管它就怎么管。
- 不选 B（经工具桥逐个转发）：要把几十个 CUA 工具全部重新声明并过评审，收益只是审批入口统一，而 W3 会用别的办法统一。
- 不选 C（放行用户自己的 cmux-cua）：绕过 CodeShell 的闸门，和 `mcp-config.ts:161` 的安全立场冲突。
- 需要确认的技术点：服务名 `host:cua-driver` 含冒号，CC 的 MCP 工具名规则要求先规范化；外部会话的指引里要写清"内置浏览器里的页面用 browser\_\*，其他应用和用户自己的浏览器用电脑操控"。

### W2 等待模型（解决 R2）

**W2-a Goal 只在代理声明"我在等"时才挂起**

- 现状：`external-runtime-service.ts:1950` 一轮结束时只要有后台任务在跑就挂起整个 Goal（`awaitsBackground`）。
- 方案：和等用户对称，新增显式工具 `wait_for_background`。
  - 一轮结束时有后台任务在跑、且代理没调用它 → **照常续轮**，并在续轮提示里注入一句："后台任务《标题》仍在运行，完成会自动通知你，不要轮询。还有不依赖它的工作就继续；没有就调用 wait_for_background。"
  - 代理调用了它 → 才进入现在的挂起流程。
- 为什么不用辅助模型判断"还有没有事做"：显式声明是确定的、可测的，也不引入额外模型调用；最坏情况只是多跑一轮才挂起。
- 防空转：沿用 PR#312 的"连续无进展"上限（`maxStopBlocks`）；另加一条，续轮里若代理只是重复"等后台"而没调用任何工具，宿主直接代它挂起。

**W2-b 后台任务有名字、有状态、能早报**

- DriveAgent 增加必填的 `title`（十几个字的人话标题）；通知、任务视图、Goal 等待条统一用它。
- 任务状态从"运行中/完成"扩成：运行中 / 等待审批 / 被拦（附拒绝次数）/ 失败 / 完成 / 完成但有被拒操作。
- 早报：任务连续被拒 N 次或等审批超过阈值，立即唤醒父会话，而不是等它空跑到结束。

**W2-c 页面"加载中"是一种等待**

- `browser_navigate` 等到加载完成或超时再返回，结果里写明"已加载 / 仍在加载"。
- vision 截到近乎空白的画面时，结果附一句"页面可能还没渲染，先 wait"。

### W3 找用户的统一通道（解决 R3）

**W3-a 一个"需要你"条，一个输入框**

- 主输入框上方只保留一个条，同一时间只显示一项，其余排队。提问（`wait_for_user` / ask_user）、工具审批（含后台任务转上来的）、浏览器登录接管、面板授权都进这个条。
- 回答一律用主输入框或选项按钮；`GoalReplyCard`、`AskUserMessageView` 里各自的输入框删除。
- 消息流里每个问题只留一条紧凑记录，回答后折叠；`goal_progress` 的"还差：等待你的回复…"不再重复问题原文。
- 可分两步：先删重复和多余输入框（小改），再做统一的条（需要 UI 设计）。

**W3-b 提问分级**

| 级别 | 什么事                                       | 怎么办                                                          |
| ---- | -------------------------------------------- | --------------------------------------------------------------- |
| L0   | 可逆的工程决定（怎么拆 PR、先做哪个）        | 不问，自己定                                                    |
| L1   | 有合理默认的偏好（"发版本"指 rc 还是正式版） | 说明默认做法后直接继续，最后总结里列出"我按 X 做了，要改告诉我" |
| L2   | 不可逆 / 对外 / 生产写入 / 新增凭据 / 花钱   | 必须问，并且只有明确同意才算数；含糊的回复（"研究下"）不算同意  |

- `wait_for_user` 改成结构化：短问题、可选项、默认项、级别。L2 的条上渲染"同意 / 不同意"按钮。
- 宿主限流：同一轮只允许一次；已问未答的不许再问；工具说明和 Goal 提示词里删掉"在回复里再问一遍"。
- 现在的提示词 `external-runtime-goals.ts:510` 把"发布等对外动作"一律定为必须停，改成只针对 L2，并把 L1 的"说明默认后继续"写进去。

**W3-c 后台任务的权限跟父会话走**

- DriveAgent 启动子进程时接上 `--permission-prompt-tool`（主运行时已在用，`runtime.ts:243`），子任务的审批请求转到父会话的"需要你"条，标明来自哪个后台任务。
- 默认权限继承父会话：父会话是完全放行，子任务也是；否则走审批。不再出现"说明写默认放行、实际默认最严"的情况。

### W4 状态说实话（解决 R4）

- **任务结果**：解析 `permission_denials`；有拒绝就不是"完成"，而是"完成但有 N 个操作被拒"，通知和任务视图都这么写。
- **工具结果**：见 W2-c，跳转结果带加载状态。
- **工具说明**：`drive-agent.ts:152` 和 `:1256` 的默认值说明改成和代码一致，并写明各模式下 Bash 会不会被拦。
- **提示词**：关于"线上/服务器/远端当前是什么状态"的结论，要么先查，要么明确标注"依据文档推断，未核实"。

## 6. 验收

把这次会话当回归脚本重放一遍，逐条核对：

1. 用户先在面板里登录某站点，外部会话请求授权后能直接驱动那个标签页，不用重登。
2. 派一个需要跑测试和 git 的后台任务：能看到标题和进度；需要审批时父会话的条上出现请求；被拒时任务显示"被拦"。
3. 后台任务运行期间，代理继续做不依赖它的前台工作；确实无事可做才显示"等待后台任务《标题》"。
4. 整个过程中任意时刻界面上最多一个待回答项、一个输入框；同一个问题只出现一次。
5. 代理要往生产环境写东西时停下来等明确同意；用户回复含糊时不执行。
6. 跳转到慢页面后不出现"白屏就收工"。

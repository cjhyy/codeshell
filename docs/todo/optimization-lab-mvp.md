关联：[优化 Agent 总体设计](agent-optimization-agent.md)、[通用评测契约](agent-evals-platforms-and-adapters.md)、[现有评测说明](../../evals/harness/README.md)、[AgentModule 组装设计](agent-module-resolved-composition-design.md)。本文收敛总体设计的首期范围；首期范围冲突时以本文为准。

## 1. 决策摘要

面向一个人先用、使用记录较少的情况，建设本地优先的 **Optimization Lab**，作为 CodeShell 内置能力包实现（见 §5.1），不是独立 Panel。用户选择记录、确认评测样本、授权实验预算，系统生成有限候选并提供效果与差异报告，用户另行决定是否采用。

第一条闭环固定为：**一个项目、一类任务、一个目标模型、一个纯文本 Skill、最多两个候选、人工采纳**。

- 不以用户数量或大规模日志为前提。少量真实案例配合人工确认的合成样本即可做探索实验；不承诺由此证明普遍提升。
- 不依赖 Langfuse 部署、不新增服务集群、消息队列、向量库或训练系统。已有 Langfuse 可作为后续证据来源和报告导出后端，不成为执行控制器。
- 先使用一次反思生成候选的简单策略，不引入 GEPA、Opik、自动路由或强化学习。
- 支持付费模型 API，但授权、数据范围、总投入和不确定用量可见；默认不开启后台扫描、定期执行或自动追加预算。
- 实验授权和正式采用是两个独立决定。候选不写入当前生效的 Skill、Memory、dream 或系统提示词。
- 先交付“可实验、可审查、可导出”；随后交付“普通新任务按范围采用、可回滚”。前一阶段不能宣传为日常 Agent 已自动进化。
- 先证明方法有用，再建界面：P1a 只接入 Desktop，只配一个最小授权页，产出一份文件报告；Core 只新增三项导出（§5.2），不做完整界面。P1a 的真实报告值得反复查看时再做 P1b 界面。

自用的成功标准：能从自己反复遇到的问题出发，用一次明确授权的实验得到一份可信的改动提案，并能决定是否使用。找到“没有值得采用的改动”也属于正常结果。

## 2. 当前代码事实与缺口

以下结论来自本地源码核查，不代表已发布版本均具备这些能力。表中 `core/`、`desktop/` 分别指仓库内的 `packages/core/`、`packages/desktop/`。

| 当前能力                                                                                   | 可以复用                                                                                                      | 不能据此声称已经具备                                                                                  |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `desktop/src/main/run-history-service.ts`、`runs-service.ts`、`renderer/runs/RunsView.tsx` | 运行索引、用户输入、回执、有限事件和用量展示                                                                  | 最终模型请求、完整轨迹、历史模型配置和环境可重放                                                      |
| `evals/harness`                                                                            | 硬断言与语义判分分离、证据清单、隔离环境、不可覆盖实验输出、请求级记录                                        | 任意任务/Skill 的通用评测器；现有 15 个案例不是 15 项真实模型通过结果                                 |
| `evals/harness/provider-proxy.mjs`                                                         | 请求次数预占、单次输出上限、中止和未知 usage 语义                                                             | 累计输入与输出 Token 硬上限、精确账单封顶、多角色统一持久预算                                         |
| `core/src/composition`（AgentModule）与 `core/extension`                                   | 工具、behavior profile、隐藏 session kind、protocol queries 与 observer；`createLLMClient`、`SettingsManager` | 能力包读取 Skill 管理或跨进程锁（二者只在 `/internal`）、自行创建隔离会话、拦截 Engine 发出的模型请求 |
| `core/src/skills/management.ts`                                                            | revision、冲突检查、原子编辑                                                                                  | 实验版本历史、永久回滚副本、按模型启用                                                                |
| `core/src/session/memory.ts` 与现有 Memory/Dream                                           | 现有记忆机制继续使用                                                                                          | 通用优化候选池；dream 会注入正常上下文，不能暂存未接受候选                                            |

关键限制：当前历史 `prompt` 是用户消息，最多 64 KiB；事件最多 200 条，读取 transcript 尾部最多 16 MiB；模型与 provider 来自会话当前 state。`sanitizeRunTraceValue` 是限长/限深度，不是完整脱敏器。因此旧记录默认只能作为问题来源，不能冒充冻结原版的执行证据。

另有两个真实缺口：

1. `runs:list/get` 是 Desktop main 私有 IPC，能力包所在的 agent server 进程读不到。P1b 由 Desktop main 按用户选定的 run IDs 生成证据包再交给模块，不给模块全盘会话读取权；P1a 用手工整理的样本绕开。
2. 能力包的 query handler 只拿到参数，`ProtocolObserverHost` 不能创建会话或 Engine；hook 事件中也没有“模型请求前”，Engine 自行发出的请求无法入账。现有 Skill 工具读取 scanner 当前内容；“按模型启用、运行中固定版本”需要新能力，不能靠增加一个版本表实现。

## 3. 首期范围

### 3.1 纳入

- Desktop、本机单用户、可信项目、手动选择记录或手动建样本。
- 一个明确选中的文本模型连接；第一版要求可用的请求适配、输出限制和用量记录。
- 一个无脚本、无额外参考文件、无外部服务依赖的 Skill 正文；保留名称、描述、工具权限及其他元数据。
- 文本输入输出及合成的只读资料；工具只提供受控的资料读取，不开放 Shell、浏览器、MCP、网络写入或真实文件修改。
- 原版重新运行、有限候选生成、开发集筛选、独立保留集验收、逐样本报告。
- 每次实验一个 worker、模型请求并发为 1；实验独立记账、独立限额，但供应商账户余额与速率限制仍与普通会话共享。实验预算不覆盖用户其他调用。
- 手工审核，采用、拒绝、导出和回滚均留记录。

### 3.2 后置

多用户、共享 Skill 市场、自动定期优化、多目标模型批量搜索、跨项目推广、Memory 自动采用、代码/工具 schema 修改、真实外部写操作、复杂工具链和整套上下文策略优化。

长期事实和用户偏好归 Memory；重复流程归 Skill；模型专属措辞归模型适配版本；模型选型归路由实验。首期只实现 Skill 正文这一种产物，不把所有经验塞进同一种存储。

## 4. 用户流程与页面

| 阶段   | 用户操作                                     | 系统行为与输出                                                                       |
| ------ | -------------------------------------------- | ------------------------------------------------------------------------------------ |
| 选材料 | 运行记录中选“导出为优化材料”，或手动建样本   | 预览输入、附件、纠正与缺失字段；脱敏后生成 evidence bundle                           |
| 定题目 | 确认任务目标、输入、验收条件                 | 去重、划分开发/保留集、保存不可变数据集版本；此时不调用模型                          |
| 批预算 | 查看模型、数据范围、可改内容、预计消耗及上限 | 冻结实验计划，生成授权单；点击后才能发起付费请求                                     |
| 跑实验 | 看进度或停止；需要时回填评分并确认继续       | 原版、候选生成、开发筛选、最终验收；必要开发评分缺失则等待；展示已用、预留、未知用量 |
| 看提案 | 查看“改动 / 效果 / 成本”                     | 逐样本胜负和回归、正文 diff、原因与来源、证据不足项                                  |
| 作决定 | 接受、拒绝、导出、修改后重测                 | 绑定具体候选与作用域；接受不自动启动下一轮优化                                       |

首次使用默认推荐手工整理 6–12 个独立案例，数量是产品引导值而非统计有效性保证。建议至少有开发集和保留集，覆盖原本成功的任务；不足时允许生成探索报告，但不显示“已验证可采用”。

关闭实验页面后实验继续；agent server 或应用退出即中断（见 §5.1 生命周期限制）。重新打开读取持久结果，不默默重新花费 Token。

## 5. 模块归属与接入方式

### 5.1 内置能力包，而不是独立 Panel

优化实验室是 CodeShell 内置能力，以能力包 `packages/optimization-lab` 实现（包名沿用 `@cjhyy/code-shell-capability-*`），导出 `createOptimizationLabModule(): AgentModule`，与 `coding`、`pet` 同层，只 import `@cjhyy/code-shell-core/extension`。

`CODESHELL.md` 的 Panel feature ownership 约束的是 Panel 功能；本功能不做成 Panel 的理由是系统边界：它要读取运行历史和 Skill revision，P2 还要介入会话构造、模型请求入口和子任务作用域。做成 Panel 时，这些都要先给 Host 开专门接口才能跨越边界；内置后运行记录和 Skill 由 CodeShell 自己访问，只需把少数能力导出到 `/extension`（§5.2）。代价是业务逻辑变更随 CodeShell 发版。

吸取 Arena 维护成本的教训（移除工作另在任务分支；本次集成基线的宿主仍加载 Arena，不能把未合入改动当作主线事实）：

- 模块由新增 feature flag 控制，默认关闭；关闭时不注册到组装根，界面无入口，不创建工作目录。
- 包标记为 private，不进入 npm 发布流水线；Desktop 打包脚本与 package boundaries 测试同步登记。
- P1a 只接入 Desktop 组装根（`desktop/src/main/agent-bridge.ts` 的模块列表与 `expectedModules`），TUI 和 server 暂不接入。
- P1a 报告未证明价值时，移除组装根注册即可整体下线，不留用户可见入口。

| 位置                        | 内容                                                                                                  |
| --------------------------- | ----------------------------------------------------------------------------------------------------- |
| `packages/optimization-lab` | 契约 schemas、控制器、账本、runner、优化策略、判分、报告；protocol queries 与进度 observer            |
| Desktop main                | 把界面请求转发给 agent server 中的模块 queries；P1b 起从自身 `runs:list/get` 生成用户选定记录的证据包 |
| Desktop renderer            | P1a 最小授权页；P1b 样本、进度与报告视图                                                              |
| Core `/extension`           | 只新增经核实缺失的通用导出，见 §5.2                                                                   |

| 模块（拟建）            | 职责                                           |
| ----------------------- | ---------------------------------------------- |
| `EvidenceImporter`      | 验证导入包、脱敏预览、来源与完整性标记         |
| `DatasetBuilder`        | 人工确认样本、去重、分组切分、生成冻结版本     |
| `ExperimentController`  | 唯一调度者，执行状态机、调用预算、冻结验收对象 |
| `BudgetLedger`          | 持久化预留、结算、未知额度、停止与恢复         |
| `TaskRunner` / `Grader` | 运行文本/受限工具任务，生成结果与确定性断言    |
| `OptimizerStrategy`     | 只根据允许的开发反馈生成候选，不决定通过或上线 |
| `ReportBuilder`         | 配对比较、改动解释、成本与证据覆盖率           |
| `CandidateStore`        | 候选内容、父版本、采用证据；不直接改正式配置   |

这些是同一个本地程序中的逻辑职责，不要求各建服务、进程或抽象框架；首期可用少量模块和函数实现。

P1a 只实现最小切片：`DatasetBuilder` 仅校验并冻结手写 JSON 样本（不做导入界面和去重建议），`EvidenceImporter` 推迟到 P1b，`ReportBuilder` 输出 JSON 与 Markdown 文件，`CandidateStore` 只保存候选正文、父 hash 和 manifest。人工判分仅提供按阶段导出评分 JSON、回填校验和确认继续，不等待 P1b 的完整编辑界面。`ExperimentController`、`BudgetLedger`、`TaskRunner` / `Grader`、`OptimizerStrategy` 在 P1a 就须完整实现：它们承载花费与证据语义，事后补救代价最高。

控制器运行在加载该模块的 agent server 进程内，通过 `protocol.queries` 暴露 `optimizationLab.*` 操作（计划校验、授权、开始/停止/继续、导出/导入评分、读取报告），进度由界面轮询状态 query 获得：Desktop preload 会丢弃未登记的 worker 通知，P1a 不为此新增通知通道。worker 只在 `agent/run` 时按需启动，其他请求在 worker 不在线时会被丢弃，所以 Desktop main 须先确保 worker 在线，再转发 queries。P1a 的模型调用由模块用 `/extension` 已有的 `createLLMClient` 与 `SettingsManager` 按用户选中的连接发起，全部经过 `BudgetLedger`；凭据只在 agent server 进程内使用，不写进 Prompt、报告或数据文件。首期模型无 Shell/任意代码工具。

生命周期限制：AgentModule Phase C 尚未完成，模块没有自有 lifetime 与 disposer，agent server 关闭即中断实验。P1a 接受这一点：中断按 §8.3 进入 `interrupted`，重启后由用户确认恢复；不为本功能提前另造一套 lifetime。

### 5.2 Core 需补的能力

P1a 的三项导出已由计划 A 实施（只读快照、共享文件锁、文本连接解析）；P2 项仍是拟议能力，不是已存在的 API 承诺。下表保留原缺口与约束：

| 阶段 | 能力                    | 已核实的缺口                                                                                                          | 边界                                                                                                                                                                                             |
| ---- | ----------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P1a  | 只读 Skill 快照导出     | Skill 管理只在 `core/internal/skills`，能力包只能 import `/extension`                                                 | 按 Skill ID 返回正文、元数据、revision 与 hash；只读，不含编辑、安装或扫描目录写入                                                                                                               |
| P1a  | 跨进程文件锁导出        | `acquireLockOnPath` / `mutateJsonFile` 只在 `/internal`；Desktop、TUI、server 可能各起 agent server，账本须跨进程单写 | 原样复用现有实现，不另写锁。该锁是同步的（`Atomics.wait`，默认最多等 30 秒，10 秒未释放视为过期），只能用于短临界区；实验单写者用租约记录（owner、心跳时间）实现，每次写账本时短暂加锁并校验租约 |
| P1a  | 文本连接解析导出        | query handler 只拿到参数，拿不到 Engine 的 `modelPool`；`resolveLLMConfigForTag` 只在根入口                           | 原样导出现有解析函数；该函数允许回退，B 必须先按选中连接过滤 settings，缺失时拒绝而非换用默认连接。凭据不离开 agent server 进程                                                                  |
| P2   | 模型请求准入            | hook 事件没有“模型请求前”，试跑会话中 Engine 自行发出的请求无法入账                                                   | 请求发出前同步预留、失败即拒绝，完成后回调结算；只做准入，不内置预算策略                                                                                                                         |
| P2   | 隔离试跑会话            | query handler 只拿到参数，`ProtocolObserverHost` 不能创建会话或 Engine                                                | 以隐藏 session kind 启动，装载指定指令快照与 behavior profile，关闭 Memory/dream/hooks                                                                                                           |
| P2   | 指令快照与 binding 解析 | 现有 Skill 工具读取 scanner 当前内容                                                                                  | 会话构造时解析 binding 并冻结；不接受任意路径写入或候选自行激活                                                                                                                                  |
| P2   | 模块 lifetime           | AgentModule Phase C 未完成                                                                                            | 按 Phase C 设计实现，不为本功能单独造一套                                                                                                                                                        |

Core 只提供通用导出、request admission、指令快照/解析契约；Optimization Lab 的角色、评分策略和 queries 全部留在能力包里。缺少 P2 能力时，界面只能报告或导出，不能显示“已用于普通任务”。项目代码类任务以后由 coding 能力提供环境适配，不写进通用 Engine。

### 5.3 先跑文本实验，再接真实运行路径

最早可用版本由模块内的文本 runner 直接运行冻结文本片段和合成只读资料，结果标记 `text_fragment`，不称为完整 Agent/Skill 工作流提升。

支持正式采用前，补上 `codeshell_isolated` 适配器：通过 §5.2 的隔离试跑会话启动任务，装载同一份 Skill 快照，所有实际请求经过模型请求准入进入统一预算入口。不得绕过现有 Engine 构造守卫，不临时安装候选到扫描目录。迁移后重新验证冻结候选；若根据隔离运行结果继续改写候选，已揭示的保留组降为开发数据，另建保留组。

该适配器保留 Skill 的真实加载语义。每次试跑记录是否实际加载目标 Skill、加载 hash 和结果；未加载不能归因为 Skill 改善，也不能简单删除这类失败来提高通过率。仅显式选用 Skill 的测试，其结论也限定为“选用该 Skill 的任务”。

## 6. 从记录形成评测包

### 6.1 证据导入

`EvidenceBundle` 包含 `schemaVersion`、来源 run/session/event IDs、输入与可选附件、工具事件引用、用户纠正、原始结果、完整性状态和脱敏记录。每个内容块有 hash、大小、是否截断；原始来源不可用时保留这个事实。

- 用户指定本次读取哪些记录，不遍历个人全部会话；模块只接收 Desktop 按用户选择生成的证据包，不自行扫描会话目录。
- 默认去掉凭据、认证头和已识别密钥；再提供人工预览。结构化过滤不能保证发现自由文本中的全部个人信息。
- “导入本地”不等于“允许发给模型”。授权单列明被测、优化、评分角色各自可收到的数据和连接。
- 原始聊天、网页、工具返回中的指令均为不可信数据；不据此更改权限、评测规则或预算。

### 6.2 样本内容

每个 `EvalCase` 至少保存：

| 字段                                 | 用途                                              |
| ------------------------------------ | ------------------------------------------------- |
| `id / version / sourceGroupId`       | 样本身份与同源分组，防止近重复跨集合              |
| `input / fixtureRefs`                | 实际发送的输入、合成附件或工具资料                |
| `expected / rubric / hardAssertions` | 用户确认的预期和可验证条件，注明来源              |
| `taskFamily / caseRole`              | 任务族；目标故障集或正常回归集                    |
| `split`                              | `dev` 或 `holdout`，候选生成前冻结                |
| `readiness / missingEvidence`        | `analysis_only` 或 `runnable`，缺失不能默认为通过 |

首期用两组即可，不单独建立第三套验证集。开发集用于生成和选择候选；保留集只在最终候选冻结后开启。案例太少时先补用户确认的合成案例，记录 `synthetic` 来源；同源变体仍只算一个独立来源组。

LLM 自动建议预期值属于可选付费步骤，也必须授权；它不能自己生成答案再凭一致性认定正确。仅整理原始记录、做格式检查和切分不产生模型调用。

历史输出不作基线分数。基线是本次冻结配置下重新执行的原版。固定历史工具回包属于 `recorded_response`；受控资料工具属于 `fixture_tool`；实际隔离执行另记，三者不混称真实外部工作流。

## 7. 优化与评测算法

首期策略名：`reflect_once_v1`。

1. 本地预检：数据、目标 Skill、模型可用性、权限、预算和数据外发范围；冻结计划。
2. 授权后执行原版开发集，确认问题与测量实际消耗。若必要语义条件尚待人工判分，保存检查点并进入 `awaiting_baseline_grading`；评分齐全并经用户确认继续后，才向优化模型提供开发反馈。
3. 向优化模型提供原版正文、目标、允许修改范围、开发集输入及反馈，生成最多两个候选。输出采用结构化完整正文和改动说明，不允许任意文件补丁。
4. 校验名称/描述/元数据未变，正文不超过授权的字节及上下文预算；拒绝修改工具权限、插入可执行脚本或引用未授权文件。静态检查只是第一道保护，不等同安全证明。
5. 候选逐一执行开发集。若必要语义条件尚待人工判分，保存检查点并进入 `awaiting_screening_grading`；评分齐全并经用户确认继续后，按预先冻结的排序规则选一个：硬约束优先，其次已验证任务数，再看成本；无法区分则不强行选优。必要评分缺失时不得用成本打破平局、冻结候选或开启保留集。
6. 冻结一个候选 hash，使用保留集对原版/候选配对执行。原版和候选交错顺序，每次重建相同 fixture，独立会话，不继承前一次回答、工具或应用状态。供应商 prompt cache 不一定可关闭/重置，其影响另行记录和评估。
7. 控制器生成报告与采用建议。最终语义评分未齐时先生成标为“待人工判分”的未验证报告；回填后仅本地生成新报告版本，不再次调用模型。优化模型没有采用接口，也不能修改评分器和保留集。

基线、候选保持相同模型连接与参数、工具 schema/权限、样本和评分器。记录请求模型、响应模型及不可获得的版本字段；provider 别名无法证明底层权重固定，必须保留复现限制。受测模型 fallback 默认禁用，发生意外切换则该配对无效。

首期优化模型默认沿用用户选中的连接以减少配置；其角色、调用和成本单独记录。语义 judge 默认关闭；开启时必须在授权前固定评分模型、模板和 rubric。同模型自评明确标为辅助判断，不能覆盖硬失败。

**开发集过拟合提示**：开发样本只有几个时，一次反思很容易把正文写成针对这几道题的特例。报告对候选相对原版新增的内容，列出同时出现在开发集输入或期望、但不出现在原版正文和任务目标中的专有名词、数字、文件名和长片段。比对使用确定性分词与 n-gram，不调用模型。它只是给人工审阅的提示，不参与通过判定，也不自动拒绝候选。`sourceGroupId` 只防近重复，不保证两组覆盖不同故障模式；建议保留集至少有一例使用开发集未出现的资料与实体。

首期不做自动多轮“直到变好”。保留集结果不回流给本轮优化器；下一轮若参考了已揭示的结果，该批案例应降为开发数据，另准备独立保留组。

## 8. 预算授权与计量

### 8.1 授权单

`BudgetGrant` 绑定不可变 `planHash`，至少包含：

- 项目、目标 artifact 与父 revision、数据集/评分器 hash、允许修改范围。
- 每个调用角色允许使用的 connection/model/config hash，以及允许外发的数据范围。
- 总 Token 估算限额、费用估算停止阈值、最大请求数、单次输出上限、候选数、时长、并发数。
- `enforcementMode`、计量/估算方法及价格来源与日期；不可得的价格不填零。
- 用户确认时间、授权 revision、剩余额度、撤销/过期状态、授权到期时间 `expiresAt`、开始操作的幂等键；首次开始时原子记录 `startedAt`。时长分为累计模型执行时间上限 `maxExecutionMs` 与绝对到期时间 `expiresAt` 两个口径，见下文。

首期计量模式为 `reserved_estimate`：有请求前预留，但不能对任意供应商承诺精确 Token 或账单硬封顶。UI 明确展示“估算限额 + 硬请求/输出/时长约束”。只有适配器能给出包括特殊/推理 Token 在内的保守上界时，才可以额外声明该维度的硬限额。首期不支持图像、音频等难以统一计量的输入。

推理模型单独说明：思考 Token 无法从输入推算，单次上界只能来自请求里的输出上限是否同时约束推理部分。适配器必须声明 `outputCapCoversReasoning`（`true` / `false` / `unknown`）。现有 `provider-proxy.mjs` 只改写 `max_tokens` / `max_completion_tokens`，这个上限是否包含推理由供应商语义决定，不能默认成立。授权页展示最坏情况 `最大请求数 × (输入上界 + 单次输出上限)`：声明为 `true` 时该值才是 Token 上界；`false` 或 `unknown` 时明确显示“Token 与费用无上界，仅请求数与时长受限”，不能用平均估算冒充上限。

一个授权覆盖本次计划内全部调用，不逐次弹窗；修改模型、数据范围、可改对象、评分器或增加预算均生成新的授权 revision。不存在默认自动续费。未授权的实验、样本提炼和模型评分均不得发出上游请求。

硬时长约束分两个口径。`maxExecutionMs` 是累计模型执行时间，与 Token 一样记账：每个操作发送前按自身截止窗口预留，结束后按实际耗时结算，崩溃或终态不明时整窗计为已用。人工等待期间没有在途操作，不消耗执行时间；执行时间由账本推算，重启与恢复不能清零。`expiresAt` 是绝对时间，包含人工判分等待，用于限制授权的陈旧程度（价格、模型别名漂移），到期后不得再发模型请求。授权页在开始前展示两者，`expiresAt` 默认应留出预计的人工判分时间。延长任一时限或增加额度，须由用户明确确认新的授权 revision，保留全部累计消费、执行时间、在途与未知预留，不能借续期重置账本。按冻结 rubric 回填 `GradingRecord` 只是新增结果，不改变 plan/scorer hash，也不触发重新授权；修改 rubric、expected 或评分模板才属于改规则。

### 8.2 调用前预留、调用后结算

所有模型角色走同一入口，包括基线、候选、优化、评分、辅助请求和失败重试。P1a 的入口挂在 HTTP 层：用 `createLLMClient` 的 `ClientDefaults.fetch` 注入计量 fetch，每一次真实 HTTP 请求（包括 SDK 内部可能的重试）都先预留、后发送；同时以 `retryMaxAttempts: 1` 关闭 CodeShell 客户端自身的重试。现有 `LLMResponse` 不含实际响应模型 id，`TokenUsage` 也没有推理 Token 字段：P1a 只用非流式请求，从响应体读取 `model`，读不到记为“不可得”，不拿配置的模型名顶替。首期关闭可关闭的自动 Memory、dream、hooks、摘要及隐式重试；确需发生的调用也必须入账，不允许直连绕过。

每次调用：

1. 检查授权、计划 hash、`expiresAt` 与剩余执行时间；按序列化有效输入估算 input 上界，加 output 上限及适配器安全余量。每个 trial 开始时固定 `trialDeadlineAt`，并从剩余 `maxExecutionMs` 中预留该窗口，预留不足则不启动；其请求截止时间取 `min(trialDeadlineAt, expiresAt)`。候选生成等非 trial 操作以预先冻结的操作 timeout 同样预留执行时间并确定截止时间。多轮请求不重置所属操作的时限，预留后发送前再次检查。
2. 在持久账本中原子预留请求名额及额度，写入 `attemptId`，成功后才发送。
3. 调用完成保存 provider usage、实际 model、错误和计量状态，按 attempt 结算。重复 usage 事件去重，不把 ModelFacade 与 provider 同一调用计费两次。
4. 缺失 usage 或取消后终态不明时保留对应预留为 `unknown`，不当成免费、不自动释放全部额度。超出预估立即停止新调用并显式报告估算失效。

界面分开显示“已报告用量 / 在途预留 / 未知预留 / 剩余可分配预算”。缓存 Token 按 provider 语义记录并避免与 input 重复求和；无法核定费用时只展示 Token 和费用未知/估算。

每个 trial 预先冻结 `maxTurns / maxRequests / maxOutputTokens / timeout`，含允许的工具轮次、辅助调用、可选评分和重试；默认不自动重试。无工具且每题重复一次时，任务试跑数为 `devCount × (1 + candidateCount) + holdoutCount × 2`，另外还有候选生成和评分请求。任务数不是模型请求数，授权页应分别展示。

控制器提前锁定最终原版+候选保留集所需的 Token/费用预留、请求名额与评分额度，按 trial 上限校验可行性；剩余执行时间不足以容纳最终阶段的 trial 窗口时停止搜索；这部分执行时间与 Token 预留一样提前锁定，不被搜索消耗，人工等待也不消耗它。用户点击“继续”时，还须确认距 `expiresAt` 的剩余时间足以完成最终阶段。候选正文变长后重新检查其上下文和最终预留是否足够。预算不足时降低尚未生成的候选数量、停止或返回证据不足，不临时减少保留样本却仍宣称达到原验收门槛。

### 8.3 停止和恢复

- 达到任一限制：不启动新请求。请求截止时间到达、授权过期/撤销或用户停止时，主动中止相应在途请求；总模型执行时限耗尽记为 `budget_exhausted`，保留超时原因与部分报告。在预先固定的收尾等待窗口内接收 receipt，未确认部分按 `unknown` 保留；收尾不再发模型请求。取消不保证供应商立即停止处理或计费，收尾时长单独记录。
- 账本先写再调用。崩溃后 `reserved/dispatched` 未结算项保持未知占用；不能当作从未调用。
- 重启后显示 `interrupted` 并保留原阶段检查点，用户确认才恢复；只运行尚未发起的步骤，剩余授权、`expiresAt`、执行时间与最终阶段预留仍需有效，恢复不重置执行时间账本。未知请求不透明重放；确需重试消耗新的名额。
- 等待人工评分时没有在途模型请求，也不后台发起付费调用。评分回填本身不自动恢复执行；等待不消耗执行时间，但 `expiresAt` 照常流逝。用户点击“继续”时重新检查授权、`expiresAt`、剩余执行时间、评分完整性和剩余预算。过期后仍允许本地回填评分和生成报告；若还需模型调用，必须先取得新的有效授权 revision。
- 同一 experiment 的跨进程单写者锁（§5.2，复用 CronStore 协议）加开始操作幂等键，防止双击、多窗口或多个 agent server 重复花费；锁获取非阻塞，不在同一进程内用同步等待阻塞异步持锁者。
- 连接只在 agent server 进程内使用，模型和子任务只接触受限调用入口；不将凭据写进 Prompt、报告或数据文件。

## 9. 数据模型与存储

首期用版本化 JSON、不可变 artifacts 和追加式账本，不引入数据库。小规模采用单写入进程；索引可从账本重建，成功事件持久化后才能推进下一步。JSON 临时写入加原子 rename，日志对截断尾行可检测恢复，不能把损坏账本当成零消耗。

| 对象               | 必要标识与关系                                                              |
| ------------------ | --------------------------------------------------------------------------- |
| `EvidenceBundle`   | 来源、字段完整性、脱敏版本、内容资源引用                                    |
| `DatasetVersion`   | case hashes、分组/split、人工确认信息、dataset hash                         |
| `ExperimentPlan`   | 目标、父 artifact、模型配置、数据集/评分器、允许修改范围、运行器版本        |
| `BudgetGrant`      | plan hash、额度、enforcement mode、用户授权 revision                        |
| `CandidateVersion` | parent hash、正文 hash、提出理由、来源证据、生成策略版本                    |
| `Trial`            | experiment/case/candidate/repeat、请求与工具 IDs、证据模式、加载 Skill hash |
| `CallLedgerEntry`  | attempt/role、预留与实际 usage、请求/响应模型、计量状态、时间               |
| `GradingRecord`    | trial/candidate/rubric hashes、人工或模型检查结果、证据、审核者和时间       |

工作目录位于 `codeShellHome()` 下按项目隔离的 `optimization-lab/<project-key>/`（示意如下），不硬编码用户 HOME，测试时随 `codeShellHome()` 指向隔离目录：

```text
optimization-lab/
  datasets/<dataset-hash>/manifest.json
  experiments/<id>/plan.json
  experiments/<id>/grants/<revision>.json
  experiments/<id>/ledger.jsonl
  experiments/<id>/candidates/<content-hash>/body.md
  experiments/<id>/candidates/<content-hash>/manifest.json
  experiments/<id>/trials/<trial-id>/manifest.json
  experiments/<id>/reports/<report-hash>.json
```

候选目录不在 Skill 扫描根，正文也不以 `SKILL.md` 命名，避免日后扫描规则或宽泛 glob 误装载；来源 Skill ID、revision 与元数据写在同目录 `manifest.json`。保留集与完整 expected 只由控制器掌握，不作为资源/路径提供给候选生成或任务模型；被测执行每次仅收到本题输入和允许的 fixture。

数据集、报告、候选、账本和采用依据都写入上述长期目录，不使用临时目录；恢复时验证 hash 和 sequence。普通任务需继续使用的已接受内容由 Core 的 binding 存储托管（P2），不引用实验目录。

默认不上传任何实验资料。首期不自动删除已接受版本及其回滚依据；清理其他实验通过预览和确认执行，提示派生数据与导出副本也可能保留原始信息。

## 10. 状态机与失败语义

实验状态：

```text
draft → ready → authorized → baselining
      → [awaiting_baseline_grading] → proposing → screening
      → [awaiting_screening_grading] → final_evaluating → report_ready
```

方括号表示仅在必要人工评分缺失时进入的等待状态；纯确定性断言等无需人工补分的阶段可直接推进。等待状态持久化检查点、当前阶段已完成 trial 与待评分项，只有有效回填且用户确认继续后才推进；不向评分模板提前暴露未执行的保留集。最终待人工评分由 `report_ready` 下报告的未验证状态表达，不保持模型任务运行。

每个执行或等待阶段可以进入 `budget_exhausted`、`cancelled`、`interrupted`、`failed`。这些状态也应生成可读的部分报告，不伪装成最终验收完成；本地补评分不会自动重开已停止的执行。

`budget_exhausted` 与 `interrupted` 保留原阶段检查点，可以恢复：前者需用户确认新的有效授权 revision，后者需用户确认且授权仍然有效；两者都回到原检查点，只运行尚未发起的步骤。`cancelled` 与 `failed` 是终态。等待状态中 `expiresAt` 到期不自动转移，只标记“授权已过期”，本地回填评分和生成报告照常可用；点击“继续”前须先取得新 revision。若 `final_evaluating` 跨越授权 revision 才完成，报告注明保留集跨 revision 执行，且续期决定是在已看到部分保留集结果之后做出的。

报告结论独立于生命周期：`improved`、`no_improvement`、`regressed`、`inconclusive`。采用决定再单独保存 `pending / accepted / rejected / rolled_back`，不因生成了候选就写 `improved`。

报告冻结后不可覆写。补测生成新 report hash；采用只能引用明确的一份报告和候选。用户修改任意正文或只接受部分 diff，得到新 hash，不能继承旧版“已验证”状态。

## 11. 如何判分与展示效果

判定枚举和“硬断言与语义独立”的规则直接沿用 `evals/harness/cases.json` 的 `verdictPolicy`（`hardFailureCannotBeOverriddenBySemanticScore`、`missingEvidenceVerdict: inconclusive`、含 `not_evaluated` 的 `semanticStatuses`）。以 schema 常量复制进能力包契约并注明来源 `suiteVersion`，不另定一套近义状态。

优先使用程序可验证条件，如输出 schema、必填字段、源资料数值一致、引用 ID 存在、工具返回对应真实 fixture。自由文本质量采用冻结 rubric 和人工复核；模型 judge 是辅助证据。

首期默认“可建议采用”门槛在授权前确认：

1. 关键安全/权限断言全部通过；必要证据齐全，最终验收完成。
2. **质量优先**：在开发反馈之外的保留任务上至少修复一个可验证失败；预先指定的回归集没有新增失败。
3. **降本优先**：与第 2 条二选一，冻结质量不退步条件与成本下降门槛，不要求额外修复失败；不能在结果出来后临时改主目标挑好看的指标。
4. 成本/延迟满足用户设定的约束；未知值不能按满足处理。

这是个人小样本的采用门槛，不是统计显著性保证。直说其含义：保留集只有 3–6 例时，非确定性模型上单个案例翻转就足以满足“修复一个失败”，因此这条门槛只是合理性过滤，不是改进证据。真正的依据是人工阅读改动及理由后，判断它能否推广到未见任务。单次配对得到的修复标注为“单次观测”；如需更强证据，在授权前把保留集重复次数设为 2 或以上，不在看到结果后临时补跑。样本不足、结果不稳定或只在开发集改善时，结论为探索性/证据不足。用户仍可导出候选或在实验室内主动试用，但必须看到未验证标记，不能伪造合格结论。

judge 关闭时，语义条件需人工填写 `GradingRecord`；未完成的项目保持 `not_evaluated`，报告显示“待人工判分”。结构断言通过不能代替语义正确。开发基线和候选筛选分别遵循 §7 的等待检查点，不能把必要开发评分推迟到最终报告后再补。

P1a 导出仅含当前阶段已完成 trial 的评分 JSON 模板，用户回填结果、证据与审核信息后导入。模板按随机顺序列出不透明的 `gradingItemId` 及本题输入、输出和冻结 rubric，不含 trial/candidate/parent hash、执行顺序或其他能区分原版与候选的字段；`gradingItemId` 到 experiment/trial/candidate/rubric hashes 的映射只由控制器保存。导入时控制器按该映射校验 hashes 和必要项完整性，拒绝错配、重复冲突或夹带规则修改；同一记录重复导入幂等。各阶段使用的评分记录 hash 随检查点冻结，后续更正不得静默改变已经使用的反馈或候选选择。模板导出、导入和报告重算均不调用模型；模型续跑另由“继续”操作触发并重查 §8 约束。

人工补评分生成新报告版本，必要评分未完成前不显示“通过本组验收”。已在有效授权与时限内完成的试跑，不因之后才本地判分而失效；因超时未执行完的必要试跑也不能靠补评分变成完成。P1a 模板默认隐藏原版/候选身份以减少预期偏差；输出内容本身仍可能透露差异，这一点无法通过模板消除。

成本指标在授权前固定，分开报告总 input/output Token、缓存命中、已回报费用和按同一价格表归一化的估算。不能把冷基线与热候选的费用差直接用作降本通过依据；缓存条件不可比时按缓存状态分层，或将费用收益标为不确定。推理 Token 与可见输出 Token 不混作同一个测量口径。

报告按以下顺序展示。改动放在最前，因为在小样本下它是主要判断材料，计数是辅助：

- 改动：完整正文 diff，每条改动关联假设、来源案例及验证结果，附开发集过拟合提示；模型生成的原因说明标为解释，不当作因果证明。
- 效果：原版/候选逐案例结果、改善/退步/不变/未知数量；故障集与正常集分别汇总。
- 分母：独立任务组数、重复次数、已判定通过率、全部计划样本的验证成功占比；失败、跳过和未知均可展开。
- 成本：原版/候选运行用量与时长，以及一次性生成、评分、重试的优化投入；费用估算与已回报值分开。
- 限制：`text_fragment / codeshell_isolated`、未加载 Skill、模型别名、环境限制、样本选择偏差和缺失证据。

少量样本优先显示原始数量与成对差异，不用伪精确 p95 或置信区间包装结果。后续增加区间估计时按独立任务组计算，重复调用不是新的独立案例。

## 12. 采用、运行版本固定与回滚

### 12.1 阶段一：实验室内试用与导出（P1a 仅导出，实验室内试用属 P1b）

用户可接受为“实验室首选版本”，后续实验室内明确指定模型的任务装载这个不可变文本版本；也可导出供人工阅读。此阶段不改用户原 Skill，不影响普通对话，不宣称跨模型生效。

### 12.2 阶段二：普通任务受控采用

需要 Core 的通用 instruction snapshot/resolver（§5.2）；不是直接覆盖 `SKILL.md`。

`AdoptionBinding` 最少包含：`projectId`、`agent/profile selector`、来源 Skill ID/revision、目标 model/config fingerprint、候选 artifact hash、report hash、binding revision 和启用状态。

- Desktop 确认界面展示最终正文 diff、作用域、验证级别；确认由 Desktop 原生对话框发起并绑定准确 hash，Core binding 入口不接受模块传来的“已经同意”布尔值。
- 正式 binding 必须关联有效的 `codeshell_isolated` 最终报告，候选 hash、父 revision、目标模型/config、数据集、评分器与加载证据一致，满足冻结门槛且所需人工评分已完成。Core binding 入口验证报告来源、运行回执与摘要关联；只有 `text_fragment` 报告或手填的验证标记不能通过此入口，UI 确认也不绕过证据门槛。
- 校验当前来源 Skill 与实验父 revision 一致、权限仍有效、项目仍受信任，随后原子更新 active binding，并持久化采用回执。冲突先提示，不能静默覆盖。
- 新会话解析 matching binding，冻结已接受内容及来源快照。模型、profile、项目或来源 revision 不匹配时使用正常来源版本，显示优化未适用；不将未测模型自动归入适用范围。
- 已有会话保留其版本，跨轮与 Skill 工具使用冻结快照，不能再次扫描时换成新正文。子任务重新匹配自己的模型/config、角色和作用域，只有匹配且显式传递时才继承；不匹配的子任务不得复制含该优化指令的父会话历史，应从获准输入和正常来源版本建立干净上下文。改变模型时新建/显式重置隔离会话，首期不保证在已含优化内容的旧上下文内安全“切回”。
- Skill 禁用、权限撤销、项目失信等安全规则仍即时优先。正文若已经进入上下文，仅停用 loader 不够：硬撤销阻止后续请求并中止相关在途执行，确认停止后要求从干净上下文继续；不能宣称抹去了供应商已收到的内容。供应商同名别名漂移只能记录，不能承诺自动识别所有权重变化。
- 采用后仍按 Skill 原有触发方式加载；不能把注册候选等同于每次自动执行。

Core 管理正式 binding 和内容，能力包管理实验业务与报告。两边通过 artifact/report hashes 和幂等 operation ID 关联；Core 的采用回执是生效事实。模块超时后先查询回执，不重复创建采用操作。

### 12.3 回滚

回滚生成新 binding revision 指向此前版本或禁用覆盖，原版本与报告保留。要求当前 binding revision 与用户确认时一致；期间发生用户修改则重新预览，不能覆盖新改动。回滚影响新会话，旧会话显示所用旧版本并允许用户主动新建。

首期同一作用域只支持一个修改目标 Skill 的有效 binding；若作用域重叠，必须替换明确的旧 binding 或拒绝。关闭 feature flag 或移除模块时默认禁用其 binding，Core 保留回执和回滚内容，并按前述硬撤销流程停止受影响的执行。普通用户回滚可以只影响新会话；安全撤销/移除模块不能继续携带旧正文运行，两者在 UI 和回执中区分。

### 授权后的自用验收

选作者真实重复遇到的一类问题，例如“从提供的资料整理报告，易遗漏来源”。人工建立少量合成资料与明确条件，记录原版失败；预算内生成并比较候选。

P1a 验收交付一份真实报告，哪怕结论是没有改进；不得预填演示提升值。P2 额外验证：接受后在新会话实际加载准确版本，拒绝不生效，回滚后新会话恢复原版，其他模型与项目不受影响。

真实主观收益由作者后续新任务补充评价；这些任务可作为下一批新样本，不反过来覆写旧实验报告。

## 15. 默认取舍与后续触发条件

- **记录不多**：人工选题/验收优先，不建自动聚类和大规模清洗管线。
- **业务形态变化快**：业务逻辑集中在能力包内，Core 只保留通用导出、请求准入和指令快照接口；未证明价值前以 feature flag 关闭且不发布包，下线只需移除注册。
- **只有部分 trace**：允许开始 P1，不承诺历史重放；未来再补请求级 prompt/tool/schema 与配置采集。
- **钱花了但没有改善**：保留原因、失败候选与实际投入，避免重复搜索；不自动扩预算。
- **需要跨模型**：建立各自基线、预算与报告，再新增明确 binding；不迁移一个模型的“已验证”标签。
- **需要 Memory**：另行设计事实来源、冲突、过期、人工 ownership 和隐私审核；不直接复用质量分数自动写入事实。
- **需要 Langfuse**：增加授权的 import/export adapter，保留其 trace IDs；本地仍是唯一调度和采用权威，避免双方各跑一轮。
- **需要更复杂优化**：只有简单策略在真实任务中产生价值后，再比较替换策略的收益与额外成本。

第一版的核心不是“无限自我进化”，而是一次用户看得懂、花费有边界、结果可检查、采用可撤回的优化实验。

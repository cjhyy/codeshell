# CodeShell harness 专项评测方案

状态：设计草案。本文没有新增评测运行器，也没有运行真实模型。

平台选型与通用接口见 [通用 Agent 评测层：平台调研与适配方案](agent-evals-platforms-and-adapters.md)。本文保留为 CodeShell 专项任务与证据规范；运行、评分和后端接入采用通用契约，批量实验优先复用现有平台能力。

## 目标

用可重复的任务衡量 CodeShell 如何组织上下文、暴露工具、执行操作和恢复会话。每次修改 harness 后，都能回答：任务是否更容易成功，失败发生在哪个环节，成功需要多少时间和 token。

第一批从真实问题改编为合成任务：多目录识别、跨目录操作、工具参数缺失、跨会话消息送达、新会话初始化。不直接重放原来的私人会话或外部写入操作。

## 仓库已有基础与缺口

| 现有能力                                              | 可以复用的部分                                    | 仍缺少什么                                                                        |
| ----------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------- |
| `evals/personal-sanitized/`                           | 从历史会话发现工具循环、失败率、耗时和 token 问题 | 导出不含任务和答案，不能据此判断回答正确；`completed` 也不是质量标签              |
| `packages/core/src/logging/session-recorder.ts`       | 开发/debug 模式的请求、响应和工具时间线           | 普通安装版不会默认启用；记录位于供应商转换之前                                    |
| `packages/core/src/engine/model-facade.ts`            | 统一模型调用边界，已有请求关联 ID 和脱敏消息记录  | 缺少与最终 SDK 请求一致的结构化证据                                               |
| `packages/core/src/prompt/composer.workspace.test.ts` | 证明 composer 会生成全部工作区根目录              | 不能证明最终请求保留它们，也不能证明模型会正确使用                                |
| `scripts/smoke-core-harness.mjs`                      | 使用真实 Engine、替代模型客户端进行离线检查       | 固定回复不能评测真实模型行为；新运行器采用独立子进程与隔离目录                    |
| `packages/core/src/run/Evaluator.ts`                  | 复用只读判分思想及结果格式                        | 当前接口只接收 run/checkpoint/artifacts；不是完整的任务集、对比和请求轨迹评测框架 |

已有 recorder 保存的是 `systemPrompt`、脱敏后的 messages、tools 等调用输入；它不等于供应商适配完成后的请求体，也不证明远端实际处理了哪一段内容。

## 两条评测通路

### 离线契约检查

使用合成目录、真实 Engine/协议链路和可控制的模型客户端。另用替代 SDK 或本地假服务捕获供应商适配后的请求。

检查目录是否传递完整、参数是否有效、消息是否发到正确会话、权限是否按实际目标执行、取消/重启后是否正确恢复。响应和故障时序由 fixture 控制，结果应当确定，不产生模型费用。

不得用假模型返回的标准答案计算“模型任务成功率”。假模型的用途是触发并验证 harness 状态变化。

### 真实模型行为评测

同一批合成任务分别运行 baseline 与 candidate harness。使用相同的模型版本、参数、工具集、初始文件、权限和预算，比较最终回答与真实文件/会话结果。

首次先做小样本试跑，例如每个用例每个版本 5 次；这只用于发现方向和不稳定性。正式结论应增加样本，并报告成功数/总数、配对差异与不确定性，不能把一次成功视为修复完成。

分开报告 native Engine 与外部运行时。不能把 native provider 的捕获覆盖率当成 DriveAgent 或外部 CLI 的覆盖率。

## 采集四个位置，让失败能归因

| 位置                       | 需要保留的证据                                                         | 能判定的问题                                       |
| -------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------- |
| 宿主生成工作区             | project revision、会话主根、全部 roots、实际 cwd                       | 项目已经挂载，但宿主遗漏副根                       |
| `ModelFacade` 调用前       | 上下文片段来源、顺序、长度、指纹，模型输入和工具 schema                | composer、压缩或工具选择阶段丢失信息               |
| 供应商适配完成、SDK 调用前 | 实际 request body 中的角色、内容块、工具参数、流式/非流式标记          | 适配器转换丢失、截断或改写信息                     |
| 工具执行与结束             | 模型原始参数、hook 改写后参数、实际 cwd/目标路径、结果、文件差异、终态 | 模型选错目标、参数验证失败、执行失败或错误宣称完成 |

请求使用 `evalRunId → caseId → sessionId → turnId → requestId → attemptId` 关联；工具调用和子会话通过各自 ID 接回同一轨迹。记录 retry、fallback、compaction，区分一次逻辑调用与多次实际请求。

工具结束后还要核对结果是否正确返回给模型：现有 executor 的 verbose 记录早于 post-tool hook 修改，部分拒绝路径会提前返回。应从 turn loop 接收到的最终结果继续关联到下一次 ModelFacade 请求中的 `tool_result`，覆盖拒绝、取消、压缩和结果外置后的摘要/引用。工具实际成功，但模型收到错误或缺失结果，也属于 harness 失败。

MVP 首先捕获适配完成的 SDK 参数。如果需要证明 HTTP 出站序列化也正确，再通过本地假服务断言收到的 body；两种证据在报告中明确标注。

多目录用例应分别输出：`host_roots_ok`、`model_input_roots_ok`、`provider_request_roots_ok`、`answer_roots_ok`。不能只读 state.json 的两个根，就把“已传给模型”判为通过。离线已知的 fixture 根应从实际内容中核验，不能给请求旁边附一份期望元数据就算通过。

### 记录策略

- 合成 eval 环境保留用于重现的上下文、请求体、响应、工具输入输出和最终产物；凭据与认证头不进入结果包。
- 日常诊断保留结构化摘要；完整内容捕获作为独立、显式的诊断模式，不把全量个人聊天默认写进 eval 数据集。
- 脱敏、截断或缺失必须有标记。证据不足时判为 `inconclusive`，不能视为通过。
- 现有 prompt-cache 诊断使用进程内随机 HMAC key，其指纹不能直接跨进程比较。合成 fixture 可使用规范化内容摘要；内容顺序必须保留，随机临时目录只在单独的语义比较视图中映射为稳定别名。

## 首批任务集

| 用例            | 输入或场景                                               | 判定依据                                               |
| --------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| 根目录清单      | “当前项目包含哪些目录？”；挂载 `app-main` 与 `panel-kit` | 列出两个挂载根及主副关系，不把主根内部文件夹冒充挂载根 |
| 子目录清单      | 同一 fixture，问“当前主目录下有哪些一级文件夹？”         | 按 fixture 返回实际子目录，区分前一题的意图            |
| 副目录读取      | 问仅存在于 `panel-kit` 中的随机标记                      | 答案正确，轨迹存在对副目录文件的成功读取               |
| 两根联合查找    | 两个根各放一个匹配项                                     | 结果完整且标明来源；不限定必须使用某个工具             |
| 同名文件编辑    | 两个根都有 `src/config.ts`，只要求改副目录中的值         | 指定文件差异符合要求，主目录文件完全一致               |
| 范围排除        | 工作区外的兄弟目录放同名诱饵                             | “当前项目”检索不把诱饵当成项目结果                     |
| worktree 与副根 | 主根切换到临时 worktree                                  | 主根操作发生在 worktree，副根路径仍正确                |
| 恢复与压缩      | 在恢复/受控压缩后再次询问挂载目录                        | 当前请求仍携带有效根信息，答案仍正确                   |
| 参数失败与修复  | 工具缺必填参数或 hook 改坏参数                           | 正确拒绝并可修正，执行记录与最终答复一致               |
| 跨会话送达      | 冷启动目标、排队、失败、取消分别注入                     | 消息归属与结果正确，接受/排队不等同于完成              |
| 新会话未落盘    | authority 查询先失败，随后 session_started               | 初始化不报告目录移除，启动后刷新恢复                   |
| 实际移除根      | 持久绑定对应根被移除                                     | 明确报告真实异常，不偷偷回退到别的根                   |

根目录名、子目录名、排列顺序与主副角色做固定种子的变体，至少包含中文路径和空格路径。开发集用于调优，保留集使用不同 fixture/措辞；同一来源问题的近似变体按组划分，避免把答案记忆误当能力提升。

## 第一个用例的具体规格

```text
caseId: workspace-root-inventory
workspace:
  primary:   <fixture>/app-main
  secondary: <fixture>/panel-kit
files:
  app-main/src/main.ts
  app-main/docs/readme.md
  panel-kit/src/widget.ts
user: 当前项目包含目录有哪些？
expected:
  挂载目录恰好为 app-main 与 panel-kit
  主目录为 app-main
  src、docs 不是独立挂载目录
  没有文件变更
```

保留自然语言提问和回答，以复现原来的产品体验。判分先从回答提取其宣称的挂载目录、角色及完整性，再与 fixture 比较；不能仅检查答案是否同时包含两个名字——“panel-kit 不属于项目”也包含名字，但结论错误。

目录、文件差异、参数、会话关联采用确定性判分。自然语言的否定关系或回答范围不清时，使用固定 rubric 辅助判分并人工抽查；有争议的样本保留原始证据，避免让另一个模型的一句总分成为唯一依据。

该题无需枚举文件即可回答。额外工具调用记为效率损失，通常不直接判失败；若声称已经读取文件或完成修改，则必须能由轨迹和产物证明。

## 优化实验与报告

先选择一个变量：例如在 runtime header 中说明“Workspace roots 是项目挂载目录；cwd 是默认执行位置；询问项目所含目录时按 roots 作答”。保持其他项相同后做配对评测，再决定是否采用。工具描述、工具数量、上下文顺序和压缩策略分别实验。

每次运行记录：

- 源码提交及未提交 diff 的摘要、实际构建摘要、依赖锁文件摘要；只记录提交号不足以识别当前工作区版本。
- fixture 版本/种子、评分规则版本、模型标识与参数、运行时类型、preset、有效工具 schema、插件与 hook 配置。
- 单例时间、轮数、token、重试和工具调用预算，缓存冷/热状态；不支持固定 seed 时明确记录。
- 成功率和失败类型、耗时分布、输入/输出/cache token、工具与失败重试次数。模型之外的摘要等辅助调用也纳入成本，避免低估整次任务。

优先判断正确性，再比较成功任务的效率；同时报告所有尝试的总消耗，避免快速失败造成“更省钱”的假象。超时、环境错误、provider 错误与答案错误分列，不能静默剔除失败样本。

离线契约检查作为硬门槛。真实模型评测先积累 baseline，再设定各任务类别的回归容忍度；跨目录错误写入、跨会话错误送达单独列为硬失败，不被其他任务的高分平均掉。

评分结果先作为离线报告产物。若复用现有 Evaluator 接口，需要适配 `warning` 与 `inconclusive`：当前 RunManager 会把非 passed 视为运行失败，不能直接把评测的不确定状态接进生产完成判定。

## 落地顺序

1. **第一阶段：打通多目录样例。** 三个任务：根清单、子目录清单、副目录读取；先做离线出站请求核验，再跑真实模型 baseline。
2. **第二阶段：形成对比闭环。** 增加语义/产物判分、baseline/candidate 配对报告，验证一次 runtime header 改动是否有效。
3. **第三阶段：扩展故障集。** 增加参数恢复、跨会话投递、会话初始化、恢复/压缩及 worktree 场景，并纳入持续回归。

建议新增的目录结构如下，均是计划中的路径：

```text
evals/harness/
  cases/             # 合成任务与版本化 rubric
  fixtures/          # 可重建的目录和会话初始状态
  capture/           # 输入、SDK 请求和工具轨迹的适配器
  graders/           # 目录、产物、关联关系与语义判分
  runner.ts          # 隔离执行、预算、重复采样
  compare.ts         # baseline 与 candidate 对比
```

运行产物写入单独的本地忽略目录，fixture 与 rubric 可提交。运行器通过独立进程的环境配置及临时工作目录隔离状态，禁用真实外部服务写入；需要外部行为的用例使用本地假服务。评测不应修改正在使用的 CodeShell 会话、飞书文档或 GitHub Star。

第一阶段完成的验收条件：对于同一个失败样例，报告可以区分“宿主漏根”“模型请求漏根”“请求正确但回答偏题”“副目录工具执行失败”，并附上能支持该归因的证据。

# 提示缓存整体方案：根因实测与修复顺序

- 日期：2026-11-12（第四版：补齐根因实测，按实测损失重排范围，并用 OpenRouter 探针验证了设计假设）
- 基线：`main` @ `006bee8c5`（行号以此为准，动手前先 `git diff` 核对；路径均在 `packages/core/src/` 下）
- 状态：方案草稿，未实现
- 关系：承接 `prompt-cache-append-only-tool-discovery-20261111.md`（工具表冻结，已落地）和 PR#316（双断点）。抽象模型和规则见 `prompt-cache-optimization.md` 第五节，本文是按那五条规则落地的具体方案
- 探针：`prompt-cache-probes-20261112/`（方案、脚本、原始结果）
- 数据来源：本机最近 9 天的工作会话（843 次相邻请求对）、`~/.code-shell/logs/engine-2026-11-12.log`、两个证据会话 `s-mwdbhosc-81450a86`（3 个 run，4 万 token）和 `s-mvhsr47g-4fadcfc5`（32 万 token）。全部是 `gpt-6.1-sol` 线路

## 1. 结论

缓存损失来自四个互相独立的原因，按实测损失排序：

| # | 原因 | 9 天内次数 | 丢失 token | 现状 |
|---|---|---|---|---|
| 1 | 每个新 run 拿走上一个 run 的动态上下文 | 133 次 run 首次请求，0 次完整命中 | 约 21M | 未修。其中间隔超过 30 分钟的 37 次（约 7.5M）是缓存过期，救不回来 |
| 2 | 新的浏览器快照到来时，回头折叠旧快照 | 34 次 | 约 5.6M | 未修，今天的构建上仍在发生 |
| 3 | `ToolSearch select:` 改写顶部工具表 | 33 次，读取全部归零 | 约 3.1M | 11-11 已修，今天的数据里没有再出现（样本只有 28 对） |
| 4 | 其他：图片换占位符 3 次、压缩 3 次（预期内）、未归类 5 次 | 11 次 | 约 0.9M | 图片未修 |

另有两项不破坏缓存、但直接多花钱：

| # | 问题 | 实测 |
|---|---|---|
| 5 | 插件的 hook 提醒每个 run 重新注入一份，旧的留在历史里 | 每个 run 多约 1.7–1.9k token 重复内容；只在内存里，进程重启后全部消失 |
| 6 | 辅助调用完全不命中缓存 | 证据会话里辅助调用 95k 未缓存 token，比主循环的未缓存部分（约 65k）还多 |

## 2. 根因

### 2.1 跨 run（原因 1）

- `engine/run-context.ts:151` 每个 run 把动态上下文（技能、能力、记忆、来源、Goal 工具状态，约 3.6k token）放在用户消息后面，登记为 volatile，不落盘。
- 下一个 run 从历史里拿掉它，再在新末尾放一份。PR#316 在它前面打了"稳定断点"，所以新 run 能读到上一个 run 那份动态上下文**之前**的部分，之后的全丢。
- 证据会话：#13 读到 12,692（run 1 动态块之前），#16 读到 33,345（run 2 动态块之前）。引擎日志的消息数能对上：run 1 结束 30 条，run 2 开始 32 条（减 1 条旧动态块，加唤醒消息、hook 提醒、新动态块）。
- **动态块每个 run 都在变**：记忆提取在每个 run 结束后都跑，证据会话的 3 个 run 分别新增 1 条、新增 1 条、更新 1 条记忆（日志 `memory.extraction_done`）。所以"内容没变就不重发"在整块粒度上永远不成立。记忆索引的每一行本身是稳定的（`session/memory.ts:861`，只有名称、描述、范围、置顶）。

### 2.2 浏览器快照折叠（原因 2）

- `context/compaction.ts:724-758` 的 `maskOldObservations` 只保留最新一份快照，其余换成一行占位符。它在每个模型步骤前无条件执行（`context/manager.ts:432`）。
- 每来一份新快照，上一份就被改写。改写点在动态块之前时，`engine/turn-loop.ts:636-671` 会把动态块挪到末尾，稳定断点随之失效。
- 该线路用显式断点（`llm/providers/openai.ts:1300-1345`：系统、稳定、上一次滚动），缓存读取只落在断点上。稳定断点和滚动断点同时失效后，只剩系统断点。
- 实测：`s-mvhsr47g` 今天两次快照后的请求都只读到 14,386（正好是头部），各丢约 31 万 token，而被折叠的旧快照只有几百到一千多 token。第一次折叠后动态块被挪到末尾，于是第二次折叠的改写点又在它之前。
- 结论：现在任何一次对旧消息的改写，代价都是整个上下文重新计费，与改写点的位置无关。

### 2.3 hook 提醒（问题 5）

`engine/engine.ts:2984-3038`：`on_session_start` 注释写的是"每次 `Engine.run()` 触发一次，不分冷启动和恢复"，加上每轮的 `user_prompt_submit`，两者的输出合成一条提醒插在最新用户消息之前。它不落盘，但留在进程内的消息数组里，所以每个 run 累加一份。

### 2.4 辅助调用（问题 6）

证据会话每个 run 结束后：记忆提取两次调用（约 14.9k + 7.2k），约 20 秒后另有一次 9–10k 的调用，外加一次标题。70 秒内 3 个 run 就做了 3 轮。全部是"系统提示一句 + 用户消息一整段"（`engine/auxiliary-pipeline.ts:209`），缓存读取为 0。那次 9–10k 调用的来源未识别。

## 3. 设计

一条规则，四处改动。不新增"周期对象""调度器"之类的组件，尽量复用现有机制。

> **规则**：摘要压缩之间，已经发给模型的内容不改、不挪、不删；新信息只在末尾追加。确实要回头改写旧消息时，攒到不花钱或者划算的时候一次做完。

### 3.1 上下文落盘、按条目追加变化（解决原因 1）

动态上下文从"每个 run 一份快照"改为"会话里的普通历史"：

- **拆段**：`prompt/composer.ts:241-287` 改为返回带 key 的段（技能、能力、记忆、来源、Goal 状态、运行时状态、MCP 失败摘要）。
- **首次全量**：摘要压缩之后的第一个 run 写一条全量快照事件进 transcript，投影为用户消息，位置不变。
- **之后只追加变化**：
  - 记忆和技能是带稳定 id 的列表，按条目追加"新增 / 更新 / 移除"。这是第一期必须做的，因为记忆每个 run 都在变。
  - 其余段整段替换，声明"替代此前同名段"。
  - 全部没变就不追加。
- **状态从 transcript 推出**：各段各条目"上次发过什么"由回放 transcript 得到，不另存，回滚和撤销轮次时自动一致。
- **正文不进 transcript**：事件里只存 key 和摘要，正文放会话目录下按摘要命名的旁路文件。这样导出、归档、手机同步默认不带记忆文本。
- **去掉 volatile 登记**：`engine/turn-loop.ts:618-672` 的搬动逻辑随之删除，2.2 里"改写后动态块挪到末尾"的放大效应一并消失。
- 系统提示加一句固定说明："后出现的上下文更新替代先前同名内容"。
- **内容表示不随断点变化**：所有文本内容统一以文本块数组发送。探针显示，在 Claude 线路上，一条用户消息从"带断点的数组"变回"字符串"会让缓存从这条消息开始失效；不做这一条，落盘在 Claude 线路上不起作用（探针 X2 为 45%，X2a 为 100%）。
- 兜底：累计更新超过全量的 2 倍时，触发一次重整（见 3.3 的时机）。

### 3.2 hook 提醒去重并落盘（解决问题 5）

- `on_session_start` 的输出每个会话只注入一次；恢复时若历史里已有相同内容则不再注入。
- `user_prompt_submit` 的输出与历史里上一条相同则不重复。
- 注入的提醒按 3.1 的方式落盘，进程重启后位置和内容不变。

### 3.3 回溯改写改为攒批（解决原因 2、4）

涉及三处：旧快照折叠（`context/manager.ts:432`）、重复 Read 去重（`:422`）、图片换占位符（`engine/turn-loop.ts:773`）。微压缩（`:438`）同理。

不再每步执行，改为登记待办，只在以下时机一次做完：

| 时机 | 说明 |
|---|---|
| 摘要压缩 | 缓存本来就要重建 |
| 缓存已冷 | 新 run 开始且距上一次成功请求超过缓存有效期（该线路配置为 30 分钟）。9 天里有 37 次这样的 run 首次请求，是免费的清理窗口 |
| 划算 | 待清理的 token 超过阈值时。阈值按"改写要重新计费的 token"与"每次请求省下的 token × 预计剩余请求数"比较；默认值等诊断数据定，初始建议待清理量 ≥ 上下文的 15% |

- 从磁盘恢复时本来就要重放历史，按"缓存已冷"处理，把待办一次清掉。
- 写入时就能决定的处理不受影响：大结果落盘换预览、硬截断、单条预算（`context/manager.ts:406-415`）保持原样。
- 敏感结果脱敏是安全要求，保持即时。

### 3.4 断点位置

断点不能阻止缓存断开，只决定断开后退回到哪里：缓存读取只落在系统段末尾、显式断点、上一次请求末尾这三种存档点上（探针 M5：改写点在 69% 处、唯一断点在 36% 处时，两条线路都只读到 36%–38%）。

落盘后不再有 volatile 消息，现在的"稳定断点"失去锚点。中间那个断点改放在**定型线**上：

- 定型线 = 最早一条将来还可能被改写的消息之前（还没折叠的旧快照、还没去重的 Read、还在窗口内的图片）。它之前的内容不会再变。
- 没有这类消息时，放在本 run 开始处。
- 定型线只在一次攒批改写完成后前移，两次攒批之间位置不变，所以断点处的存档一直有效。

这样下一次攒批改写无论动哪条，损失都限制在定型线之后。探针 M4 验证了机制（改写点之前有断点时，两条线路都读到断点处，约 70%）；"按最早待改写消息选位置"这一选法本身没有单独测。

### 3.5 诊断：扩展现有的 `cache_read_drop`

`engine/engine.ts:4380-4400` 已有诊断，但只跟踪系统提示、工具表、配置的哈希，所以这次的两类问题都被记成 `no_tracked_prefix_change`。扩展为：

- 记录与上一次请求相比**第一条不同的线上消息**的序号和类别（上下文更新、hook 提醒、工具结果改写及其来源、压缩）。
- 上一次请求的逐条哈希放会话目录的旁路文件，进程重启后仍可比较。只存哈希和序号。
- 测试模式下，未登记的旧消息变化直接断言失败。

### 3.6 头部

- 日期和指令文件（`prompt/composer.ts:165-187`）每个 run 重算。改为压缩之间冻结，变化时按 3.1 追加一条更新。9 天数据里没有分离出这一项造成的损失，优先级低。
- 模型切换不重建头部：头部内容与模型无关，主备模型来回切换不应反复重排。

## 4. 落地顺序

| 步骤 | 内容 | 解决 | 依据 |
|---|---|---|---|
| 0 | 扩展诊断（3.5 的记录部分），不改行为 | 之后每一步都能用数据验收 | — |
| 1 | 旧快照折叠等改为攒批（3.3） | 原因 2、4，约 5.7M | 改动小，今天仍在发生，单次损失最大（31 万 token） |
| 2 | 上下文落盘、按条目追加（3.1）+ 断点调整（3.4） | 原因 1，上限约 13.6M | 最大的一项，但改动面大 |
| 3 | hook 提醒去重落盘（3.2） | 问题 5 | 依赖步骤 2 的落盘机制 |
| 4 | 头部冻结（3.6）；诊断的测试断言默认开启 | 防回归 | — |
| 5 | 辅助调用（另开方案） | 问题 6 | 见第 8 节 |

旧会话没有快照事件：升级后第一个 run 出一次全量，损失与现在的单次跨 run 相同。读到不认识的事件不抛错、不清空历史。新逻辑放新文件，`turn-loop.ts` 和 `engine.ts` 已接近行数上限。

## 5. 验收

门槛是离线断言，真实端点只作佐证（OpenRouter 的承载方切换会带来噪音）。

1. **前缀断言（不联网）**：请求 N+1 的线上消息以请求 N 为前缀，除非诊断里登记了一次攒批改写。覆盖：跨 run、后台任务唤醒、从磁盘恢复、连续两次浏览器快照、重复 Read、看图、Goal 开关、安装或卸载技能、每个 run 后新增一条记忆、跨午夜。
2. **不重复**：连续 5 个 run、每个 run 后新增 1 条记忆，历史里追加的上下文总量不超过 5 条记忆行加固定开销；hook 提醒只出现一次。
3. **攒批生效**：32 万 token 上下文里连续两次快照，不发生改写；缓存已冷的新 run 开始时，待办一次清空。
4. **诊断**：人为制造上述每类变化，`cache_read_drop` 都能给出正确的类别。
5. **真实端点佐证**：重放证据会话形态（长 run → 后台唤醒 → 短追问，间隔 30 分钟内），新 run 首次请求的缓存读取 ≥ 上一次 prompt 的 95%。
6. 发 PR 前跑全仓契约和预算测试。

## 6. 探针验证（2026-11-12）

经 OpenRouter 在 `gpt-6.1-sol` 和 `claude-sonnet-5` 上各跑两遍，结果一致。数字是被测请求的缓存读取量占上一次 prompt 的比例。

| 设计点 | 现状 | 改后 | 线路 |
|---|---|---|---|
| 跨 run：旧动态块留原位、只追加变化（3.1） | 43%–45% | 100% | GPT 直接成立；Claude 需要内容统一用数组形式 |
| run 内：旧快照不折叠（3.3） | 36%–37% | 100% | 两条线路 |
| run 开始处断点（3.4） | 36%–38% | 约 70% | 两条线路 |

另外确认了两件事：单是折叠旧快照就足以让缓存退到系统段，与动态块是否被挪动无关；缓存读取只落在系统段末尾、显式断点、或上一次请求的完整前缀上，不是最长公共前缀。

探针的上下文只有 1–1.6 万 token，间隔固定 8 秒，没有覆盖 30 万 token 量级和缓存有效期边界。

## 7. 风险与待定

- **旧内容与更新并存**：模型可能引用旧条目。靠固定说明句和更新里的"替代"措辞约束；已卸载的技能被调用时由执行器拒绝。
- **攒批期间上下文偏大**：旧快照多留一段时间。"划算"阈值要低于触发摘要压缩的阈值，否则会把便宜的清理拖成昂贵的压缩。浏览器密集的任务需要单独看数据。
- **系统提示加一句说明**：所有会话一次性冷启动。
- **待定**：记忆正文放旁路文件后，归档和会话迁移是否要带上这些文件。

## 8. 范围之外：辅助调用

单独立项，方向有三个，按代价从低到高：

1. 记忆提取不在每个 run 后都跑，改为会话空闲或收尾时跑一次。证据会话 70 秒内跑了 3 轮，共约 66k token。
2. 辅助调用的提示把固定指令放前面、变化内容放后面，让固定部分能命中缓存。
3. 需要整段历史的辅助调用复用主会话前缀（相同工具表、系统提示和历史，只在末尾追加指令）。

先要识别那次 9–10k 调用是什么。

## 9. 未核对

- 第 1、2 节的损失统计全部来自 `gpt-6.1-sol` 的真实会话。Claude 线路只有探针数据，没有真实会话数据；它的缓存有效期更短，跨 run 能救回的比例会更低。
- Claude 线路上"断点有无会改变前缀"的原因是推测（相邻用户消息被合并），没有单独验证；直连 Anthropic 是否同样如此没有测。
- hook 提醒具体来自哪个插件、5 次未归类的 run 内断点、调用技能后系统提示是否变化（`engine/engine.ts:2347-2352`）、子代理请求的前缀，都没有查。
- 今天构建上的 run 内样本只有 28 对，"工具表冻结后 `ToolSearch` 不再破坏缓存"需要更多数据确认。

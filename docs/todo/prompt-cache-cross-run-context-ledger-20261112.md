# 提示缓存整体方案：根因实测与修复

- 日期：2026-11-12 立项，2026-11-16 更新为实现后的状态
- 状态：**已实现**（分支 `claude/core/prompt-cache-ledger-20261112`，经 PR 合并；基线 `main` @ `006bee8c5`）
- 关系：承接 `prompt-cache-append-only-tool-discovery-20261111.md`（工具表冻结）和 PR#316（双断点）。抽象模型和五条规则见 `prompt-cache-optimization.md` 第五节，本文是按那五条规则落地的方案与结果
- 探针：`prompt-cache-probes-20261112/`（方案、脚本、按比例整理的结果）
- 路径均在 `packages/core/src/` 下，另有注明的除外

## 1. 立项时的实测结论

数据来自立项前一段时间本机工作会话的相邻请求对和引擎日志，全部是 `gpt-6.1-sol` 线路。下面只给比例。

缓存损失来自四个互相独立的原因：

| # | 原因 | 占全部可归因损失 | 说明 |
|---|---|---|---|
| 1 | 每个新 run 拿走上一个 run 的动态上下文 | 约 69% | run 首次请求从未完整命中过。其中约三分之一来自间隔超过缓存有效期的 run，本来就救不回来 |
| 2 | 新的浏览器快照到来时，回头折叠旧快照 | 约 18% | 单次折叠就让整段上下文重新计费，而被折叠的旧快照只占其中很小一部分 |
| 3 | `ToolSearch select:` 改写顶部工具表 | 约 10% | 立项前一天已修（工具表冻结） |
| 4 | 其他：图片换占位符、压缩（预期内）、未归类 | 约 3% | |

另有两项不破坏缓存、但直接多花钱：

| # | 问题 | 实测 |
|---|---|---|
| 5 | 插件的 hook 提醒每个 run 重新注入一份，旧的留在历史里 | 每个 run 多一整份重复提醒；只在内存里，进程重启后全部消失，重启后的第一次请求因此对不上 |
| 6 | 辅助调用完全不命中缓存 | 证据会话里辅助调用的未缓存部分约为主循环未缓存部分的 1.5 倍 |

## 2. 根因

### 2.1 跨 run（原因 1）

- 每个 run 把动态上下文（技能、能力、记忆、来源、Goal 工具状态）放在用户消息后面，登记为 volatile，不落盘。
- 下一个 run 从历史里拿掉它，再在新末尾放一份。PR#316 的"稳定断点"让新 run 能读到上一个 run 那份动态上下文**之前**的部分，之后的全丢。
- 动态块每个 run 都在变：记忆提取在每个 run 结束后都跑，几乎每个 run 都新增或更新记忆，所以"整块没变就不重发"永远不成立。记忆索引的每一行本身是稳定的。

### 2.2 浏览器快照折叠（原因 2）

- `maskOldObservations` 只保留最新一份快照，其余换成占位符，每个模型步骤前无条件执行。
- 每来一份新快照，上一份就被改写；改写点在动态块之前时，动态块还会被挪到末尾，稳定断点随之失效，只剩系统断点。
- 实测：折叠后的请求只读到头部（系统段加首条用户上下文），其余全部重新计费。

### 2.3 hook 提醒（问题 5）

`on_session_start` 每次 `Engine.run()` 都触发，加上每轮的 `user_prompt_submit`，两者的输出合成一条提醒插在最新用户消息之前。它不落盘，但留在进程内的消息数组里，所以每个 run 累加一份。

### 2.4 辅助调用（问题 6）

每个 run 结束后的记忆提取、会话摘要都是"系统提示一句 + 用户消息一整段"，缓存读取为 0。

## 3. 实现

> **规则**：摘要压缩之间，已经发给模型的内容不改、不挪、不删；新信息只在末尾追加。确实要回头改写旧消息时，攒到不花钱或者划算的时候一次做完。

### 3.1 上下文账本（原因 1）

- **分段**：`PromptComposer.buildDynamicContextSections()` 返回带 key 的段：技能、技能缺口、能力（各能力包可以有自己的段）、记忆、来源、Goal 工具状态；引擎再加 MCP 失败摘要和日期变更（`engine/run-context-ledger.ts`）。
- **首次全量、之后只追加变化**（`context/context-ledger.ts`）：
  - 技能按名称、记忆按条目比较，只追加"新增 / 替换 / 移除"。
  - 其余段整段替换（`<context-section>` 替代同名段，`<context-section-removed>` 撤回）。
  - 全部没变就不追加。
- **每次更新自带说明**：更新消息开头有一段固定说明，解释"后出现的同名段替代先前内容"。没有往系统提示里加句子，所以不会让所有会话冷启动一次。
- **状态从 transcript 推出**：快照和更新作为注入的用户消息事件写进本地 transcript（`data.contextLedger`，带序列化的账本状态），回放即得"上次告诉过模型什么"，回滚和撤销轮次时自动一致。
- **正文只在本机**：上下文正文就在本地 transcript 里，没有另开旁路文件。所有离开本机或导出的路径都把它拿掉（`session/context-messages.ts` 的 `isContextEvent` 一组函数）：协议和 Hub 的 `session_detail` 把这些事件换成不带正文的占位（保留 id、类型、时间，客户端按 id 定位的历史恢复锚点不受影响）；Hub 的 JSON / Markdown 导出、TUI 的 `/export`、手机的旧外部会话历史直接去掉。会话状态里的 `promptSubmitHookMessages` 同样不出本机。本地分叉和归档照常带着它们。
- **git 状态只进快照**：coding 包的 git 状态段是 `snapshot-only`，只在快照里出现一次，之后变化不重发（它几乎每个 run 都变）；状态最多列 40 行、提交最多 5 条，并注明是快照。
- **工作区变化即撤销**：账本记录所属工作区；换了工作区，旧工作区告诉过的上下文从历史和回放里撤销，再对新工作区重新发快照。
- **运行时上下文保留为 volatile**：行为档案声明为非持久的运行时上下文（Mimi 的世界状态）仍按 run 放、不落盘；在显式断点线路上它始终放在请求末尾，下个 run 拿走它不损失任何已缓存历史。
- **内容表示不随断点变化**：显式断点线路上所有文本内容统一以文本块数组发送（Claude 线路上字符串与数组切换会让缓存从该消息断开，探针 X2 / X2a）。

### 3.2 hook 提醒（问题 5）

- `on_session_start` 的输出与历史里仍在的最近一次相同就不再注入。
- `user_prompt_submit` 的输出只在"上一条提示也得到同样输出"时省略；会话状态 `promptSubmitHookMessages` 记录上一条提示的输出，所以进程重启后判断不变。
- 提醒作为注入消息落盘（`data.hookReminder`），放在它所属的用户消息之前，回放位置与在线时一致。
- run 内的提醒（`on_turn_start`、`post_compact`、停止 hook 的阻止原因、轮数与上下文预算警告、任务提醒）同样落盘（`engine/context-reminders.ts`），重启后回放的历史与发出去的一致。
- hook 改写了提示时，改写结果存为 `prompt_rewrite` 事件；模型回放用改写后的内容，界面仍显示用户原文。

### 3.3 回溯改写攒批（原因 2、4）

快照折叠、重复 Read 去重、微压缩和图片换占位符不再每步执行，而是先算出待改写的批次，只在下列时机一次做完（`context/rewrite-gate.ts`）：

| 时机 | 条件 |
|---|---|
| `cold` | 任何一步，距该会话上一次成功请求超过该线路的缓存有效期（OpenAI 显式与 hybrid 线路 30 分钟，其他线路 5 分钟）；或本进程还没为该会话发过请求（启动、从磁盘恢复） |
| `worth_it` | 待省下的量达到下限，且不低于未改写历史的 15% |
| `pressure` | 上下文已到首个压缩阈值，便宜的清理先做 |
| `hard_cap` | 图片数量或字节超过请求硬上限，必须立即做 |

写入时就能决定的处理（大结果落盘换预览、硬截断、单条预算）和敏感结果脱敏保持即时。线路从显式缓存降级到隐式后，引擎按进程记住该线路，有效期按降级后的线路算。

### 3.4 断点放在定型线上

`engine/stable-prefix.ts`：中间那个断点放在最后一条已定型的消息上——

- 有待做的改写批次时，放在批次最早要动的那条消息之前；
- 否则放在本 run 开始处；
- 运行时上下文在请求末尾时，放在它之前，但不越过待改写批次的位置（取两者较小值）。

### 3.5 头部

首条用户上下文里的日期冻结为会话开始日期；日期变了，账本追加一条"日期已变更"段，而不是改写头部。指令文件变化按登记的改写处理。

### 3.6 诊断与前缀守卫

- `cache_read_drop` 诊断在内存里保存每个会话上一次请求的逐条哈希，缓存读取下降时指出第一条变化的消息及其类别（进程重启后不保留）。
- 测试用的前缀守卫（`testing/prompt-prefix-guard.ts`）按测试套件显式开启：同一会话的每次请求必须以上一次为前缀，除非该会话登记过一次改写（攒批、压缩、归档、清除指令、指令头变化、工作区撤销、上下文超限恢复、截断续写）。改写按会话登记，不会替别的会话开脱；字符串回复与回放时的单个文本块只在线路确实发送相同字节时视为相同（`LLMClientBase.sendsLoneTextBlockAsString`）。生产代码只在装了守卫时才计算这些信息。

### 3.7 兼容降级

- 网关拒绝 GPT 显式缓存字段时，客户端降级为隐式缓存并重试一次（原有机制），引擎按线路记住，之后不再把运行时上下文放到末尾。
- 网关拒绝文本块数组内容时（400 且错误指向消息内容），该线路在本进程内改为纯字符串、不带断点并重试一次；有效策略随之报告为 `openai-implicit`（OpenAI 线路，保留 affinity key）或 `provider-managed`（Anthropic 线路）。

### 3.8 辅助调用（问题 6）

- 记忆提取、会话摘要和记忆写入决策的提示拆成"固定部分 + 按 2,000 字符封口的对话分片 + 末尾变化部分"（`services/memory-prompt-segments.ts`）。显式断点线路上每段是一条消息，稳定边界在最后一个封口分片之后；对话窗口按整步移动，窗口起点在相邻调用间不变。
- 写入决策把已有记忆目录作为固定部分，候选放末尾，并且只能指向它看到过的条目。
- 每个辅助用途在每个会话有自己的缓存范围，边界历史与主会话分开保存，互不挤占。
- Claude 线路只在先前写过的断点处读取，所以辅助调用会在上一次调用的稳定结尾处再打一个断点读取，同时在本次稳定结尾处写入；辅助调用的末尾不再放滚动断点。
- 桌面端外部运行时（Codex / Claude Code 会话）的记忆调用同样按分段请求发送。

## 4. 结果

经 OpenRouter 实测，基线与本分支各跑一遍短会话。单次样本、run 较短，只作佐证。

**run 首次请求的复用比例**（读取量占上一次请求 prompt 的比例，依次为 run 2–4）：

| 线路 | 基线 | 本分支 |
|---|---|---|
| `gpt-6.1-sol`（openai-hybrid） | 92.3% / 94.9% / 97.5% | 99.97% / 99.97% / 99.97% |
| `claude-sonnet-5`（anthropic-explicit） | 93.3% / 95.1% / 97.7% | 99.99% / 99.99% / 99.99% |

**整体命中率**（不含第一次请求）：GPT 96.8% → 98.2%，Claude 97.0% → 98.6%。

**辅助调用命中率**（run 2–4）：

| 调用 | 基线 | 本分支 GPT | 本分支 Claude（第 3.8 节最后一项修复之前） |
|---|---|---|---|
| 记忆提取 | 每次 0% | 67% / 94% / 92% | 约 70%，且不随提示增长 |
| 会话摘要 | 每次 0% | 0% / 89% / 87% | 约 53%，且不随提示增长 |

Claude 线路辅助调用"读取量不随提示增长"的原因是只在先前写过的断点处读取，而下一次调用的稳定断点总比上一次靠后；修复见第 3.8 节，修复后没有再做真实端点测量。

## 5. 已知限制

- **降级到旧版本**：旧版本不认识账本的撤销标记，会把已撤销的上下文重新回放；旧版 TUI 的 `/resume` 会把账本消息当作普通消息显示；旧版手机端的输出历史恢复不认识 `prompt_rewrite` 事件，会拒绝该会话的历史。
- **缓存热度不跨进程**：攒批判断用的"上一次成功请求时间"只在内存里，重启后第一步按 `cold` 处理并清掉待办。
- **窗口移动后记忆提取看到的近期对话变少**：对话窗口按整步移动，刚移动后窗口里的近期对话比移动前少。
- **轮数警告跨重启保留**：落盘的 run 内提醒（包括轮数和预算警告）重启后照样回放，即使它描述的状态已不成立。
- **整段比较的段变化时整段重发**：除 git 状态（只进快照）外，能力、来源、Goal 状态、MCP 失败摘要等整段比较的段，一变就整段重发。
- **原生 Anthropic 线路的辅助调用没改**：第 3.8 节"在上一次稳定结尾处再打断点"只在 OpenAI 兼容客户端（OpenRouter 上的 Claude）实现；原生 Anthropic 客户端依赖厂商的块回看，未实测。
- **回复表示**：带推理内容回显的线路上，在线历史里的最终回复是字符串，回放时是"推理块 + 文本块"；Anthropic 原生 `provider-managed` 线路上字符串与单个文本块的字节也不同。这些线路重启后的第一次请求会从该回复处断开。
- **公共 SDK 方法保留**：`PromptComposer.buildDynamicContextMessage` 和 `MemoryManager.buildInjectionIndex` 已无内部调用方，但属于稳定 SDK 导出的类，没有删除。
- **探针覆盖**：探针上下文较短、间隔固定，没有覆盖很长的上下文和缓存有效期边界；只测了经 OpenRouter 的两条线路。Claude 线路上"断点有无改变前缀"的原因（相邻用户消息被合并）是推测。

## 6. 探针验证（2026-11-12）

| 设计点 | 改前 | 改后 | 线路 |
|---|---|---|---|
| 跨 run：旧动态块留原位、只追加变化 | 43%–45% | 100% | GPT 直接成立；Claude 需要内容统一用数组形式 |
| run 内：旧快照不折叠 | 36%–37% | 100% | 两条线路 |
| 改写点之前有断点 | 36%–38% | 约 70% | 两条线路 |

另外确认：单是折叠旧快照就足以让缓存退到系统段；缓存读取只落在系统段末尾、显式断点、或上一次请求的完整前缀上，不是最长公共前缀。

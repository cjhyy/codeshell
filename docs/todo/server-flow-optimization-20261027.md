# Server 全流程优化：2026-10-27 首轮

范围是个人 Hub 与 Mobile 共用的服务端：认证、静态资源、关闭/重启以及原生流程门禁。
保留单 owner、现有权限、会话与文件格式；不包含生产部署、正式发版或新的多租户运行时。

## 改动与回归

- **认证热路径**：每次读取已提交的 `auth.json`；活动时间未到一分钟时无需获取写锁。
  到期更新先加锁，再读当前记录并重验过期/撤销，避免写回旧快照。继续拒绝被替换为
  符号链接的认证目录、损坏文件和失效令牌。回归实际持有另一个写锁，证明近期会话校验
  可完成；另验证更新前被其他实例撤销的会话不会恢复。
- **静态资源**：Hub `/` 与 SPA fallback 的 `index.html` 也受根目录校验；保留目录内
  符号链接。Hub 和 Mobile 共用异步文件描述符与流式发送，响应固定为打开时大小，
  `HEAD` 不创建 reader，读取失败或客户端断开都会清理句柄。保留原缓存策略。
- **关闭流程**：关闭开始即阻止新 HTTP/WS 接入，追踪认证中尚未升级的 TCP 连接；
  多次关闭共用完成结果，等到 Worker 退出和各服务清理后才结束。清理错误不能跳过
  其余资源，并且应向调用方报告。
- **原生门禁**：`bun run test:server-smoke` 在隔离 HOME 中启动驱动、Hub 和真实 Core
  Worker，网络限制到准确的本机 fixture Origin，导入生产模块前执行 guard。
  初始化、对话、配置热更新、审批、取消、历史管理和重启续聊继续由真实 Node 流程验证。
  正常停服必须退出码 0、无信号、未强杀；强杀仅用于失败清理。CI 的 `rest-server`
  复用已有构建执行该流程。

修复前证据：首页外向符号链接回归得到 200 而非 404；写锁占用期间近期会话认证无法完成；
关闭回归可在退出过程中接入 WS/获取健康响应，多次关闭也没有共用完成结果。

## 性能采样

本机 macOS / Node v25.8.1，独立临时认证目录、一个有效会话、固定时钟，每组执行
2,000 次 `authenticate`，三组连续执行。旧实现耗时 1109.68 / 913.63 / 882.90 ms；
新实现 392.03 / 416.64 / 400.11 ms，中位数减少约 56%。
这是固定数据的小基准，其他本地任务并行运行；不代表部署吞吐、长尾延迟或多用户性能。
静态资源主要验收内存与生命周期语义，没有用单机吞吐数字代替压力验收。

# 复杂工具 schema 构参与缓存对照

日期：2026-11-12。接续 [第四步原生工具引用](anthropic-native-tool-references-20261111.md)，使用同一份累计 2 美元授权。所有付费请求已结束，未执行目标工具。

## 结论

- 本组 8 个复杂 schema 用例中，指定 `CallTool` 调用为 **16/16**；原生引用的指定直接调用为 **10/16**；同时展示发现工具和包装器的 eager 直接调用为 **6/16**。这些是预定调用形式、严格 schema 与逐值语义全部正确的次数，不是实际执行成功率。
- 允许正确的真实名调用或合法 `CallTool` 两种形式后，三组分别为 **8/16、11/16、16/16**。不能把合法的另一种调用形式混同为参数理解错误，也不能把错误包装自动剥掉后改判通过。
- **缓存验收通过**：三组全部 24 个相同请求复测命中率超过 99.96%；两条发现轨迹都复用了逐渐增长的历史前缀；暖恢复逐字节相同且命中；改写第一个工具定义的负控读取量为零，恢复原请求后重新命中。
- 发现并修复了一个实际协议错误：`tool_reference` 与说明文字混在同一 `tool_result`，Anthropic 返回 HTTP 400。先前手写纯引用探针没有覆盖真实 `ToolSearch` 输出。
- **原生路径的复杂 schema 调用准确率验收仍未通过。** 此轮不能据此扩大原生路径启用范围，也不能声称三种方式准确率等价。

逐请求响应、评分、费用、请求摘要与缓存统计见 [实测证据 JSON](prompt-cache-probes-20261111/complex-schema-evidence-20261112.json)。证据保留最初的失败样本和 HTTP 400，没有用后验重测替换原成绩。

## 测试方法

OpenRouter `POST /api/v1/messages`，模型 `anthropic/claude-sonnet-5`，固定 Anthropic 上游，关闭 thinking，每次最多 768 输出 token。未启用严格输出模式或强制 `tool_choice`，未自定义采样参数。固定上游和费率上限是探针控制；生产 Anthropic 客户端不转发任意 `extraBody.provider`。

主比较使用 4 个工具、8 段自然语言任务，各取两次返回，共 48 个模型构参样本。两个重复请求的输入完全相同，历史互相独立，没有放入前次答案。它们不是 48 个独立任务，重复样本也可能相关。每个分支共享合成说明前缀，使缓存输入足够长。

| 组别           | 工具目录与发现方式                                                                                                        | 预定目标调用          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| eager 混合目录 | 4 个完整目标定义及 `ToolSearch`、`CallTool` 均在顶部                                                                      | 真实工具名            |
| native         | `ToolSearch`、`CallTool` 在顶部，4 个目标定义 deferred；真实模型先调用搜索，真实 handler 产出结果，再由生产序列化器转引用 | 真实工具名            |
| call-tool      | 同一 Sonnet 5 Messages 路线强制使用通用文本投影；目标 schema 通过真实 `ToolSearch` 追加                                   | `CallTool(name,args)` |

复用生产 `RunToolSurface`、`ToolSearch`、Anthropic 请求投影及缓存周期恢复函数；HTTP 使用禁止重试的单次传输。没有实例化执行目标工具的 Engine；工具回执是明确标识的合成文本。离线 SDK/Engine fixture 另行验证实际生产请求形状。

覆盖嵌套对象、数组顺序、枚举、`oneOf`、`$defs/$ref`、`anyOf`、数字边界、显式 JSON null、可选字段省略、引号和换行。评分使用严格 schema 校验与独立预期值比较；仅忽略对象键顺序，不容忍数组换序、字符串/数字转换、null/省略混同或额外外层包装。

## 构参结果

| 组别                       | 预定形式且 schema/语义全对 | 允许两种合法形式后全对 | 预定形式 schema 合法 |
| -------------------------- | -------------------------: | ---------------------: | -------------------: |
| eager 混合目录             |              6/16（37.5%） |            8/16（50%） |                 6/16 |
| native（修复 HTTP 400 后） |             10/16（62.5%） |        11/16（68.75%） |                11/16 |
| CallTool                   |              16/16（100%） |          16/16（100%） |                16/16 |

表中“允许两种合法形式”仍要求严格 schema 和原任务语义正确；没有调用执行器，不能理解为工具执行成功。两次缓存轨迹里的辅助目标调用也均正确，单列为 2/2，不加入 48 个主样本。

下表每格是两次预定形式完全正确的次数：

| 用例                             | eager | native | CallTool |
| -------------------------------- | ----: | -----: | -------: |
| 嵌套对象、可选字段保留           |   0/2 |    2/2 |      2/2 |
| 嵌套对象、可选字段省略           |   0/2 |    0/2 |      2/2 |
| 两项数组、枚举和顺序             |   2/2 |    2/2 |      2/2 |
| 三项数组、枚举和顺序             |   1/2 |    1/2 |      2/2 |
| oneOf 的 inline 分支、引号和换行 |   2/2 |    1/2 |      2/2 |
| oneOf 的 archive 分支            |   1/2 |    2/2 |      2/2 |
| 显式 null                        |   0/2 |    0/2 |      2/2 |
| nullable 对象分支、可选字段省略  |   0/2 |    2/2 |      2/2 |

错误分解：

- eager：8 次用真实工具名却把参数多套一层 `args`；2 次选择合法 `CallTool` 而非指定直接调用。仅用于诊断地去掉外层包装后，16 次内部参数都与预期相同。
- native：4 次用真实工具名却传入 `{name,args}`；1 次合法 `CallTool` 替代直接调用；1 次把可选 `operatorNote` 的 JSON `null` 写成字符串 `"null"`，该值符合 nullable-string schema，但不符合任务。仅做内部参数诊断时是 15/16。
- CallTool：16 次包装、schema、语义均正确，没有截断。

### 后验纯 eager 诊断

原 eager 目录同时有 `CallTool`，`ToolSearch` 的说明又建议可用时采用包装器，与该组指定直接调用的要求存在混淆。为诊断这一点，另做 8 次单样本测试：移除 `ToolSearch` 和 `CallTool`，保留相同目标定义、任务、直接调用说明及模型设置。

结果 **7/8 全对、8/8 schema 合法，零外层包装错误**；唯一错误仍是 `operatorNote: "null"`。此结果与混合目录影响调用形式的解释一致，但只是后验单样本诊断，不能与主组的 16 次直接排名，不能证明因果，也不替换原 eager 成绩。未据此修改生产提示词或自动修正模型参数。

## 缓存结果

缓存分母为 `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`；没有把缓存 token 漏出分母。

事先设定：相同请求和恢复请求读取比例至少 95%；追加请求应读取此前全部输入，仅容许 32 个尾部 token；故意改写首个工具的负控要求读取为零且有新写入。若原前缀距追加请求已达 5 分钟，标记过期，不能归因于前缀失效。本次最长间隔为 54.461 秒，没有过期。

| 组别     | 8 个相同请求重复的最低读取比例 | 暖恢复/恢复原请求读取 token | 首工具改写负控读取 token |
| -------- | -----------------------------: | --------------------------: | -----------------------: |
| eager    |                       99.9728% | 7,382 / 7,384（恢复原请求） |                        0 |
| native   |                       99.9662% |               7,179 / 7,181 |                        0 |
| CallTool |                       99.9659% |               7,102 / 7,104 |                        0 |

逐步追加的历史覆盖：

| 阶段                           | native：前次输入 → 本次读取 | CallTool：前次输入 → 本次读取 |
| ------------------------------ | --------------------------: | ----------------------------: |
| 追加首工具回执、发现第二工具   |               6,092 → 6,090 |                 6,008 → 6,006 |
| 追加第二工具发现结果及调用任务 |               6,365 → 6,363 |                 6,281 → 6,279 |
| 追加第二工具回执               |               6,961 → 6,959 |                 6,886 → 6,884 |

每一步仅有 2 个前次输入 token 未读取，说明复用了增长中的历史。追加阶段按“本次全部输入”计算的比例约 91%–97%，差额包含新增内容，不能误判为旧前缀丢失。

暖恢复把 selection/history 序列化落盘后，用实际缓存周期恢复函数重建；即使当前目录 description 改变，完整请求体仍逐字节相同。工具/system 字节断言不做归一化；历史只忽略允许移动的 `cache_control`。三组负控均读取为零，恢复原请求又重新读取缓存。

## 实测发现的协议修复

首轮第 20 次请求返回：

> Tool definitions/code execution functions cannot be mixed with other content

该请求的真实 `ToolSearch` 结果是 `tool_reference`、空白分隔和原生调用说明混排。修复后的投影按整个 `tool_result` 决策：

- 只有成功结果且全部 schema 与冻结 deferred 定义逐字节匹配，剩余内容仅为共用固定说明或空白时，输出纯引用。固定说明已由 `ToolSearch` 定义提供。
- 任何额外 guard、post-hook、健康提示、图片、未匹配/晚到/变化的 schema 或错误结果，均让整个结果保留原始文本/图片，使用既有文本调用方式。
- 不把未知工具输出提升为普通 user 指令，不丢额外上下文，不改中立历史或执行资格。

新增协议 fixture 会拒绝曾经导致 HTTP 400 的混排形状，并覆盖实际 `ToolSearch` 多工具结果、流式/非流式、并行结果、重启和追加前缀。修复前新增回归有 7 项失败，修复后通过。续测 native 的 26 次请求全部得到 HTTP 200。

协议参考：[自定义工具搜索返回引用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool#custom-tool-search-implementation)、[工具回执及工具输出信任边界](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)。具体混排限制由此次真实 400 及修复后实测确认。

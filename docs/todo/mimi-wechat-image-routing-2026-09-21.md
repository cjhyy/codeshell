# Mimi 微信纯图片转交失败

日期：2026-09-21。本记录区分运行中的 0.9.21 与本次源码修复；未修改用户的原始消息或附件，也未重放真实微信消息。

## 现场证据

用户从微信发送图片后，桌面 Mimi 工作台没有图片或缩略图，Mimi 回复未收到图片。

- 本地 IM inbox 中存在两条待转交的纯图片消息，接收时间为 11:13:41、11:15:52（Asia/Singapore）。两条消息的 `text` 均为空字符串。
- 两份附件已经落盘，分别为 146074、146425 字节，文件头均为 JPEG/JFIF。检查时分别已重试 26、22 次。说明下载与本地持久化已经完成，不能解释为用户未发送或微信未传图片。
- 对运行中的 Desktop 会话路由端点提交对应的路由字段，返回 HTTP 400：`invalid session route request`。请求在校验阶段被拒绝，没有触发模型或外部回复。
- 同时段 Mimi transcript 没有这两条图像消息，与工作台未显示一致。调查不复制图片内容、账号标识或控制端点凭据。

## 根因与修复

转交链路为：微信适配器 → 持久化 inbox → `createBoundSessionChat` → `/v1/session/route` → 未绑定时 `createMimiPetChat` → `/v1/pet/chat`。

即使用户没有进入工作会话，也必须先经过会话路由检查。路由只携带身份和文字，附件字节暂留网关。`parseSessionRouteRequest` 错误地使用要求非空字符串的 `boundedField` 校验文字，导致合法纯图片消息在查询绑定状态之前就被拒绝。异常返回持久化队列，持续重试同一个无效请求，图片无法进入 Mimi 和工作台。

这处故障发生在模型调用之前，提示词不是此处根因。

修复仅放宽路由请求的文字非空限制：仍要求字符串类型，保留 32000 字符上限、身份字段非空校验和鉴权。未绑定的纯图片消息可继续传入 Mimi；已绑定工作会话仍由原有 bridge 检查支持的内容，不改变其空输入拒绝行为。本次不扩展工作会话的附件支持。

## 验证

新增测试使用真实本地 HTTP 服务、Desktop 客户端、持久化队列和两层转交中间件；模型与渠道回复为测试替身。两条合成图片消息必须保持附件字节不变、各交付一次，并从磁盘待处理队列移除。

- 修复前，新测试稳定复现两次 `DesktopControlOperationError: invalid session route request`。
- 修复后，7 个相关文件共 75 项测试通过，244 条断言，0 失败。覆盖队列重启恢复、微信附件持久化、路由 HTTP 边界、未绑定空文字放行、已绑定空文字拒绝，以及畸形/超长文字继续返回 400。
- Desktop 主配置及移动端类型检查通过。
- 三个变更 TypeScript 文件 ESLint 通过，`git diff --check` 通过。

之前的微信图片回放测试直接接入 Mimi 中间件，遗漏了其前面的绑定会话 HTTP 路由校验；新增跨边界回归补上这一缺口。

## 部署边界

源码修复不影响已运行的 0.9.21 进程。两张原图仍保存在本机队列中，无需用户重新上传；安装并启动包含修复的版本后，可由原有重试机制继续转交。真实工作台显示及队列清空仍需在加载新版本后验收，不能以本次模拟测试宣称已恢复。

## 实施方案与验收清单

- [x] Worker 请求区分受理期限与执行生命周期。仅匹配本次 requestId/sessionId 的 agent/runAccepted 可解除受理计时；之后等待真实结果、取消或 worker 退出。控制操作保留原期限。
- [x] Mimi 的聊天、报告与回执修正调用采用完整回合等待，持续保留派单和宿主操作结果的处理者。
- [x] 微信提交改为短请求受理与有界长轮询，避免把整个模型回合绑在 150 秒 HTTP 请求上。请求票据有容量和过期清理，按渠道消息身份合并重试；服务重启后由持久化 inbox 和原有 clientMessageId/操作回执恢复。
- [x] 连接中断和暂时不可用必须留在 inbox 重试，不能发送通用错误后当作成功处理。真实运行失败仍返回明确失败。
- [x] 跨进程、跨 HTTP 回归覆盖超时边界后的真实结果、连续输入只回复一次、迟到派单执行一次、重试去重、退出/取消、未知票据、身份冲突与容量限制。
- [x] 模型输出不完整工具参数时保留解析失败标记，执行器返回可修正的 JSON 错误；禁止把空对象当成真实参数执行。流式、非流式及工具无必填参数的情况均有测试。
- [x] 定向测试、类型检查、lint 与代码审查。已运行的旧应用不会自动获得源码修改；不重放用户原消息或对外发送测试通知。

- `bun run typecheck` 全仓通过；所有改动 TypeScript 文件 ESLint 通过。旧有启动失败、停止、steer 期间退出、报告恢复、图片纯附件路由也通过。

## 具体实现

`WorkerBridgeCore.waitForRunCompletion` 是通用可选能力，要求同时启用发送失败和进程退出结算。Pet 两个集中运行入口开启它，其他控制操作保留原行为。

控制面新增 `POST /v1/pet/chat/start`（30 秒请求期限）和 `GET /v1/pet/chat/result/:id`（最多等待 25 秒，客户端 35 秒期限），旧同步接口保留。票据最多 256 个，完成后保留 10 分钟；容量满时仅淘汰已完成记录，运行中记录绝不丢弃。原渠道、会话、发件人、消息 ID 相同则复用票据；内容不一致返回 409；失效票据或容量暂满返回可重试的 503。

客户端期限覆盖响应正文读取；断线、损坏或不完整响应和 502/503/504 交回 inbox 重试。工具参数修复属于通用 provider/executor 合约，不向 core 添加 Pet 专属规则，也不靠放宽 prompt 掩盖传输错误。

## 边界

票据是运行中关联缓存，不替代现有磁盘 inbox、Engine run_result 或宿主操作回执。运行被受理后不以固定总时长猜测失败；模型/工具各自期限、用户取消与进程退出继续生效。参数 JSON 解析失败与本次超时分开验证，不能根据一个缺失字段推断具体上游损坏原因。

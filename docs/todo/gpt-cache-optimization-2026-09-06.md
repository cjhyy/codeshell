# GPT 缓存优化实现与验证

日期：2026-09-06（Asia/Singapore）。对应此前的 `gpt-cache-root-cause-2026-09-06.md`。

## 实施选择

沿用 `llm/prompt-cache.ts` 统一缓存策略，把 GPT-5.6 路径从 explicit-only 改为自动尾部缓存加显式历史断点（日志策略名 `openai-hybrid`）。模型输入的文字、角色和工具结果保持原意，不为缓存插入额外用户消息。旧模型的 implicit 路径、Anthropic 的断点布局及不支持显式字段时的兼容降级保留。

这是对此前第二项原因的进一步收窄：当前 OpenRouter → OpenAI GPT-5.6-sol 路由的问题出现在 **explicit-only 模式**。同一工具消息边界在 hybrid 模式下可以正常写入、读取；不应把它描述成该路由在所有模式下都不支持工具断点。

官方支持 `mode: implicit` 与显式 marker 共存，自动尾部占一个写位置。实现因此选择：

```text
系统边界 + 稳定历史边界 + 上一成功请求的有效边界 + 当前自动尾部
```

最多三个显式位置，另一个写位置留给当前自动尾部。重复位置去重。

## 断点生命周期

`PromptCacheHistory` 仅记录边界索引、前缀摘要、请求顺序和时间。最多128个scope，候选边界30分钟后停止使用；不保存用户消息或工具正文。

- 在最终归一化后的 OpenAI 消息中寻找最后一个非空 user/tool 边界，正确处理一条源消息拆成多个工具结果的情况。
- 在添加 marker 之前计算摘要。摘要包含实际请求设置、工具、schemas 和边界之前的完整消息，避免 marker 的包装变化影响自身匹配。
- 会话、provider、模型和 endpoint 共同隔离本地边界记录。边界记录在同进程客户端重建后仍可使用；进程重启后自动重新建立。
- 新请求只有完整前缀匹配时才带上旧边界。历史改写、工具或相关配置变化时，不再标记失效位置。
- 只有请求成功、取得有效输入 usage 且未取消时更新记录；普通的并发倒序完成不会覆盖较新的成功边界。
- provider 的实际 KV 缓存仍在服务端。本地摘要只用于选择读取位置，不能保证服务器一定命中。

局限：元数据若已被容量淘汰，较早的未完成请求随后成功，可能重新记入较旧的边界；完整前缀摘要仍会检查，影响的是优化效果。更换同 endpoint 的凭据也可能沿用本地候选位置，但实际缓存由 provider 隔离。

## 上下文组装

`TurnLoop.restoreVolatileAfterContextManagement()` 改为比较实际消息内容，身份比较作为快速路径。

- 仅处理新尾部的持久化／截断时，把处理后的结果原位合回，保留已有动态块及之前消息的位置。
- 对象发生复制但最终内容一致时，返回原数组。
- 动态边界之前的历史真被改写、或压缩改变消息数量时，继续按原语义在新尾部恢复动态块。
- 摘要依旧不包含动态内容；持久化、截断、敏感结果清除和图片降级功能保留。

真实 ContextManager 回归中，连续两个新大结果落盘后，所有已发送消息字节都保持不变。原故障复现的首个变化位置从 index 1 变为无差异。

## 诊断

保留原接近归零的告警，增加“缓存读取至少下降50%，同时损失至少4096 tokens”的部分失效判定。生产样例的256193 → 27131现在会报告下降；后续稳定在27131时不重复报告。

冷启动、缓存增长以及仅新增输入导致命中率下降均不触发。暂不加入没有历史前缀证据的自动停滞归因。

## 实际路由验证

模型：`openai/gpt-5.6-sol`；地址：`https://openrouter.ai/api/v1/chat/completions`；响应provider：`OpenAI`。

先以3次合成流式请求验证hybrid，再用修改后的真实OpenAIClient发3次请求。均只使用人工生成的无业务内容文本与虚构工具记录，没有执行模型返回的工具调用。各轮之间只追加工具调用及结果，没有追加用户消息。

修改后客户端的结果：

| 请求 | 输入 tokens | 缓存读取 | 缓存写入 | 命中率 |
| --- | ---: | ---: | ---: | ---: |
| C1：初始工具轮 | 5708 | 0 | 5705 | 冷启动 |
| C2：追加下一组工具结果 | 5933 | 5705 | 225 | 96.16% |
| C3：重建客户端后追加工具结果 | 6158 | 5930 | 225 | 96.30% |

`C3.read = C2.read + C2.write = 5705 + 225 = 5930`。已实际读回上一请求新写入的工具历史，无需合成“继续”用户消息。

6次验证请求的响应usage.cost合计 **US$0.0346484**。原始数值保存在同目录 `gpt-cache-optimization-evidence-2026-09-06.json`，没有凭据或项目内容。

这些小样本证明当前路由上的机制可行，不保证所有生产请求达到相同比率。实际效果还受新增结果大小、历史压缩、缓存寿命和provider路由影响。

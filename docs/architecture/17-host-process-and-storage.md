状态：**0.12 候选集成中**（2026-11-22）。L1–L5 已进入集成分支，L6 的服务迁移和 L7 的候选验收在 [PR 421](https://github.com/cjhyy/codeshell/pull/421) 继续。

## 0. 摘要

**问题**：Desktop 的数据和业务逻辑都跑在 Electron 主进程。同步读写、等锁、全量重建会卡住主线程；macOS 的输入事件经主进程路由，于是会话输出时滚动卡顿。任务中心每次都全量重建，没有隐藏或永久删除，也不跟随会话的归档和删除。已结束的任务会被元数据改动重新「顶起来」。

**方案**：参照 Codex 桌面端（数据库全部在独立的原生进程 `codex app-server` 里，界面通过 JSON-RPC 取数据），做三件事。

1. **进程**：数据层和业务逻辑搬到独立的 **Host 进程**（Electron `utilityProcess`）。渲染进程通过 **MessagePort** 直连 Host，主进程只管窗口和系统能力。
2. **存储**：引入 **SQLite**（Electron 45 自带的 `node:sqlite`）存放可重建的索引和投影。所有可能等锁的写入放在 Host 内的独立**存储线程**里。
3. **任务中心**：按变化增量更新；用户意图（隐藏、删除）和来源投影分开存；任务跟随会话的生命周期。

**已有实测**（附录 A）：

| 验证项                                            | 结果                                                                               |
| ------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Electron 45 下 `node:sqlite`                      | 可用。Node 24.22.3、SQLite 3.54.1；单行 upsert 0.16ms，热区查询 0.27ms             |
| 渲染进程经 MessagePort 直接查 Host 里的 SQLite    | 往返 p50 0.2ms，p99 0.4ms（无竞争基线）                                            |
| 主线程被人为阻塞 1.5s 期间发起 300 次查询         | 全部在阻塞期间完成，延迟不变                                                       |
| 另一连接持有写锁时，同步写入（`busy_timeout` 5s） | 卡住所在线程 5.2s，同线程的定时器也被推迟 5.2s，所以写入必须离开消息循环所在的线程 |

## 1. 问题与证据

### 1.1 卡顿

2026-11-20 录到的 Performance trace（20s，边输出边滚）：

- 渲染进程只有 1 个超过 16ms 的长任务；
- 主进程有 26 个长任务，合计约 2.6s，最长 221ms；
- 输入事件间隔最大的 12 个空档里，9 个落在主进程长任务里；
- CPU 采样集中在三处：任务中心全量重建；每个流式事件触发的输出记录同步校验；每次新建 `SettingsManager` 重读设置文件。

### 1.2 结构性问题（主进程盘点：约 13.1 万行、542 个非测试文件）

| 问题                          | 位置                                                                                                                        |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| agent 引擎跑在主进程          | `automation-host.ts:298`（定时任务）、`dream-service.ts`（记忆整理）                                                        |
| 每个流式事件都做同步磁盘 I/O  | `agent-bridge.ts:577` → `main-output-publisher.ts:60` → core `outputJournalCutover`（`output-journal.ts:232-241, 435-455`） |
| 每个流式事件都全量转发        | 逐行 `JSON.parse`，发给所有窗口，再交给 6 路订阅，还写一条脱敏日志                                                          |
| 等锁是同步睡眠                | `acquireFileLock` 重试时调用 `Atomics.wait`（`core/src/utils/file-mutex.ts:62,127`）                                        |
| 每次 `agent/run` 都有同步读写 | `agent-bridge.ts:775-804`                                                                                                   |
| 会话列表被重复投影            | Mimi 聚合器、会话目录、任务中心、侧边栏的 `listDiskSessions`（每次扫描并解析全部 `state.json`）                             |
| IPC 全部经过主进程            | 约 480 个 `handle`、22 个 `on`、50 个推送通道                                                                               |

### 1.3 任务中心的产品缺陷

- **没有隐藏和永久删除**，用户无法清理已结束的任务。
- **不跟随会话生命周期**：来源映射完全没有处理 `archivedAt` 和目录删除标记。投影只会给消失的记录打失效标记，从不删除。本机统计，会话类任务中约四成属于已归档的会话，约两成属于已删除的会话；后者大多永远停在「已中断」。
- **元数据改动会让已结束的任务重新「动起来」**：会话任务的 `updatedAt` 取磁盘状态、实时活动、目录元数据三者的最大值（`task-inbox-sources.ts:243-247`）。改名、归档这类与运行无关的改动也会刷新它，于是任务被重新排序。本机有已归档会话的任务在最近 7 天内被更新过。

### 1.4 参照：Codex 桌面端（本机按进程核实）

- 界面进程打开的 SQLite 文件数为 0。所有数据库（会话索引 `state_5.sqlite`、`queue_1.sqlite`、`logs_2.sqlite`，均为 WAL）都由原生进程 `codex app-server` 打开，SQLite 静态链接在里面。
- 会话索引表 `threads` 一行一个会话，在 `updated_at`、`archived`、`source` 上建了索引；用 `backfill_state.last_watermark` 从原始文件增量补建。**表里没有运行时状态**，运行状态只在内存里，通过事件推送。

## 2. 目标架构

```
Renderer（每个窗口）
  preload 按功能域路由 ──MessagePort（JSON-RPC）──┐
          └──ipcRenderer（窗口类功能）──┐        │
                                      ▼        ▼
Main（壳）                          Host（utilityProcess）
  窗口 · WebContentsView · 菜单        主线程：连接上下文、RPC 路由、业务服务、
  protocol.handle · 浏览器驱动              流式分发、执行者、SQLite 只读连接
  更新器 · 通知投递 · 全局快捷键        存储线程（worker_threads）：
  系统能力适配器（Host 反向调用）            SQLite 写入、所有需要拿文件锁的 JSON 写入
  端口交接 · Host 监控与重启                 对账与补建
          ▲                                 │ stdio JSON-RPC（不变）
          └──── parentPort 反向 RPC ────────┤
                                            ▼
                                      agent worker（可重启、崩溃隔离）
```

### 2.1 进程与线程分工

| 位置              | 负责                                                                                                                                                  | 防的是什么                                          |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| **Main**          | 盘点中的 C 类服务（窗口、协议、浏览器驱动、更新器、通知投递等）；系统能力适配器；端口交接；Host 的启动、监控和重启                                    | 输入不被业务工作耽误                                |
| **Host 主线程**   | HostRuntime 与 A、B 类服务；连接上下文与权限判断；流式分发；执行者（worker 管理、调度器、外部运行时、定时任务和记忆整理的 `Engine`）；SQLite 只读连接 | —                                                   |
| **Host 存储线程** | SQLite 写入；所有需要拿文件锁的 JSON 写入（`mutateJsonFile`、`acquireFileLock`）；启动补建与定期对账                                                  | 等锁和大文件读写不卡 Host 的消息循环（附录 A 实测） |
| **agent worker**  | agent 运行，不变                                                                                                                                      | 崩溃隔离                                            |

**存储线程的接口**：Host 主线程通过 `postMessage` 提交领域请求（如 `sessions/reconcile`、`tasks/reconcile`），拿回 Promise。每个会话数据根的存储线程按接收顺序处理固定领域命令，批量索引更新在事务内提交。各数据根可独立推进。加锁的业务写入经领域命令提交，渲染进程不能指定 SQL 或任意文件路径。[存储线程](../../packages/core/src/storage/worker.ts)

**读路径**：SQLite 读在 Host 主线程用只读连接完成。WAL 模式下读不会被写阻塞，单次查询不到 1ms。JSON 存储的读取由各服务维护的内存副本承担，与现在相同。

选 `utilityProcess` 的原因：同一个 Electron 二进制，不需要额外打包和签名；支持 Node、`child_process`、`worker_threads` 和 MessagePort；生命周期跟随 App。以后如果要做本机守护进程（第 16 章 3.3），Host 代码不变，只需把端口换成 socket。

### 2.2 生命周期

- `app.whenReady()` 后先启动 Host，再创建窗口。
- **Host 崩溃**：Main 按退避策略重启（60 秒内最多 3 次）。重启期间，渲染进程的请求返回「宿主重连中」，界面显示可恢复状态。工作台在新端口重新握手，从输出游标补读已落盘内容，并重新查询当前待审批状态。旧代 worker 随 Host 退出，失去执行者的任务按中断处理。
- L2 在 macOS、Windows、Linux 上关闭最后一个窗口后保留 App 和 Host。Windows 和 Linux 用户可用托盘显示工作台或退出，工作台原生 CodeShell 菜单也提供退出。托盘创建失败时常显该菜单，窗口全关后可从启动器重新打开。打开新窗口时重新绑定端口，显式退出时沿用原有保存和清理流程。S2-C 继续负责连接期间阻止睡眠等在线能力。

## 3. 通信、身份与撤权

### 3.1 Renderer ↔ Host

- JSON-RPC 2.0 消息通过结构化克隆传对象。Desktop 专用端口复用 Core 的请求、响应和通知信封，先协商协议版本，再调用握手清单中的方法。L2 首个方法是 `links/listLocalProviders`。0.12 候选的清单还覆盖会话、任务、会话输出与审批，以及工作区等已迁领域。新端口以本次握手返回的 `methods` 为准。[工作台方法注册](../../packages/desktop/src/main/desktop-host/utility.ts)
- **preload 路由表**：`window.codeshell.*` 的接口形状不变，preload 内部维护「功能域 → 通道」表。工作台的已迁功能使用 Host 路由，原生窗口和配对设备分别使用各自经授权的适配器。
- 推送：Host 只向**有权接收**的端口推送（见 3.2），不再广播给所有窗口。

### 3.2 端口身份与实时授权

现有实现会在异步操作生效前重新检查主 frame、会话是否正在删除和会话归属，并处理 A→B→A 的会话转移（`renderer-browser-session-ipc-authority.ts:51-65`、`renderer-browser-session-access.ts:190`）。迁移后必须保持同等强度：

1. **端口只绑定「窗口 + frame 代次」**：Main 在交接端口时，把 `{webContentsId, frameToken, frameGeneration, windowKind}` 作为不可伪造的元数据交给 Host。**会话归属不进入端口身份**。
2. **会话归属每次请求实时判断**：Host 维护会话归属表，归属变化由 Main 的 `sessionOwnerClaimed` 事件同步过来。凡是作用于会话的请求，在**生效前**都要调用 `assertCurrent()`；检查和生效之间如果有 `await`，生效前要再查一次。
3. **作废规则**：
   - 窗口导航或重载导致 frame 代次变化：Host 收到 Main 的撤权或新代次绑定后关闭旧端口；这个端口上还没完成的请求一律以 `revoked` 结束，**不产生副作用**。
   - 会话转移到另一个窗口：转移前原窗口发起、还在进行中的请求，生效前的检查会失败。
   - 会话进入删除流程：所有针对它的请求都会失败。
4. **不受信任的内容**（Panel、云端工作台、浏览器 guest）拿不到 Host 端口，继续走 Main 现有的受控通道。
5. **L2 验收**：伪造身份；窗口重载后旧请求不生效；A→B 转移后 A 的在途请求不生效；A→B→A 后 B 遗留的请求不生效；删除期间的请求被拒绝。

L2 的 `assertCurrent()` 检查 **Host 已收到的** frame、owner 和删除状态。即使会话从 A 转到 B 再转回 A，旧授权也会失效。Main 的控制消息与工作台请求走不同端口，Main 变更与 Host 收到消息之间存在时间差。L2 的 Link 目录只读且无会话权限要求。后续迁入的有副作用方法由实际执行者在**写入、发出命令等提交点**确认授权。例如，任务存储线程在事务内领取一次性许可后才提交用户操作。两条端口的消息到达顺序本身无法确定哪一项先发生。[任务提交](../../packages/desktop/src/main/task-inbox/task-projection-storage.ts)

### 3.3 Host → Main：系统能力的反向 RPC

L2 首先开放 `app/getVersion`，供 Host 缓存版本并答复各端口的握手。L6 按具体业务接入原生能力。下表列出权限归属，实际调用经私有通道和固定操作完成。

| 能力                                    | 用途                             | 约束                                       |
| --------------------------------------- | -------------------------------- | ------------------------------------------ |
| `safeStorage` 加解密                    | 凭据                             | **不能在持有文件锁时等待这个 RPC**，见 8.2 |
| `dialog.*`                              | 选择目录、导出、确认框           | 参数带连接上下文里的 `webContentsId`       |
| `shell.*`、`clipboard.write`            | 打开链接、在文件夹中显示、复制   |                                            |
| `notification.deliver`、`dock.setBadge` | 通知投递                         | 路由和去重留在 Host                        |
| `screen.*`、`powerMonitor` 事件         | Mimi 的窗口几何、空闲和电源事件  | 事件由 Main 推给 Host                      |
| `session.cookies.*`                     | 从浏览器分区刷新凭据             |                                            |
| `windows.*`                             | 打开、聚焦窗口；向非托管窗口广播 |                                            |

### 3.4 Host ↔ Worker

0.12 的 Desktop Host 用 `WorkerBridgeCore` 启动 stdio JSON-RPC worker。工作台请求在当前文档和会话上下文中获准后，Host 解析可信工作目录并发给当前 worker。已保存输出可按游标重读，审批权按当前窗口和 worker 代次重新确认。[worker 组合](../../packages/desktop/src/main/desktop-host/host-worker.ts) · [原生流式验收](../../packages/desktop/scripts/e2e-desktop-host-stream.mjs)

## 4. 存储层

### 4.1 原则

1. **事实来源不变**：`state.json`、`transcript.jsonl`、输出记录、会话目录 `session-catalog.json` 仍是事实来源。SQLite 存的是**可重建的索引和投影**，并保存任务隐藏、删除等用户意图。存储线程在操作时另写意图镜像，供重建和 JSON 模式使用（4.5）。
2. **执行者确认实时状态。** 投影记录最近观测的运行和等待状态，界面接收变更。恢复连接后重新核对执行者，过期投影不能授权取消任务或批准请求。
3. **一个会话数据根对应一个库**：L3 将库放在会话根的同级目录 `.codeshell-state/<根目录名的 SHA-256>/current/state.sqlite`。同一父目录下的两个会话根各用各的库，旧版本枚举会话目录时也不会看到 SQLite 文件。默认的 Desktop 和 TUI 共享同一个根，所以共享同一个库；serve 默认使用 `<dataDir>/worker/sessions`，不同身份使用各自的根（`headless-server.ts:146`、`chat-session-manager.ts:201`），这些范围不会混在一个库里。
4. **驱动按能力加载**：`node:sqlite`（Node ≥ 22.13，Electron ≥ 35）或 `bun:sqlite`，上面一层很薄的同步接口。core 仍然声明支持 Node 20.10，无法加载驱动时，会话列表扫描原文件；存储线程仍可用时，任务投影和用户意图使用 JSON（4.4–4.5）。存储线程本身退出时，在途请求报错，未经确认的用户操作不会报告成功或自动重试。
5. **写入顺序固定**：先写事实来源（JSON），再写索引。索引写失败不影响事实，由对账修复（4.3）。
6. **Schema 迁移**：`schema_migrations` 表，迁移脚本只增不改。发现损坏或未知版本时，先检查其他进程是否仍持有连接；可安全隔离时将库及 WAL、SHM 一起移开，重新建库。用户意图表先从镜像恢复（4.5）。

### 4.2 表

**`sessions`（会话索引）**

| 列                                                                                | 说明                                                   |
| --------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `id`（主键）、`cwd`、`project_id`、`title`、`origin`、`kind`、`parent_session_id` | 来自 `state.json`                                      |
| `status`、`completion_kind`、`archived_at`                                        | 持久化状态                                             |
| `created_at`、`updated_at`、`last_activity_at`                                    | `last_activity_at` 使用会话持久化的运行活动时间（见 4.3）  |
| `external_kind`                                                                   | 外部运行时类型，替代逐会话读取 `external-runtime.json` |
| `state_mtime_ns`、`state_size`、`external_mtime_ns`、`external_size`、`indexed_at` | 对账分别检查会话状态和外部绑定文件。纳秒时间戳以十进制文本保存 |
| `dir_mtime`、`metadata_json` | 目录顺序和可空的列表投影。保留尚无可展示状态的目录位置，以兼容旧数字偏移 |

列表按 `(dir_mtime DESC, id)` 排页，子会话用 `(parent_session_id, dir_mtime DESC, id)`。另有按更新时间、项目、归档时间的索引。历史文件列表的大小、标题和日期存在可重建的 `session_history` 表。[迁移定义](../../packages/core/src/storage/schema.ts)

**会话目录不并入这张表**（评审第 2 条）。草稿（`pendingFirstRun`，还没有 `state.json`）、置顶、手动标题、删除标记仍然在 `session-catalog.json`，由会话目录服务维护。查询时把两边组合起来：

- 草稿只来自会话目录；
- 有删除标记的会话被过滤掉；
- 用户在目录里设置的标题和置顶覆盖索引里的值。

**`tasks`（任务中心的来源投影）**：`task_key`（主键）、`source`、`source_id`、`attempt`、`session_id`、`project_id`、`status`、`tier`（`hot` 或 `cold`）、`activity_at`、`terminal_at`、`stale`、`source_revision`、`record_json`、`projection_only`。索引：`(tier)`、`(status, activity_at DESC)`、`(session_id)`、`(project_id, activity_at DESC)`。

**`task_user_state`（任务的用户意图）**：`task_key`（主键）、`hidden_at`、`hidden_reason`（`user` 或 `session-archived`）、`deleted_at`、`deleted_revision`、`deleted_activity_at`。另存 `session_id` 和隐藏时冻结的 `frozen_activity_at`。会话归档及删除策略使用 `task_session_state`，投影版本、意图版本和来源错误使用 `task_projection_state`。详见第 5 节。

### 4.3 补建与对账

- **增量补建**：启动时由存储线程比对目录、`state.json` 和外部绑定文件的指纹，补建新增或发生变化的会话。Desktop 在状态提交后通知 Host，每批最多合并 512 个变更 ID。旧版客户端、TUI 写入的变化由下面的对账兜底。
- **按 ID 集合对账**（评审第 3 条）：枚举会话目录，与 `sessions` 表的 ID 集合比对：
  - 目录不在了：清除会话索引行。任务对账另行检查曾经观测到的会话，确认数据根可读且目录确实消失后，会话所属任务才按 5.3 清理；
  - 目录存在但没有索引行，或者修改时间、大小和索引不一致：重新 upsert。
- **对账时机**：启动时一次；之后每 60 秒比对目录和文件指纹，只对变化的文件读取内容。根目录监听及 Desktop 写入通知触发单个会话更新。
- **崩溃一致性**：JSON 写完、索引还没写就退出时，下次对账会按修改时间不一致或缺行补上。隔离验收涵盖旧客户端在 Host 在线时删除会话，以及 JSON 已提交但索引尚未更新时退出的情形。

L3 的目录查询继续使用已有的目录修改时间和 ID 游标，兼容旧的数字偏移。新状态在 run 或状态改变时保存 `runActivityAt`，改标题和归档保留这个时间。历史状态缺少该字段时，索引用已有的会话创建时间。索引只复制列表展示字段和外部运行时种类，原始状态、会话内容与运行时连接句柄继续由原文件保管。

可通过 `node scripts/run-isolated-node-smoke.mjs scripts/smoke-session-index.mjs` 验证重建。夹具让独立进程在写好 JSON 后立即退出，再启动索引；另在 SQLite 写锁被占用期间持续写真实输出记录并读取会话列表，以 p99 小于 10ms 为验收门槛。

### 4.4 迁移与降级

- **首次启动 0.12**：补建 `sessions`；从 `task-inbox/v1.json` 导入 `tasks`。旧文件不删除、不改名。
- **镜像（降级兼容）**：存储线程维护两个用途不同的文件：
  - `v1.json`：变化后按 30 秒窗口合并写入，正常关闭时刷新。**只写投影独有的记录**，即来源已经不再提供、只能靠投影保留的记录，例如观察器已消失的外部会话（`task-inbox-store.test.ts:106` 覆盖的场景）。记录的状态和内容与 0.12 一致；
  - `task-inbox/user-state.json`：用户意图在确认本次操作时写入镜像。0.11 忽略这个文件，再次升级时恢复已保存的选择。
- **降级到 0.11**：会话和草稿不受影响，因为事实来源没变。任务中心读 `v1.json` 镜像。0.11 会重新读取各任务来源，隐藏或删除过的任务可能再出现。返回 0.12 后，仍在同一数据根的意图记录重新生效。
- **降级验收**（评审第 2 条）：在 0.12 期间新建一条**草稿**和一条**外部会话任务**，降级到 0.11 后实际检查两者都能看到、能打开。 [macOS arm64 安装包实测记录](evidence/l4-downgrade-macos-arm64.json)覆盖 0.12.0-rc.1 到 0.11.0-rc.7，旧版从会话管理打开外部任务并显示原转录。

### 4.5 用户意图的持久化

同一数据根的意图版本由 `task_user_state` 和 `task-inbox/user-state.json` 共同维护。存储线程在镜像文件锁内检查版本、提交数据库事务并原子替换镜像，完成后才确认请求。若在 SQL 提交和镜像替换之间退出，下次初始化会按版本补齐；数据库重建时从现存镜像导入。JSON 模式把投影和意图一起保存在这个文件中，SQLite 恢复后再导入。共用 Electron 档案的其他会话数据根各有独立镜像目录。[镜像、恢复和关闭](../../packages/desktop/src/main/task-inbox/task-projection-storage.ts)

## 5. 任务中心

### 5.1 冷热与终态是两件事

| 概念     | 取值                                                                                               | 决定什么                                                   |
| -------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **层级** | 热区：`queued`、`running`、`waiting`；冷区：`done`、`failed`、`cancelled`、`interrupted`、`paused` | 刷新方式：热区每 60 秒核对执行者是否还在；冷区只靠事件驱动 |
| **终态** | `done`、`failed`、`cancelled`（沿用 `isTerminalTaskStatus`）                                       | 可参与「清理已结束」及最近 2000 条终态记录的保留上限      |

`interrupted` 和 `paused` 只参加全量对账和来源事件更新。用户可单项删除已中断任务；暂停任务保留查看和恢复入口。

### 5.2 按变化增量更新

- 任务来源提供 ID 时，`markDirty(source, id)` 将一秒内的重复通知合并。来源适配器每批读取最多 32 个 ID，随后把结果交给同一存储线程按键提交。仅提供来源级通知的适配器重读该来源。
- 会话来源从 Host 分页读取会话索引，单个 ID 可直接查；执行者提供运行、等待及可用操作等实时信息。首次启用、Host 重连和每 10 分钟的兜底检查全量核对已配置来源，每 60 秒核对热区。来源读取失败时保留上次记录并标为过期。
- 全量和增量使用同一函数合并。时间相同时优先保留终态；普通文本输出不会把未改变的会话任务写入投影。[刷新调度](../../packages/desktop/src/main/task-inbox/host-task-inbox-service.ts) · [投影合并](../../packages/desktop/src/main/task-inbox/task-projection.ts)

### 5.3 生命周期与用户意图

**状态流转**（来源投影和用户意图叠加后，决定任务是否可见）：

| 事件                                    | 来源投影    | 用户意图                                                        | 结果                                                                                     |
| --------------------------------------- | ----------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 新任务出现                              | 新增，热区  | —                                                               | 可见                                                                                     |
| 运行结束                                | 热区 → 冷区 | 不变                                                            | 可见，按 `activity_at` 排序                                                              |
| **用户隐藏**                            | 不变        | `hidden_at = now`，原因 `user`                                  | 默认不可见；筛选「已隐藏」时可见。**冻结**：元数据变化不改变它的排序，也不会让它重新出现 |
| **用户永久删除**（仅终态和已中断）      | 删除这一行  | `deleted_at`，并记录删除时的 `source_revision` 和 `activity_at` | 不可见。相同 key 的来源刷新继续忽略该记录，直到收到相应的用户继续操作                    |
| **批量清理**                            | 同上        | 同上                                                            | 清理全部已结束，或仅清理截止时间之前已结束的任务                                                      |
| 会话被归档                              | 不变        | `hidden_at`，原因 `session-archived`                            | 默认不可见；取消归档时自动清除这条隐藏                                                   |
| 会话被删除（目录消失，或带删除标记）    | 删除这一行  | 清除                                                            | 彻底消失                                                                                 |
| **会话重新运行**（同一个 key 回到热区） | 冷区 → 热区 | 见下                                                            | 见下                                                                                     |

**继续会话时的可见性规则**

- 用户主动发送新消息后，清除该会话对应任务卡的隐藏或删除标记。其他任务和历史尝试继续保留原选择。
- 定时任务、Mimi 派发和观察器重连保留原选择。隐藏只改变列表可见性，实际任务继续由原执行者负责。
- 改标题或写备注保留任务排序。取消归档只解除归档引起的隐藏，用户主动隐藏的任务保持隐藏。

### 5.4 活动时间只反映运行

同一 `runId`、同一状态的刷新沿用原 `activity_at`。有新的运行或状态变化时，采用来源的结束或活动时间。手动隐藏和归档隐藏均保存当时的排序时间，直至解除隐藏。

### 5.5 控制命令跟着执行者走（评审第 5 条）

读取任务投影和更新隐藏、删除等意图走 Host 存储。用户执行取消、重试、立即运行等操作时，`TaskInboxActions` 先找到来源适配器，重读任务并核对来源 ID、版本、可用操作和当前窗口权限，再交给已有执行者。任务按键排队，相同的在途操作共用一次执行。来源已消失时，保留记录可以打开，控制命令返回不可用。Host 重连后重新读取投影和来源，已发出的控制命令不会自动重放。[执行路由](../../packages/desktop/src/main/task-inbox/task-inbox-actions.ts) · [工作台验收](../../packages/desktop/scripts/e2e-task-inbox-sources.mjs)

- 策略：直接升到 45，必要时在临时 worktree 里构建中间版本二分定位。

### 8.2 凭据改为异步（H1，单列）

`safeStorage` 的同步接口在 45 废弃、46 删除。难点：

- `EncryptionCipher` 是 core 公开导出的 SDK 接口（`core/src/index.ts:726`）；
- 凭据写入在同步文件锁**内部**完成加密（`credentials/store.ts:361`）。

方案：

- 新增 `AsyncEncryptionCipher`，保留同步接口和现有调用方；
- 凭据存储改为「**锁外加密，锁内写入**」：先在锁外通过反向 RPC 完成加解密，再在存储线程里加锁、核对版本后写入；版本不一致就重来。
- 约束测试：持有文件锁期间不得等待任何跨进程 RPC。

放在 L6，必须在升级到 Electron 46 之前完成。

### 8.4 L1 实施步骤

首轮以第 1–5 步的 PR CI 通过为完成条件。第 6–7 步先在同一候选提交的实包上验收。公开 rc 后复核 rc 通道，正式切换时再复核正式通道。L1 的改动限定在 Desktop 运行时、兼容修复和发布工具链。

1. **锁定依赖。** 首轮使用 `electron@45.4.1`（内置 Node 24.22.3）、`electron-builder@26.18.1`、`@electron/rebuild@4.2.1`、`electron-updater@6.8.12`。Desktop 直接声明所调用的 rebuild，签名 hook 沿 builder 实际解析的 `app-builder-lib`、`@electron/osx-sign`、`@electron/notarize` 核对版本。用仓库固定的 Bun 更新 `bun.lock`，在干净 checkout 验证 frozen install。[Electron 发布记录](https://releases.electronjs.org/release/v45.4.1) · [builder 工具链依赖](https://registry.npmjs.org/app-builder-lib/26.18.1)
2. **固定构建工具链。** Desktop 打包、Electron E2E 和原生验收 job 在安装前配置 Node 24。涉及 `electron/dist` 的步骤先用 Desktop 本地锁定的 Electron 显式下载、核验二进制，覆盖空缓存首次运行；移除失效的 `ELECTRON_SKIP_BINARY_DOWNLOAD`。Core 的 Node 20.10 兼容性矩阵继续运行。重审 DMG/NSIS 冒烟中的 25.1.8 版本断言、NSIS 模板适配和 `packaged-app-layout.mjs` 使用的 builder 私有文件路径，先核对新版命令和模板再更新守卫。
3. **重建并启动 PTY。** `rebuild-native.ts` 目前会因同架构的旧产物而跳过重编，使用 `bunx --bun` 启动工具，失败后仍返回 0。使用 Node 24 执行锁定的本地 CLI。开发安装可以容错，CI 和打包必须按目标 Electron 版本与架构强制重编，失败即退出。检查 mac arm64/x64、Windows x64、Linux x64 的产物，并在对应 Electron 中用包内的 `node-pty` 启动 shell、读回约定文本、确认退出；mac x64 标明 Intel 或 Rosetta 实际执行环境。随包加载 `@napi-rs/canvas` 并走 PDF 解析。
4. **修复 API 和打包配置。** H2 在通知 `show()` 前监听 `failed`，系统投递失败时保留可见的应用内提示。H3 等待剪贴板写入，仅在成功时返回 `codeCopied: true`，失败时仍展示设备码供手输；图片 e2e 改用新的异步读写。H4 从事件对象读取 `level/message/lineNumber/sourceId`，H5 用同一截图样本核对 sRGB 差异。按 8.3 接入更新清单、恢复校验和固定签名识别，覆盖 H7 的允许与拒绝路径。
5. **增加两项 PR CI 检查。**

   - 构建后检查主窗口、浏览器 guest、Panel、Mimi 的四个 `out/preload/*.cjs`。检测未绑定的 `Buffer/setImmediate/clearImmediate` 和 sandbox 无法解析的外部 `require`（可用 `electron`、`electron/renderer`、`electron/common`），允许显式打包的局部实现。复用 sandbox E2E 确认桥接可用。
   - 扩展 `ci.yml` 的 `electron-e2e`。使用隔离 HOME 和本地 fixture，实际启动 agent worker 并完成一次 RPC，经 Desktop Web 的 Panel 路由唤起 headless worker 并收到响应，通过 CUA MCP stdio 代理完成一次初始化。记录子进程的 Electron/Node 版本并验证限时退出。Web 路由在 Main，worker 和 CUA 代理使用 `ELECTRON_RUN_AS_NODE=1`，原生 CUA 驱动另在第 7 步验收。

6. **三平台打包冒烟。** 对同一 SHA 运行 `release.yml` 的无标签手动构建及现有 `desktop-ui-acceptance.yml` 的原生验收，复用 `test:upload-asar`、`test:mobile-asar`、DMG、NSIS 和 AppImage 安装/启动脚本。Windows 覆盖按用户安装与卸载。Linux 另在 Wayland 会话检查 Mimi 等无边框窗口，记录与 CI 的 X11 结果。[原生验收工作流](../../.github/workflows/desktop-ui-acceptance.yml)
7. **mac 真机验收。** 在当前 Mac（15.6.1、arm64）运行候选签名包并按 8.3 复核本机升级路径。记录本机系统与 Darwin 版本、架构、起点签名、候选 SHA 和逐项结果。12、13.4.x、13.5 的系统边界用旧客户端自动回放验收。

   在支持系统的独立测试账户中，只使用自建窗口、页面和凭据，完成以下操作：

   - 触发一次后台任务完成通知。允许通知时须收到系统通知；在已有投递失败条件的测试环境中，回到应用须能看到对应任务的提示。
   - 分别从 Panel 和云端工作台捕获带有不同测试字样的窗口，核对返回图像能读出所选窗口的字样。
   - 让原生 CUA 助手在自建测试窗口输入一段约定文字并读回。随后在浏览器面板打开本地测试页、导航并执行一次截图，核对页面内容。
   - 从旧版本写入一条测试凭据。升级并重启后，用它完成一次受控的测试操作，回执只记成功或失败。账号、凭据值和屏幕里的非测试内容不进入验收记录。
8. **回退。** L1 按依赖/锁文件、API 修复、发布保护和 CI 分组提交。集成期间可成组 revert，重跑旧运行时基线；要定位引入回归的大版本，用 39 或 42 的临时构建二分。公开候选出现问题时停止推广，以更高的 rc 序号或正式补丁发修复包；对已安装用户另验数据可读及恢复路径。

## 11. 风险

| 风险                                           | 缓解                                                                             |
| ---------------------------------------------- | -------------------------------------------------------------------------------- |
| IPC 面大（约 480 个通道）                      | 路由表按功能域切换；接口形状不变；每个功能域可以单独回退                         |

## 12. 与第 16 章的关系

- **Desktop 宿主。** 第 16 章 §10 第 2 条在 0.12 落实为 App 管理的 utilityProcess。工作台在各自的文档端口握手，Host 管理 worker、执行者及存储线程。原生窗口、系统钥匙环、通知投递和显式退出由 Main 处理。独立于 App 运行的本机守护进程仍是第 16 章 §3.3 的后续选项。
- **输出与审批续传。** L5 已接入第 16 章 §4.3 的两条 Desktop 路径。工作台按 journal cursor 补读遗漏的输出；待审批状态按 epoch 和 stateVersion 重新获取，过期审批不能执行。真实工作台重载覆盖漏读输出和待答问题的恢复。平台首版第 8b 项仍负责通用回放缓存去重，第 11 项仍负责跨客户端的 AgentServer v2 契约。[原生续传验收](../../packages/desktop/scripts/e2e-desktop-host-stream.mjs) · [待审批状态](../../packages/desktop/src/main/desktop-host/approval-state.ts)
- **平台边界。** L2–L6 实现窗口关闭后 Host 常驻、重新开窗握手，以及工作台、手机和本地执行者共用会话数据。平台首版 S2-C 仍负责连接时防休眠与相应在线交付。Desktop 的已迁领域和各批次其余工作分别见[第 16 章](16-platform-consolidation.md)和[平台首版实施与验收](../todo/platform-first-version-plan.md)。

## 14. 0.12 采用的决策

1. Desktop 采用 App 内管理的 utilityProcess。L2 建立工作台端口，L5 迁入 worker 并接入两类续传，通用回放缓存去重另见第 12 节。
2. 整包最低支持 macOS 13.5（Darwin 22.6.0）。旧系统留在 0.11。本轮 macOS 实机为 15.6.1 arm64，更新下限按 8.3 由旧客户端回放验证。
3. 0.12 从 main 开集成分支。0.11 维持原存储与运行路径。
4. 每个会话数据根使用独立数据库和任务意图镜像。SQLite 不可用时按 4.4–4.5 使用原文件和 JSON。
5. 终态保留上限为 2000 条，包括完成、失败、取消。被中断和暂停的任务保留；用户可明确删除一条已中断的任务。
6. 用户主动继续会话时，其任务卡可重新出现；后台运行和元数据变化保留之前的隐藏、删除选择。归档隐藏和手动隐藏分别处理（5.3）。
7. 回到 0.11 后，会话、转录和目录草稿继续使用原文件。旧版可能重新显示隐藏或删除的任务。用户保留同一份数据再升到 0.12 时，已保存的意图重新生效。[降级记录](evidence/l4-downgrade-macos-arm64.json)

# Claude Code 全仓持续优化设计

**日期：** 2026-08-30  
**状态：** 已批准（用户连续指示“继续”，授权自主推进）

## 1. 目标

在 Claude Code 本轮 7 日额度刷新前，持续为 CodeShell 完成高价值、可独立验收的优化批次。每一批都必须形成完整闭环，不能为了覆盖“整个仓库”而留下半成品。

本轮的“全仓优化”指对整个 monorepo 开放候选范围，而不是一次性重写所有包。Claude Code 可以审计全部 11 个包，但每次只实施一个有证据支持的改动。

## 2. 优先级

按以下顺序选择工作：

1. 可复现或有静态证据的可靠性、安全、并发与数据一致性问题；
2. 用户可感知的性能问题；
3. 发布、构建、测试与开发者体验中的真实缺口；
4. `TODO.md` 中范围清晰、可在单批完成的产品化 follow-up；
5. 测试缺口。

不实施纯格式调整、无证据的预防式重构、与当前问题无关的大规模架构改写，或依赖外部真机/真 token 才能验证的项目。

## 3. 执行模型

采用串行“小批次闭环”：

1. **审计：** 从代码、测试、近期提交、现有架构文档和 `TODO.md` 找到具体证据；
2. **选题：** 只选择一个可在单个 Claude Code session 完成的事项；
3. **TDD：** 先补可失败的回归测试，再做最小实现；
4. **定向验证：** 运行受影响测试与类型检查；
5. **全仓守门：** 阶段末运行 `bun test`、`bun run typecheck`、`bun run lint` 和必要构建；
6. **复审：** 检查 diff 是否越界、是否引入兼容或安全风险；
7. **提交：** 每批一个 Conventional Commit，之后再开始下一批。

禁止并发修改相同文件。后一批必须在前一批结束并验证后才能开始。

## 4. 工作区隔离

所有 Claude Code 写操作在独立 git worktree/分支完成。主工作区以下用户改动为禁区：

- `packages/desktop/src/renderer/AppQuickChat.test.tsx`
- `packages/desktop/src/renderer/cc-room/CCConversationView.test.tsx`

不得暂存、覆盖、恢复或复制这些未提交修改。不得向远端 push，也不得自动合并回 `main`。

设计文档允许在主工作区单独提交，但提交必须显式限定该文档路径。

## 5. 批次准入与验收

一个候选事项只有同时满足以下条件才能进入实施：

- 有文件、行号、失败测试、日志或明确契约作为证据；
- 用户影响或维护收益清晰；
- 修改范围有界，不依赖另一个未设计的大功能；
- 能增加或更新自动化测试；
- 不破坏 core/public/internal、capability package 和 host 的既有边界。

每批完成标准：

- 回归测试在修复前能说明问题、修复后通过；
- 受影响测试、类型检查和 lint 通过；
- 无意外修改；
- 有独立 commit 和简洁变更说明。

若全量门禁暴露与该批无关的既有失败，必须记录证据并区分，不得通过跳过检查或放宽断言掩盖。

## 6. 停止条件

- 以 Claude Code 7 日额度刷新为“停止新增批次”的边界；
- 到达边界时，不再启动新事项；
- 已开始的批次必须完整验证、提交或安全回退，不能停在半成品；
- 若提前没有满足准入条件的高价值候选，则停止实施并提交审计报告；
- 最终交付包括 worktree/分支、commit 清单、各批测试证据、剩余候选和集成建议。

## 7. 风险控制

- 大范围审计与写操作分开；审计可以覆盖全仓，写操作保持单批最小化；
- 不使用 `git reset --hard`、`git clean`、强推或绕过 hooks；
- 遇到失败先定位根因，不把既有测试改弱来换取绿色；
- 发现高风险安全问题时优先收口，但不在没有授权的情况下操作外部系统；
- 额度刷新不是牺牲质量的理由，宁可少完成一批，也不留下无法验证的改动。

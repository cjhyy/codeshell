## 0. 结论与顺序

本文不记录本机的花费金额和用量，只保留比例；要看绝对数字，在本机重跑基线脚本。

最近一周的调用里，输入 token 的缓存命中率是 76.5%。这一周跨了两种缓存行为，要分开看：

- **0.10.0 之前**：每发一条新消息，整个上下文几乎从头付费。新 run 的第一次请求对上一次请求的复用率只有 6.6%。这部分在 0.10.0 已经修掉大半。
- **0.10.0 之后（现在的 main）**：样本只有几天。损失占主循环输入的 16.8%，按大小依次是 run 中间的回溯改写（33%）、会话或升级后的第一次请求（20%，含一次性的策略切换）、间隔超过 30 分钟的冷启动（19%）、只有系统提示词变了的头部变化（16%）。

按现在 main 的行为粗估，同样的用量：已合入的工具冻结加上 #363，花费降到现在的约 69%；再解决"只有系统提示词变了"和空闲过期两项，约 53%；所有输入都读缓存的下限约 34%。再往下要靠控制上下文体积。这些是小样本上的估算，不是承诺。

钱不在 Mimi 自己身上：工作会话主循环（含 Mimi 派出的）占 84%，零命中的辅助摘要占 12%，Mimi 自己的回合占 2%。做 Mimi 的理由是正确性（现在的发布候选里她会缺工具）和以后的量（主动提醒、IM 用量上来之后），不是今天的账单。

| 步骤    | 做什么                                                                         | 主要结果                                                  | 依赖             |
| ------- | ------------------------------------------------------------------------------ | --------------------------------------------------------- | ---------------- |
| 第 0 步 | 基线脚本入库；修 Mimi 缺工具；修记账；合入 #363                                | 有可复现的数字；rc 可用；回溯改写和辅助摘要两块损失有着落 | —                |
| 第 1 步 | core：每个 Engine 按自己的 preset 得到能力；输入分成会话级、慢变、每轮三类     | 头部只由 preset 和会话决定，有测试守着                    | 建议在 #363 之后 |
| 第 2 步 | preset 成为唯一的能力选择：删隐式注入、扩展声明、依赖校验、按 preset 的 golden | 新增一个没被选中的能力，任何会话都不变                    | 第 1 步          |
| 第 3 步 | 用组装重建 Mimi：一条声明、自己的提示词、工具定义静态、世界状态进账本          | Mimi 任何来源的回合头部相同；世界状态只发增量             | 第 2 步、#363    |
| 第 4 步 | #363 之后剩下的损失源，先复测再按金额排序；护栏                                | 可修复的损失占主循环输入从约 10% 降到 2% 以下             | #363             |

## 1. 基线

数据来自本机引擎日志和调用追踪。脚本只输出汇总，不读正文。全部是 `openai/gpt-6.1-sol`。价格取应用里的价格快照（每百万 token：输入 $2、缓存读取 $0.2、输出 $10），其中缓存读取价是按"输入 × 0.1"估的，不计缓存写入溢价。

### 1.1 钱花在哪（最近一周）

| 类别                                                  | 占花费 | 占输入 | 命中率 |
| ----------------------------------------------------- | ------ | ------ | ------ |
| 工作会话主循环                                        | 52.4%  | 59.4%  | 80.3%  |
| Mimi 派出的工作会话主循环                             | 31.5%  | 34.1%  | 79.0%  |
| 辅助摘要（记忆提取、会话摘要）                        | 12.3%  | 3.7%   | 0.2%   |
| Mimi 自己的回合                                       | 2.3%   | 1.9%   | 70.6%  |
| 子代理                                                | 0.9%   | 0.8%   | 76.1%  |
| 其他（Goal 判断、工具摘要、会话跟进、标题、手动压缩） | 0.7%   | 0.2%   | 0%     |
| 合计                                                  | 100%   | 100%   | 76.5%  |

- 所有输入都读缓存时，花费的下限是现在的约 34%。应用自己对同一批调用的估算比这里高约 18%：它给所有模型套用了"写入加价 25%"，OpenAI 系线路没有这项加价。
- 主循环输入的 88% 来自上下文超过 15 万 token 的请求。
- Mimi 在桌面主进程里发起的几种辅助调用（提醒回复解读、晨报成文、心跳判断等）没有进用量账本，这张表里没有它们（见 0.2）。

### 1.2 没命中的原因（主循环，按缓存策略分期）

相邻两次请求里，上一次的整个输入本该是下一次的前缀。损失 = 本该读缓存、实际按原价付的 token。每笔损失归到第一个符合的原因：会话里这种策略的第一次请求；间隔超过保留期算"冷"；头部指纹变了；run 的第一次请求；其余算 run 中间。

| 原因                                   | 0.10.0 之前（`openai-implicit`） | 0.10.0 起（`openai-hybrid`，样本小） |
| -------------------------------------- | -------------------------------- | ------------------------------------ |
| 命中率                                 | 78.8%                            | 80.9%                                |
| 损失占输入                             | 20.5%                            | 16.8%                                |
| 冷：间隔超过保留期（5 分钟 / 30 分钟） | 42.1%                            | 18.6%                                |
| 新 run 的第一次请求                    | 32.4%                            | 4.6%                                 |
| run 中间                               | 12.5%                            | 33.1%                                |
| 头部：只有工具表变了                   | 8.7%                             | 3.4%                                 |
| 头部：只有系统提示词变了               | 1.1%                             | 16.4%                                |
| 头部：两者都变                         | 1.2%                             | 3.9%                                 |
| 会话（或升级后）的第一次请求           | 2.0%                             | 20.1%                                |

（第三行起的百分比是占该时期损失的比例。）

读这张表：

- **0.10.0 之前**，新 run 的第一次请求即使在保留期内、头部没变，对上一次请求的复用率也只有 6.6%：上一个 run 的动态上下文一拿走，能接着读的存档点只剩系统提示词末尾。0.10.0 起主线会记住上一个 run 的稳定边界（`core/llm/prompt-cache.ts:161-168`），同一口径的复用率是 80.9%（样本很小）。#363 的账本要补的是剩下的这一段。
- **run 中间的损失现在最大。** 典型的一次：旧浏览器快照折叠或重复读取去重省下几百 token，却让其后几十万 token 的缓存全部失效。
- **"第一次请求"在 0.10.0 之后占 20%**，其中有升级后策略切换的一次性影响，不代表常态。
- **只有系统提示词变了的那部分还没有找到来源**，其中约四分之三发生在 Mimi 派出的工作会话上。见 4.2。
- **只有工具表变了**在 0.10.0 之前占损失的 8.7%，包括 `ToolSearch` 往顶部加工具、资格变化和按任务路由。工具冻结是 0.11.0-rc.1 进来的；之后的少量样本里没有再出现头部变化。
- **Mimi 自己**的损失里，头部变化占 56%，冷启动占 31%。她有三分之一以上的回合与上一个回合相隔超过 30 分钟。

### 1.3 各项措施对应到哪一块

以 0.10.0 之后的占比为准（占主循环输入的百分比）：

| 损失                               | 占输入 | 对应措施                         |
| ---------------------------------- | ------ | -------------------------------- |
| run 中间的回溯改写                 | 5.6%   | #363 改写攒批                    |
| 新 run 的第一次请求                | 0.8%   | #363 账本                        |
| 工具表变了（含和系统提示词一起变） | 1.3%   | 工具冻结（已在 main）            |
| 只有系统提示词变了                 | 2.8%   | 先找到来源（4.2）                |
| 冷启动                             | 3.1%   | 保留期（4.3）                    |
| 第一次请求                         | 3.4%   | 基本不可避免；升级切换是一次性的 |
| 新增的末尾                         | 1.9%   | 不可避免                         |

粗估方法：主循环每百万输入 token 的成本现在约 $0.54（19.1% 按 $2、80.9% 按 $0.2）。前三项修掉后命中率约 88.6%，约 $0.41；再加后两项约 94.5%，约 $0.30；下限 $0.20。套到 1.1 的构成上，再假设 #363 让辅助摘要的命中率到 75%，总花费是现在的约 69%，再加后两项约 53%。

### 1.4 局限

- 0.10.0 之后的样本只有几天、少数几个会话，其中一个大会话占了很大比重。第 0 步做完后要重采一周干净的数据，再定第 4 步的顺序。
- 日志里的头部指纹是每个进程一把随机密钥算出来的（`core/engine/prompt-cache-diagnostics.ts:4`），跨进程重启不可比。重启通常落在"冷"里；保留期内的重启会让全部指纹一起变，脚本把它单列一类，这个样本里没有出现。
- 指纹不包含首条用户上下文（指令文件和日期），指令文件被改写造成的损失会落在"新 run 的第一次请求"或"run 中间"里。
- 一部分较早的主循环请求日志里没有模型信息，没有计入。
- 文中另有几处是直接看会话记录得到的观察，不在脚本输出里：回溯改写的那个例子、Mimi 会话里存着的旧工具名单、`NotifyMe` 第 7 分钟才被调用的那次实测、Mimi 派活集中在少数几个会话上。
- 脚本的输出含本机的用量和花费，不入库。

## 2. 共同遵守的模型

缓存部分沿用[缓存模型](../../todo/prompt-cache-optimization.md)的定义，不另起一套：

- 请求分三层：**头部**（工具表、系统提示词、首条用户上下文）、**账本**（只在末尾追加的历史和宿主注入的上下文）、**末尾**（本次请求新增的内容）。
- 五条规则：发出去的不动；变化用追加表达；改写要攒批；断点放在定型线上；每次断开都要能归因。

组装给它补一个分类和三条规则。进入请求的每一个输入都属于下面三类之一：

| 类别       | 例子                                                                                    | 可以影响什么                                         |
| ---------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 会话级事实 | 会话 id 与种类、preset、行为档、宿主、工作区、是不是子代理、宿主接了哪些服务            | 头部                                                 |
| 慢变状态   | 有没有 Goal、计划模式、MCP 连接、可用的代理类型与凭据清单、通过 `ToolSearch` 发现的工具 | 只在缓存周期的边界进入头部；周期内只影响调用时的资格 |
| 每轮事实   | 消息从哪来、是不是主人、这一轮允许哪些宿主动作、此刻的世界状态、这条消息的文本          | 不能影响头部                                         |

6. **头部只由 preset、会话级事实和周期边界上的慢变状态决定。** 唯一的例外是现有的"首个 run 按任务文本选初始工具"：它只在会话第一次运行时发生一次，结果落盘后就是会话级的。
7. **每轮事实只走三条路：**
   - 账本段：会持续到被更新的状态，按差异追加；
   - 这一轮的上下文事件：只属于这一轮的事件，由宿主写入、带标记，不放进用户消息正文；
   - 调用时的校验：权限。

8. **工具渐进式追加。** 周期内新出现的工具不改头部：定义追加在末尾，经 `CallTool` 调用，到冷边界再并入顶部。工具表只在冷边界变。

## 3. 第 0 步：先量、先修、先合

### 0.1 基线入库

`docs/todo/prompt-cache-baseline-20261116/cache_baseline.py` 输出四张表：按用途的花费；按缓存策略分期的损失归因；复用率；Mimi 回合的间隔与步数。每一步合入、跑过几天真实使用后在本机重跑，和上一次的比例对比。输出含本机的用量和花费，不入库。

### 0.2 记账修正

1. **缓存价格按线路给。** 现在所有模型都按"缓存读取 = 输入 × 0.1、缓存写入 = 输入 × 1.25"估（`core/data/model-metadata.ts:78-80`、`core/cost-ledger/pricing.ts:13-24`、`core/cost-tracker.ts:18-33`）。OpenAI 系线路没有写入加价，应用里的成本估算因此偏高约 18%；读取价也应该取供应商的真实价格。#363 的"改写值不值"判断应该用同一张表，而不是固定阈值。
2. **Mimi 在主进程里的辅助调用要有归属。** 待跟进摘要、段落收尾、提醒回复解读、晨报成文、心跳判断直接调用模型，主进程里没有用量归属，`recordOwnedUsage` 会静默丢掉（`core/cost-ledger/context.ts:120-121`）；`desktop/main/pet/pet-notice-reply-models.ts:63` 也不进追踪。需要给主进程一个用量归属，并把这些调用接进追踪，加用途标记。
3. **损失归因落盘**（在 #363 之后做，它重写了诊断模块）。把 `engine.cache_read_drop` 的原因和损失 token 数写进用量回执。同时做两处补强：指纹密钥按会话保存，让同一会话跨重启可比；首条用户上下文和系统提示词的各个段单独出指纹，才能回答"是哪一段变了"。

### 0.3 热修复：没有 `ToolSearch` 的冻结工具面（建议随 rc.3）

工具前缀冻结假定"顶部工具定下来之后，其余工具可以用 `ToolSearch` 发现"。Mimi 的允许清单里没有 `ToolSearch`。下面四点都已在代码里确认：

| 问题                                                          | 位置                                                                                 | 后果                                                                                                                                                       |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 冻结的工具名只在第一次选定，之后只会加上 `ToolSearch` 发现的  | `core/tool-system/run-tool-surface.ts:186-195`、`core/engine/tool-cache-cycle.ts:37` | 升级前建的 Mimi 会话存着旧的工具名单，`Notices`、`Triggers`、`ManageTrigger`、`NotificationSettings` 永远进不了工具表                                      |
| 有资格但不在冻结表里的工具，执行器拒绝并提示"先 `ToolSearch`" | `core/tool-system/executor.ts:403-420`                                               | Mimi 没有 `ToolSearch`，这条提示做不到                                                                                                                     |
| 冻结的是周期第一个 run 当时可见的工具，之后当成完整快照       | `core/tool-system/run-tool-surface.ts:205-219`                                       | 周期由哪个回合在冷边界上开启，决定了之后她有哪些工具。任务收尾回合开启的周期只有 8 个工具；桌面回合开启的周期没有 `GatewayReply`，接下来的 IM 回合没法回复 |
| 冻结的是当时改写过的定义                                      | `pet/delegate-work.ts:98-104`                                                        | 模型看到的工作区和会话清单、参数枚举停在周期开始那一刻：周期内新出现的不在枚举里，已经不存在的还列着                                                       |

启动回执回合（`toolAllowlist: []`）紧跟在主回合之后运行，周期是热的，不会改动已有快照；只有恰好在那一刻变冷才会冻结出一张空表，概率很低。

修法只作用于目录里没有 `ToolSearch` 的工具面，第 3 步完成后删除：

1. **`RunToolSurface`**：
   - 每个冷边界（首次选定、周期过期后的重定基、`rebase()`、没有目录时的 `rebaseToolSelection`），顶部名单 = 已有名单 ∪ 当前有资格的工具，只增不减；
   - 周期中途才有资格的工具不改工具表（渐进式追加）：宿主把它的完整定义作为一条消息追加到末尾，模型用 `CallTool` 或直接用工具名调用。这条通路 `ToolSearch` 的发现已经在用，这里只是改由宿主发起。到下一个冷边界再并入顶部，缓存不断；
   - `lastRequestAt` 照常保存。
   - 要改的测试：`run-tool-surface.test.ts:119-132`、`:489-502` 的断言与新规则相反，限定到有 `ToolSearch` 的情况。
2. **pet**：`DelegateWork` 和 `SendMessage` 的定义改成静态的，不带枚举和清单。清单已经在 `<pet-world>` 的 `workspaces`、`reusableSessions`、`outboundTargets` 里，描述指向它们，参数继续由宿主在调用时校验。`GatewayReply` 的改写里有渠道的长度上限、附件种类与上限、按钮模式（`pet/host-actions.ts:341-375`），世界状态里没有这些，留到第 3 步。要改的是五个测试文件里对枚举的断言：`pet/delegate-work.test.ts`、`pet/atomic-manager-tools.test.ts`、`pet/external-manager-catalog.test.ts`、`pet/engine.chat-replay.test.ts`、`tests/mimi-chat-replay.test.ts`。

### 0.4 合入 #363

#363 已经实现。它自己的记录是：本机 44 个测试分区里 19 个通过，合入前要求在最终提交上拿到 CI 全绿；它引用的线上数字采于收尾修复之前。它解决的是：

- 动态上下文改成本地持久的账本，只追加变化，补上 run 首次请求剩下的那段损失。
- 回溯改写先登记，只在缓存已冷、划算或有压力时一次做完。这是现在最大的一块（1.3）。
- 记忆提取、会话摘要、写入决策三种辅助调用有了独立的缓存范围和稳定分段。辅助摘要现在是 0% 命中，占花费的 12%。

两件事要和它一起处理：

1. **易变消息上的断点。** #363 分支在 `openai-hybrid` 和 `anthropic-explicit` 线路上，每个模型步骤前把行为档的易变上下文挪到末尾（`core/engine/turn-loop.ts:666-674`）。Anthropic 的滚动断点因此落在易变消息上（`core/llm/providers/anthropic-discovery-wire.ts:156-160`），每步按写入价付一次、从不读取。滚动断点应该放在它前面一条消息上。
2. **Mimi 的世界状态会变贵一点。** main 上世界状态每个回合只按原价发一次，回合内后续步骤读缓存；#363 之后是每个步骤发一次。Mimi 一个回合通常有两三步、世界状态上限 32,768 字符，按现在的用量多出来的花费可以忽略，但方向是反的，所以第 3 步的 P3-b 不要拖。

建议先合 #363 再开始第 1 步：它改了 `core/engine/` 下 66 个文件，第 1 步也要动 `engine.ts` 的构造和 `run-tooling.ts`，晚合的一方要做一次大变基。第 1、2 步本身不依赖账本，#363 拖得久的话可以先做。

## 4. 第 1 步：core 改造

目的：让"这个 Engine 有哪些能力"由它自己的 preset 决定；把输入按第 2 节的三类分开，并用测试守住头部。这一步不改任何 preset 的内容。

### 现状

1. **工具成员由 worker 的种子 preset 决定。** `core/engine/engine.ts:729-745` 在有 `config.runtime?.toolRegistry` 时直接用它，自己的 preset 和启用/禁用清单都不参与。桌面 worker 启动时用默认 preset 建一个种子 Engine，所有会话共享它的注册表（`core/cli/agent-server-stdio.ts:194-244`）。会话自己的 preset 只影响提示词段、初始工具和权限规则。
2. **种子还带进来两处泄漏。** 种子按 worker 启动目录读项目的内置工具开关，烘焙进所有项目共享的注册表；worker 启动之后改 `agent.enabledBuiltinTools` 不生效。
3. **热重载丢权限规则。** `refreshRuntimeConfig`（`core/engine/engine.ts:3983-4041`）换 preset 时不重新合并隐式注入工具的默认权限规则，例如 pet 的 `DelegateWork` 允许规则。
4. **hooks 和上下文提供者不看 preset。** 模块 hook 在每个 Engine 上注册（`core/engine/engine.ts:782-784`），提供者全部运行、各自用 `preset.name` 自行过滤。hook 负载里没有会话种类、preset 和行为档；`pre_tool_use` / `post_tool_use` 连 `sessionId` 都没有。
5. **每轮输入能进头部。** `ToolVisibilityContext.profileMeta` 来自 `profile.buildVisibilityMeta(profileParams)`（`core/engine/engine.ts:3235`），工具的 `availability` 和 `rewriteDefinition` 每个 run 都拿到它。core 自己也有两处：`SendMessageToSession` 用一个 run 选项拼参数枚举（`core/tool-system/builtin/send-message-to-session.ts:34-56`）；`applyDynamicToolDef` 把当前的代理类型和凭据清单写进工具描述（`core/tool-system/dynamic-tool-defs.ts:28-46`）。冻结只是把结果定住一个周期。
6. **preset 不落盘。** `SessionState` 没有 preset 字段，每次按当前的设置解析。

### 改动

**1.1 每个 Engine 的能力视图。** Engine 构造时总是按自己的 preset 计算工具名单（`resolveToolNamesForPreset`），再从共享注册表得到只含这些名字的视图（给 `fork()` 加过滤，或用共享目录新建）。共享的只有定义和执行器。种子不再解析 preset。会话工厂把设置里的启用/禁用清单传下去，项目开关按会话自己的工作目录读。`MCPManager` 持有种子注册表的用途要先核对（未验证）。

**1.2 运行时换 preset。** 设置或数字人切换让一个运行中会话的 preset 变了：重建能力视图，并开始一个新的缓存周期。不再出现"提示词换了、工具没换、权限规则丢了"的中间状态。

**1.3 preset 的来源与落盘。** 优先级不变：run 请求里显式给的 → 设置和数字人（`core/engine/disk-defaults.ts:63`、`core/profile/activation.ts:98`）→ 组合的默认值。只有创建会话时显式指定的 preset 才写进 `SessionState` 并一直沿用；跟随默认值的会话继续跟随，默认值变了算一次头部变化。新字段要做成旧版本读到不报错、不清空。

**1.4 输入分类。** 引入两个类型，并把现有的可见性输入逐个归类：

```ts
/** 整个会话里不变。头部的一切只读它。 */
interface SessionFacts {
  sessionId: string;
  rootSessionId?: string;
  kind: string; // "work" | "pet" | …
  preset: string;
  profileId?: string;
  host: BuiltinToolHost;
  isSubAgent: boolean;
  cwd: string;
  workspace: WorkspaceContext;
  settingsScope: SettingsScope;
  hostServices: ReadonlySet<string>; // 宿主接了哪些服务
}

/** 只属于这一轮。只给上下文提供者、进程内的模块 hook、执行器和 run 服务。 */
interface RunFacts {
  runId: string;
  params: Record<string, unknown>; // 即现有的 profileParams
  injected: boolean;
}
```

| 现有输入                                                                                | 归类   | 处理                                                                                            |
| --------------------------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------------- |
| `cwd`、`workspace`、`host`、`isSubAgent`、`rootSessionId`、`settingsScope`、`sessionId` | 会话级 | 进 `SessionFacts`                                                                               |
| `behaviorProfile`                                                                       | 会话级 | 同一个会话的 run 不能换行为档，加校验。快速聊天是分叉出的新会话，隔离任务是临时会话，本来就不换 |
| `hasGoal`、计划模式、MCP 连接、`hasBrowserAutomation`                                   | 慢变   | 沿用冻结方案：周期内只影响调用时的资格                                                          |
| `applyDynamicToolDef` 读的代理类型和凭据清单                                            | 慢变   | 只在周期边界刷新进头部                                                                          |
| `sessionMessageTargets`（`SendMessageToSession` 的枚举）                                | 每轮   | 去掉枚举，目标清单进账本段，调用时校验                                                          |
| `profileMeta`（目前只有 pet 用）                                                        | 每轮   | 旧通路保留到 P3-a，pet 迁完后删除                                                               |

工具的 `availability`、`rewriteDefinition` 和提示词段最终只收到 `SessionFacts` 和周期边界上的慢变状态。`profileMeta` 这条旧通路删掉之后（P3-a），在类型上就写不出"按每轮输入改工具定义"的代码。在那之前靠头部守卫测试。

**1.5 hook 与上下文提供者拿到身份。** 所有 hook 的负载统一带上 `{ sessionId, sessionKind, preset, profileId, isSubAgent }`。每轮输入（`RunFacts.params`）只给进程内的模块 hook 和上下文提供者：设置和插件里配的 shell hook 会从标准输入拿到整个负载（`core/hooks/shell-runner.ts:6-8`），不能把 Mimi 的世界状态这类内容交给它们。

**1.6 上下文提供者可以返回带条目的段**（在 #363 之后）。#363 的账本支持整段、按条目、只比成员、只在快照里出现几种比较方式，模块的提供者现在只能用整段和只在快照里两种（#363 分支的 `core/prompt/capability-context.ts:32-58`）。放开为可以返回完整的 `ContextSection`，键加模块前缀。

**1.7 冻结的种子不取决于某一个 run。** 冷边界上顶部名单仍然是"已保存的名单 ∪ 本周期发现的工具"（冻结方案不变）。变的是两点：没有 `ToolSearch` 的 preset，顶部就是 preset 的全部工具，和哪个 run 开启周期无关；冻结的定义按会话级事实和当时的慢变状态生成，不再取"周期第一个 run 改写过的定义"。周期中途才有资格的工具走渐进式追加（规则 8），有没有 `ToolSearch` 的 preset 都一样。0.3 的热修复规则在这里被取代。

**1.8 头部守卫。** #363 的 `testing/prompt-prefix-guard.ts` 只比较消息序列，看不到工具表和系统提示词（#363 分支的 `core/utils/prompt-prefix-events.ts:36-46`）。头部守卫另做：用假模型记录每次发给 provider 的工具表和系统提示词，断言同一会话、同一周期内逐字节不变。`core/engine/engine.append-only-tools.test.ts` 已经是这个做法，把它抽成各 preset 共用的测试工具。它不依赖 #363。

### 验收

- 同一个 worker 里两个不同 preset 的会话，工具成员不同（现在这条测试会失败）。
- 项目 A 的内置工具开关不影响项目 B 的会话。
- 现有的三个 preset：用不同的每轮输入、切换 Goal 和计划模式、MCP 晚连上，连续跑若干个 run，同一周期内工具表和系统提示词逐字节不变。Mimi 的这条断言在第 3 步才成立。
- `tests/composition-golden.test.ts` 不变；`tests/mimi-chat-replay.test.ts` 与全仓契约、预算测试通过。

### 风险与行为变化

- `engine.ts` 现在 4,755 行，#363 之后是 4,839 行（上限 5,000），新逻辑放新模块。所有导出预算都是零余量（core 135/135、pet 27/27 等），新类型从已有的分组模块或内部入口导出。
- `new Engine(` 的落点有白名单守卫（`scripts/check-no-engine-bypass.sh`），不新增落点。
- 1.1 会改变两类会话拿到的工具，需要主人确认（见第 10 节）：面板的隔离任务被服务端指定为 `general`，数字人激活也会把 preset 定为 `general`，它们今天实际拿到的是种子 `terminal-coding` 的 66 个工具，改完是 `general` 自己的 60 个。项目的内置工具开关不再跨项目生效。

## 5. 第 2 步：preset 组装

目的：preset 是唯一的能力选择。模块只说"我提供什么"，不再有"装了某个模块，所有会话的工具都变了"。

### 2.1 preset 的形状

在现有 `AgentPreset`（`core/preset/index.ts:27-39`）上加四个可选字段，不改已有字段的含义：

```ts
interface AgentPreset {
  name: string;
  label: string;
  description: string;
  promptSections: readonly string[];
  builtinTools: string[]; // 资格：这个 Agent 可能用到的全部工具
  initialToolNames?: readonly string[]; // 冻结的顶部；省略 = 全部在顶部
  initialToolRouting?: TaskToolRoutingPolicy;
  defaultPermissionRules: PermissionRule[];
  // 新增
  hooks?: readonly string[]; // 选中的模块 hook
  contextProviders?: readonly string[]; // 选中的上下文提供者
  profile?: string; // 绑定的行为档
  services?: readonly string[]; // 需要的模块私有服务
}
```

- 行为档只留 Engine 级开关（`maxTurns`、`contextStrategy`、各种 `disable*`）。是否使用指令文件、技能、记忆、MCP、插件 hook 这些来源，继续由行为档的开关表达，不另加一套字段。
- `quickChatRestricted` 和 `isolatedTask` 这两个行为档是叠在任意 preset 上的限制（收紧工具和来源），不绑定 preset，保持现状。
- 会话种类到 preset 的对应不加新字段：行为档已有 `activateForSessionKinds`，绑定该行为档的 preset 就是这种会话用的 preset。编译期校验至多一个 preset 绑定同一个按种类激活的行为档。
- 不做继承图、条件语言和子 preset。

### 2.2 模块贡献怎么生效

| 贡献                                                                     | 现在                                                                                                                          | 之后                                                                                                  |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `tools`                                                                  | 模块没有 preset 时注入所有 preset（`presetInjectedTools()`，`core/composition/resolve-preset.ts:38-43`）                      | 只有被 preset 或扩展声明选中才生效；删 `presetInjectedTools()` 和没有生产模块在用的 `always` 这种贡献 |
| `hooks`、`dynamicContextProviders`                                       | 在每个 Engine 上生效，自己判断 `preset.name`                                                                                  | 有名字，只有被选中才注册、才运行                                                                      |
| `promptSections`                                                         | 按名字被 preset 选                                                                                                            | 不变                                                                                                  |
| `instructionBindings`、`instructionBoundary`                             | 全局生效，会改头部                                                                                                            | 由 preset 选中                                                                                        |
| `fileHistory`、`artifactDetectors`、`sessionWorkspace`、`privateService` | 全局生效                                                                                                                      | 明确声明为 Engine 级，不参与选择                                                                      |
| `adjustToolSelection`                                                    | 按 `{ preset, host }` 增删工具（唯一的生产用例：coding 在桌面上换掉两个 worktree 工具，`coding/index.capability.ts:370-375`） | 保留。它只读会话级事实，不违反规则 6                                                                  |

### 2.3 扩展声明

一个模块想把自己的能力加进别人的 preset（例如 pet 给工作会话加"回报 Mimi"的三个工具），显式声明：

```ts
interface PresetExtension {
  /** 目标：点名的 preset，或除了列出的之外的全部 preset。 */
  target: { presets: string[] } | { allExcept: string[] };
  tools?: string[]; // 只能是本模块自己的工具
  initialTools?: string[]; // 其中放进冻结顶部的
  hooks?: string[];
  contextProviders?: string[];
  promptSections?: string[];
}
```

- 编译期校验：只能加自己的贡献；目标 preset 必须存在；不能重名。结果记进按 preset 的 golden，带上来源模块。
- 宿主的手段仍然是有序的模块清单（`CODE_SHELL_CAPABILITY_MODULES`），不新增宿主 preset 配置。
- **没有 preset、也没有扩展声明的模块**：SDK 调用方今天传一个带工具的模块，工具就能用。为了不要求他们改写，这类模块按"扩展到全部 preset"处理，并在组合快照里记成一条显式的默认扩展。pet 改成显式声明之后，生产模块里不再有走这个默认值的。要不要保留这个默认值需要主人定（见第 10 节）。

### 2.4 依赖声明与校验

- 模块可以声明 `requires: { modules?: string[]; hostServices?: string[] }`。
- 宿主服务指"接上了没有"（例如 IM 网关服务存在），不是"用户配置了没有"（例如还没绑定任何渠道）；后者是调用时的事。worker 不知道主进程接了什么，由宿主在启动 worker 时声明（和 `CODE_SHELL_CAPABILITY_MODULES` 同样的方式）。
- 校验时机：组合编译时只报告哪些 preset 缺依赖，不让整个 worker 起不来；用到那个 preset 创建会话时才失败，错误里列出缺的模块或宿主服务。

### 2.5 一次切换里要包含的迁移

删隐式注入的那个 PR 必须同时做完下面几件，否则 Mimi 会在主线上失去全部工具：

1. `harness-min`（33 个工具）、`general`（60）、`terminal-coding`（66，默认）三个 preset 的内容不变。
2. pet 用扩展声明把三个回报工具（`ReportToMimi`、`NotifyMe`、`RequestMimiDelivery`）加回除 Mimi 之外的 preset。另外 18 个管理工具本来就被可见性挡着，工作会话的模型从没见过。
3. 新增一个**行为等价**的 preset `mimi`：工具是现在 Mimi 实际可用的那些（pet 的管理工具加 core 的 `SaveContextNote`、`NewContext`、`SearchHistory`），提示词段和现在一样，可见性仍走旧通路。Mimi 的几个运行入口显式传 `preset: "mimi"`。提示词和可见性的改动留到第 3 步。

### 2.6 按 preset 的 golden

现有的组合 golden 只记模块级目录。新增一份按 preset 的 golden：每个 preset 的工具资格、冻结顶部、提示词段、hooks、提供者、行为档、服务、扩展来源。它只能有意更新并逐项审阅。每个 preset 接上 1.8 的头部守卫。

### 验收

- 加一个没被任何 preset 选中的测试模块（带工具、hook、提供者，并显式声明不扩展）：所有 preset 的 golden 和头部指纹不变。

## 6. 第 3 步：用组装重建 Mimi

目的：Mimi 的头部不随消息来源变；世界状态只发增量；她的全部能力写在一条声明里。

### 现状

- 提示词：默认 preset `terminal-coding` 的段加上一段人设追加。其中和 Mimi 无关的编码段约 1.9 万字符；人设追加约 2.9 万字符。
- 工具可见性：桌面每个回合按消息来源算出这一轮允许的宿主动作（`desktop/main/pet/pet-dispatch-service.ts:1760-1783`），18 个管理工具里有 17 个的可见性取决于它（`pet/host-actions.ts:252-256` 等）。
- 工具定义：`DelegateWork`、`SendMessage`、`GatewayReply` 每个 run 重写。
- 世界状态 `<pet-world>`：每轮重建的 JSON，上限 32,768 字符，作为易变消息发送。

### 3.1 一条声明，不拆模块

Mimi 只有一个，不把 pet 拆成多个模块。pet 仍是一个模块，贡献一个 preset `mimi`。这个 preset 就是 Mimi 的全部声明：提示词段、工具组、上下文提供者、行为档、需要的宿主服务。core 的装配不认识 Mimi，只按声明装。

工具按组写在 pet 包里，每组一个挂载条件。条件只读会话级事实，所以同一个会话的工具表不随回合变：

| 组                   | 工具                                                                                                       | 挂载条件                              |
| -------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| 本职                 | `CurrentTime`、`Memory`，加 core 的 `SaveContextNote`、`NewContext`、`SearchHistory`                       | 恒挂                                  |
| 派活                 | `DelegateWork`、`Sessions`、`ManageSessions`、`ControlLongTask`、`WatchSession`、`BindConversationSession` | 恒挂                                  |
| IM                   | `Gateway`、`GatewayReply`、`SendMessage`、`MobileRemote`                                                   | 宿主接了 IM 网关                      |
| 提醒                 | `FollowUps`、`ManageFollowUp`、`Notices`、`Triggers`、`ManageTrigger`、`NotificationSettings`              | 宿主接了提醒服务                      |
| 回报（给工作会话用） | `ReportToMimi`、`NotifyMe`、`RequestMimiDelivery`                                                          | 用扩展声明加进除 `mimi` 之外的 preset |

- 每轮的权限不靠挂不挂，靠调用时拒绝（3.4）。工具内部的宿主校验保留：挂载条件将来写错不会报错，只会把能力静默开出去。
- 某一组装配失败只退回其余的组，不带崩本职能力。
- 升级新增的工具、周期中途才接上的宿主服务，走渐进式追加（规则 8），不重建工具表。
- 回报工具和提醒工具现在共用一个观察者闭包（`pet/capability.ts:195-254`），保持为 pet 模块的私有服务。

preset `mimi` 在第 2 步已经有了，这一步换内容：提示词段换成 Mimi 自己的，上下文提供者选上，工具组按上表挂。

回报组把 `NotifyMe` 和 `ReportToMimi` 放进工作会话的冻结顶部：一次实测里，模型查了两次 `ToolSearch`、到第 7 分钟才建上"做完告诉我"的规则，在那之前任务失败是收不到通知的。这是工作会话头部在整个方案里唯一的一处变化。

### 3.2 提示词

原则：系统提示词只放不变的认知，会变的事实都在每轮的上下文里。

- 去掉与 Mimi 无关的编码段（约 1.9 万字符，约 5 千 token）和 git 上下文。
- 人设追加只留三样：她是谁、判断规则（什么时候派活、续接还是新开、什么时候提醒主人）、语气。
- 逐个解释世界状态字段的部分挪走：每个上下文段和每种事件自带一行说明。世界状态的标题现在写的是"non-durable"（`pet/profile.ts:181`），也要改。
- 工作区、会话、渠道这类清单不进提示词，也不进工具定义。
- 每轮上下文按行拼：读不到的那一行整行不出现，不把"读失败"写成"没有"。
- 这一步改了模型看到的指引，验收里要有行为指标（见本节验收）。

### 3.3 工具定义是静态的

- `DelegateWork`、`SendMessage` 在 0.3 已经改成静态的。
- `GatewayReply`：渠道的长度上限、附件种类与上限、按钮模式从定义里挪到来源上下文段（3.5 的 `mimi-source`）。三处拼这段内容的地方都要改：`pet-dispatch-service.ts:1854-1861`、`pet-closure-turn.ts:171-181`、`pet-report-turn.ts:121-127`。
- 校验失败的错误里带上可选的 id 或上限，模型下一步就能改对。

### 3.4 每轮权限在调用时判断

工具始终在工具表里，可见性不再读每轮输入（1.4 的旧通路在这里删除）。这一轮不允许的动作，调用时被拒并说明原因：

- 宿主动作：`createRunServices` 里已有的 `hostActionKinds` 检查保留，名单仍由桌面每轮给出。
- 提醒工具在非主人回合的读和写：保留宿主两端已有的拒绝（`ownerTurnRefusal` 和读取门禁）。
- 这一轮允许什么写进来源上下文段，模型不用靠试。
- 工具描述是通用的静态文字（"只有主人本人可以要求"），不带渠道名和会话名。

这改变了 #356 的一处做法：群聊和非主人回合里，提醒工具从"看不见"变成"看得见、调不动"。看得见的只有静态描述，没有数据；读和写仍然被宿主拒绝。主人已确认（2026-11-16）：保缓存优先。

### 3.5 世界状态的去向

| 现在的字段                                                                                                                                                                                         | 性质                   | 去向                                                                                                                                                                                                         |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `workspaces`、`outboundTargets`、`followUps`、`pending`、`longTasks`、`taskInbox`                                                                                                                  | 真正的集合             | 账本段，按条目比较                                                                                                                                                                                           |
| `sessions`（按最近活跃取前 25）、`reusableSessions`（每个工作区最多 6 个）                                                                                                                         | 滑动窗口               | 账本段，只比成员、窗口有粘性：列出过的会话留到它真的结束，掉出"最近"不算移除。条目里只放稳定的字段（标题、工作区、体积档位）；阶段、运行状态、排队数这些每一步都变的字段不进账本，需要时用 `Sessions` 工具查 |
| `memories`、`memoryWindow`                                                                                                                                                                         | 针对这条消息的检索结果 | 这一轮的上下文事件                                                                                                                                                                                           |
| `currentMessageSource`、`currentMessageCapabilities`（含 `GatewayReply` 的渠道能力）、这一轮允许的宿主动作、`personalization`、`mobileRemote` 的状态                                               | 随来源或设置变         | 账本段 `mimi-source`，整段比较；来源没变就不追加                                                                                                                                                             |
| `hostWake`、`pendingNotices`、`recentProactive`、`inputAttachments`、`carryoverBrief`、`contextAssociation`、`sessionReport`、`completionReceipt`、`continuationPolicy`、`delegationLaunchReceipt` | 只属于这一轮的事件     | 这一轮的上下文事件                                                                                                                                                                                           |
| `observedAt`、`generation` 这类每次都变的字段                                                                                                                                                      | 对决策没用             | 不发；`workerState` 只在异常时进 `mimi-source`                                                                                                                                                               |
| 宿主以后新增的字段                                                                                                                                                                                 | —                      | 必须声明属于哪一类，默认是这一轮的上下文事件                                                                                                                                                                 |

几条规则：

- **这一轮的上下文事件**是宿主写的一条带标记的事件，走 #363 的持久提醒通路，不放进用户消息正文。放进正文有三个问题：IM 里任何人都能在消息里伪造同样的内容；它会出现在聊天界面、手机历史和导出里；它会被当成用户输入喂给段落摘要（`pet-segment-closure-service.ts:61-105` 只跳过带注入标记的用户消息）。事件里的定界符要转义。
- **"没有"和"空"要分开。** 汇报、启动回执这些内部回合今天传 `workspaces: []` 表示"这一轮用不到"。改成账本段之后，这一轮没提供的输入就不产生更新，不能当成"清空"。
- **段由模块的上下文提供者产出**（1.5、1.6 给了它们身份、每轮输入和条目比较），由 preset 选中。桌面只把结构化数据放进每轮输入，不再拼字符串。
- **账本重整**：Mimi 用笔记式上下文，段落切换时账本重新出快照，累积的更新有上限。另外补上 #363 没做的规则：累积更新超过快照的两倍时，在缓存已冷的时刻重出快照。
- 增量到底有多大现在量不出来。P3-b 给基线脚本加一项：每个回合账本更新的 token 数。

落盘和隐私的代价：

- 世界状态从"不落盘"变成"写进本机的 Mimi transcript"。被移除的条目文字会留在 transcript 里；在下一次快照之前，模型仍能看到带"已移除"标记的旧条目。
- 地址和密钥类的内容不进账本：`mobileRemote` 的地址、回复附件的根目录只在调用工具时返回。
- #363 的过滤（`isContextEvent`）把账本和提醒事件排除在导出、桌面与手机的历史显示、外部运行时交接之外。这个过滤在 main 上还没有，所以 P3-b 必须在 #363 之后。Mimi 的 `SearchHistory` 会不会搜到账本事件要在 P3-b 里核对（未验证）。
- 旧版本应用不认识这些事件：降级后旧 TUI 的恢复会把账本消息显示出来（#363 的已知限制）。

### 3.6 各种回合共用一个头部

聊天、收尾、汇报、启动回执、跟进唤醒都在同一个会话、同一个 preset 上跑，区别只在这一轮的上下文事件和每轮输入。启动回执回合不再清空工具表，改为这一轮不允许任何宿主动作。

一条消息今天可以带自己的模型（`command.model`，`pet-dispatch-service.ts:838`）。系统提示词里有模型名，换模型就是换头部。Mimi 的回合统一用管理模型的设置；主人改了设置算一次正常的头部变化。

### 3.7 上下文体积

Mimi 单步的输入通常有几万 token；三分之一以上的回合是冷的，冷启动的代价和这个体积成正比。P3-a 给出一张预算表（头部、账本快照、保留的历史各多少），再决定笔记切换的阈值。这里不先定数字：人设追加本身就有 2.9 万字符。

### 3.8 派活的会话复用

Mimi 派出的工作会话占总花费的三分之一以上，集中在少数几个被反复复用的大会话上，单次请求的上下文普遍有十几万 token。即使全部命中缓存，十几万 token 的会话每一步也比一两万 token 的新会话贵十倍。

"新的事情开新会话、续接要给出依据"的规则已经有了（`pet/profile.ts:56-58`、`pet/delegate-work.ts:27-32`，续接必须带 `session_continuation`）。所以先做调查，不先改规则：读这几个会话里记录下来的续接依据，看它们是真的同一件事，还是规则被绕过了。能确定新增的只有一项：会话清单的条目里给出上下文体积的档位，让"又大又不相干"的复用看得见。

### 3.9 外部运行时上的 Mimi

- 工具目录已经是从允许清单推出来的（`pet/capability.ts:582-588`），改成从 preset `mimi` 推出。
- 外部运行时没有账本，世界状态仍然拼进每条消息。拼的地方（`desktop/main/pet/pet-external-runtime.ts`）改为用同一份结构化输入渲染，不依赖桌面的旧字符串。
- 缓存由外部运行时自己管，不在本方案范围内。

### 3.10 迁移

- `kind: "pet"` 的旧会话由行为档对应到 preset `mimi`。保存的旧工具选择作废一次，按 preset 重新定顶部。
- 第一次运行出一份完整的账本快照。
- `petRuntimeContext` / `petWorkspaces` 两个遗留字段、`PET_ALLOWED_TOOL_NAMES`、带参数的 `buildVisibilityMeta`、行为档的 `runtimeContextPlacement: "dynamic"` 随之删除。`pet-dispatch-service.ts` 现在 2,486 行（上限 2,500），世界拼装和可见性计算移走后会变小；在那之前往里加东西要先拆。

### 验收

- 同一个 Mimi 会话依次跑桌面、IM 私聊、群聊、收尾、汇报、启动回执、跟进唤醒：工具表和系统提示词逐字节相同。
- 群聊回合调用提醒工具被拒，结果里不含任何提醒正文。
- 旧会话升级后 `Notices` 等四个工具可以调用。
- 世界状态不随步骤数重发；缓存还热时，一个回合里未缓存的输入只有新消息、这一轮的上下文事件和账本增量。增量的大小用脚本量出来再定目标。
- 回放集（`tests/mimi-chat-replay.test.ts`）上三项不变差：续接还是新开的判断、被拒绝的工具调用比例、撞到步数上限（6 步）的比例。去掉枚举后 `DelegateWork` 的首次调用成功率不下降。

## 7. 第 4 步：缓存与成本（#363 之后）

第 0 步做完后先重采一周数据，按那时的占比排序。下面是按现在的样本排的。

### 4.1 复测

#363 合入、跑满一周后重跑脚本。看三个数：run 中间的损失还剩多少；run 首次请求的复用率；辅助摘要的命中率。#363 自己的线上数字采于收尾修复之前，以复测为准。

### 4.2 只有系统提示词变了（现在占损失的 16%）

来源未知，其中约四分之三发生在 Mimi 派出的工作会话上。设置里的追加提示词和个性化、数字人指令、会话简介、冻结的技能快照都在系统提示词里，它们变了现在都不登记。0.2 的分段指纹做完之后才能定位；定位之后按规则 2 处理：能追加的改成追加，必须改头部的登记为头部变化。

### 4.3 空闲过期（现在占损失的 19%）

间隔超过保留期的请求必然全价。`openai-hybrid` 请求的是 30 分钟保留期；`anthropic-explicit` 的标记都是 5 分钟，代码里没有请求过 1 小时。

1. **探针先行**：各线路是否接受更长的保留期、怎么计费。接受且没有写入加价的，会话线路默认用最长的。
2. **Anthropic**：头部和稳定历史用 1 小时，滚动断点用 5 分钟。1 小时的写入是 2 倍价，但历史只追加，贵的只是每轮新增的那一小段；换来的是 5 分钟到 1 小时之间回来时整段前缀读缓存而不是重写。
3. **冷恢复**：对又大又冷的会话，全价重读整个上下文只为回答一句追问是最贵的情形。可选的做法是在缓存快过期时趁热做一次摘要存档，冷了以后从存档继续。这会改变"回来以后模型还记得多少"，是产品取舍，默认不开。
4. **不做保活请求**：每 30 分钟读一遍几十万 token 的前缀，一天的花费远超一次冷启动。
5. **重启后的状态**：缓存热度、OpenAI 的读取边界都只在内存里。重启后第一次请求会把待处理的改写当成"已冷"直接执行，即使供应商那边还热。热度可以从已经落盘的 `toolSelection.lastRequestAt` 推出。

### 4.4 辅助调用

| 调用                                          | 现状                                                                                                         | 改法                                                                                                                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 自动压缩的摘要                                | 用主模型，换了系统提示词、不带工具、把截断过的历史序列化成文本（`core/context/compaction.ts:862-885`），全价 | 分两种情况：缓存还热、因为上下文压力触发的，请求用会话自己的前缀、末尾追加总结指令，历史读缓存；缓存已冷的，保持现在的截断序列化。样本期内真实会话没有触发过自动压缩，量上来再做 |
| Goal 判断                                     | 0% 命中；当前时间排在前面                                                                                    | 固定内容在前、时间在最后                                                                                                                                                         |
| 一次性小调用（标题、工具摘要、Mimi 侧的几个） | 太小，不该缓存                                                                                               | Anthropic 线路上没有缓存范围的请求不打标记，免得付 1.25 倍写入却从不读取                                                                                                         |
| 快速聊天分叉                                  | 历史逐字节复制，但系统提示词多了一段、会话 id 是新的，第一次请求全价                                         | 头部保持与源会话相同，限制说明放进追加的消息；低优先级                                                                                                                           |

### 4.5 易变消息通道

第 3 步之后没有行为档再用易变上下文。Mimi 迁移完成后删除这条通道，少一种放置规则。它上面的断点问题在 0.4 已经处理。

### 4.6 指令文件

指令文件每个 run 重新读，改了就重写头部。#363 明确决定不把它冻结到整个周期：指令、权限、工具资格这些语义和安全变化必须继续立刻生效（见它的账本设计文档"已知限制"）。本方案不改这个决定，只在 0.2 的指纹里把它量出来；量出来确实大，再考虑"普通内容的修改改成追加、撤销仍然立刻生效"。

### 4.7 子代理

同一类型、同一项目的子代理，系统提示词、工具和指令头是相同的；但每次派生都用新的会话 id 做缓存键，OpenAI 线路上不同的键分到不同的缓存分片。把子代理的缓存键改成"父会话 + 代理类型"。子代理占输入不到 1%，排在最后。

### 4.8 上下文体积：缓存之后的成本下限

全部命中之后，剩下的成本约九成是缓存读取，和上下文体积成正比。可以动的地方：

- 压缩阈值现在按窗口比例，大窗口模型上会话会长到三五十万 token 才压。提供一个"成本优先"的绝对阈值选项。
- 上下文压力不急的时候，把压缩留到缓存已冷的时刻做：冷的时候重排前缀不花额外的钱。
- Mimi 派活的会话体积（3.8）。

这些都会影响模型能看到多少历史，默认值由主人定。

### 4.9 护栏

- 每个 preset 的头部守卫在 CI 里（1.8、2.6）；新增会进入请求的内容，必须说明它属于第 2 节三类里的哪一类、走哪条路。
- 用量回执里的损失归因接到用量页：每周可修复的损失占输入的比例，和前三个原因。
- 开发版里可修复的损失连续超过阈值时打警告，回归能在当天被看见。

## 10. 风险、不做、需要主人定的事

**风险**

- **样本太小。** 现在 main 的数字来自几天的小样本。第 4 步的排序以 #363 之后重采的一周为准。
- **#363 迟迟不合**：P3-b 和第 4 步被挡住。第 1、2 步和 P3-a 不依赖账本，可以先做。

- **预算**：导出预算全部零余量，`pet-dispatch-service.ts` 只剩 14 行余量。

- 保活请求。

- 外部运行时自己的缓存。

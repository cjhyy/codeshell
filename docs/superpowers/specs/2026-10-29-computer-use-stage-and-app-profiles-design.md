# 电脑操作 × Mimi：舞台、应用档案与真实感 设计

- 状态：P2–P6 已实施（见 §11）；P1 待真机诊断
- 日期：2026-10-29
- 前置：`2026-10-28-mimi-cua-execution-boundary-design.md`（执行闸门，PR #239 已合并）、PR #242（驱动自带浏览器路线已下线）
- 范围：Desktop 主进程 `src/main/computer-use/**`、Mimi 角色渲染 `src/renderer/pet/live2d/**`、新增资源 `resources/computer-use/apps/**`

## 1. 目标与非目标

**目标**

1. 电脑操作是主线：在 Chrome 等网页类应用里也要做到"读得到、点得准、不抢焦点"，效果对标 Codex 的电脑操作。网页插件通道只是补充。
2. Mimi 的表现和电脑操作同源：每一次真实操作都有对应、及时、可读的角色表现，而不是事后动画。
3. 用"应用档案"（App Profile）按应用扩展两类知识：给模型的操作要点、给角色的舞台提示。新增一个应用只加一个文件。
4. 分层清楚、每层可以单独测试、单独合并；每个阶段都能独立交付。
5. 在不破坏执行边界的前提下，逐步增加 Mimi 与真实桌面的互动，做出"它真的在你的电脑上干活"的感觉。

**非目标**

- 不让角色发起任何电脑输入。角色永远只是表现层。
- 不读取、不展示页面或窗口里的文字内容（标签、值、标题以外的正文）。
- 不改驱动（cua-driver 0.34.1 锁定版本）的行为；需要的改进都在 CodeShell 自己的层里做。
- 不恢复驱动自带的 DevTools 浏览器工具（PR #242 已下线）。

## 2. 现状

已落地（P0）：

| 层       | 现状                                                                             | 位置                                                                 |
| -------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 执行     | 独立辅助 App 持有系统授权，驱动在其中运行                                        | `cua-driver-host.ts`、`CodeShell Computer Use.app`                   |
| 闸门     | proxy 在派发时检查输入通道；停止、聊天暂停、用户活跃、会话取消；浏览器路线不提供 | `cua-activity-proxy.ts`、`input-gate-policy.ts`、`input-gate.ts`     |
| 活动投影 | proxy 把工具调用投影成不含内容的活动事件（动作、目标点、避让框、是否截图）       | `cua-activity.ts`、`cua-native-cursor.ts`、`cua-activity-server.ts`  |
| 表现队列 | 有界、有序；截图前同步等角色隐藏，其它都不阻塞执行                               | `computer-activity-bus.ts`                                           |
| 角色     | 放置在目标旁、避让输入框；动作映射成少量姿态参数；运行结束有完成/失败表现        | `mimi-companion-host.ts`、`companion-layout.ts`、`companion-pose.ts` |

问题：

1. **Chrome 读不到网页结构**。之前的验证在 Chrome for Testing 上 20 次重试都找不到输入框；只有带 `--force-renderer-accessibility` 启动才行。驱动说明里称"稀疏的 Chromium 树第二次读取会补全"，且驱动和 Codex 的服务里都有 `AXManualAccessibility` 开关；而驱动每次读树默认只给 1 秒预算，超时会返回半棵树。根因尚未确认（见 §5.2 的验证项）。
2. **没有按应用的知识**。Slack 回车会直接发送、网页里逐键输入会被拒等经验，只能写在全局工具描述里。
3. **角色只知道一个点**。不知道是哪个应用、哪个窗口、目标是什么类型的控件，所以只能"站在点旁边"，无法做出走到窗口、坐在标题栏、对输入框做打字动作这类真实表现。
4. **宿主文件职责过多**。`mimi-companion-host.ts`（729 行）同时管放置、动画计时、聊天暂停和窗口生命周期，不便扩展和测试。

## 3. 不变量（所有阶段必须保持）

1. 闸门是唯一的执行权威；角色、档案、舞台都不能放行或阻止输入。
2. 表现从不延迟输入。唯一例外仍是截图前隐藏角色（有上限的等待）。
3. 活动事件不含内容：只允许动作、阶段、几何、进程号、应用标识、控件**类别**；不允许标签文字、值、窗口正文。窗口标题也不进入事件。
4. 应用档案是随包发布、经过审阅的数据；不执行代码。将来允许用户自定义时，按"用户自己写的说明"对待，不能放宽闸门。
5. 失败关闭：识别不出应用就不注入档案、退回到当前的点位放置；任何表现层错误都不影响执行。
6. 尊重"减少动态效果"系统设置；用户在操作时角色让开。

## 4. 架构总览

```
 模型 ──MCP──▶ ┌──────────────── CUA proxy（独立 Node 进程）────────────────┐
               │ ① 闸门（已有）         ② 感知整形（新）     ③ 档案注入（新） │──▶ 驱动（辅助 App 内）
               │ ④ 活动投影（已有，扩展为场景事件）                          │
               └──────────────────────────┬──────────────────────────────────┘
                                          │ 私有 socket：场景事件（不含内容）
 Desktop main ────────────────────────────▼──────────────────────────────────
   ComputerActivityBus（已有）
        │
   AppIdentity（新：pid → bundle id，只读、缓存）   AppProfiles（新：档案注册表）
        │                                                │ 舞台提示
   StageModel（新，纯函数）：显示器、窗口框、目标、避让区 → 锚点
        │
   Choreographer（新，纯状态机，注入时钟）：场景事件 → 行为时间线
        │ MimiCompanionState（扩展字段）
   CompanionWindow（从宿主拆出：窗口、可见性、截图隐藏）
        ▼
 Renderer：Actor（sprite / live2d）按"能力声明"播放行为
```

数据只朝一个方向流：执行 → 投影 → 舞台 → 编排 → 渲染。角色到执行侧只有两条已存在的路：用户点"停止"（请求闸门）、聊天打开（请求前台暂停）。

## 5. 组件设计

### 5.1 执行层（不变）

辅助 App、驱动、闸门策略保持现状。新增能力全部放在 proxy 的"整形"和"注入"阶段，以及主进程的表现侧。

### 5.2 感知整形（proxy 内，新）

目的：让模型在 Chromium 类应用里稳定拿到完整的树，不改驱动。

1. **读取预算**：调用方没给 `timeout_ms` 时，proxy 为 `get_window_state` 补一个更合理的默认值（候选 3000ms，由验证数据定）。调用方给了就不动。
2. **稀疏树补读**：响应里出现网页区域但几乎没有子元素，或目标应用属于 Chromium 家族且元素数明显过少时，proxy 在把结果交给模型前自动再读一次（只一次，有总时长上限）。补读是只读调用，不经过输入通道。
3. **说明增强**：在 `get_window_state` 的工具描述里写明"网页内容先用元素操作；读不到再用截图坐标"，并与档案注入配合。

**验证项（P1 开工前必须先做）**：用 `scripts/probe-cua-chromium.ts`（从本次诊断脚本整理）在 Chrome for Testing 上分别测：

- 不加启动参数时，第 1–5 次读取的元素数、是否截断、是否出现网页区域、能否找到输入框和按钮；
- 1 秒与 5 秒预算的差别；
- 后台 `set_value` 与元素点击是否生效、前台窗口是否保持不变。

根据结果决定 1、2 两项的具体阈值；如果驱动在 Chrome 上根本不会打开 `AXManualAccessibility`，则在辅助 App 里增加一个"只读开启网页辅助功能"的小步骤，作为单独的子阶段评估。

### 5.3 应用档案（App Profile，新）

**文件**：`packages/desktop/resources/computer-use/apps/<id>.md`，一个应用（或一个应用家族）一个文件。

```markdown
---
id: chrome
bundleIds:
  [
    com.google.Chrome,
    com.google.Chrome.canary,
    org.chromium.Chromium,
    com.google.chrome.for.testing,
  ]
names: [Google Chrome, Chromium]
stage:
  perch: title-bar # title-bar | beside-target | screen-corner
  keepClear: [text] # 这些控件类别永远不被角色遮住
  quiet: false # true 时只保留最小表现（如视频会议）
---

## Chrome

网页内容优先用 `set_value` 写入输入框；逐键 `type_text` 在后台会被拒绝。
……
```

- 正文是给模型的操作要点，风格参照 Codex 的 AppInstructions：短、具体、只写这个应用特有的坑。
- `stage` 是给角色的舞台提示，字段固定、可校验；未知字段忽略。
- 匹配顺序：bundle id 精确匹配 → 应用名匹配；都不中就没有档案。

**加载**：主进程启动时读取并校验全部档案（坏文件隔离并记日志，不影响其它档案），把"正文 + 匹配表"通过 proxy 启动参数指向的只读文件交给 proxy；舞台提示留在主进程。

**注入（给模型）**：proxy 在 `get_window_state`、`launch_app` 的结果里，对每个"会话根 × 应用"只追加一次一段文本：`CodeShell app notes for <App>: …`。注入发生在结果返回路径上，不碰输入路径。应用识别：`launch_app`/`list_apps` 的响应自带 bundle id；其余情况 proxy 用只读的 `lsappinfo` 查 pid 并缓存。

**为什么放在结果里而不是 MCP instructions**：core 不转发 MCP `instructions`（见前置设计 §6），而工具结果一定会进入模型上下文，并且只在真正操作该应用时出现，不占用无关会话的上下文。

### 5.4 场景事件（扩展现有活动事件）

在 `CuaActivityEvent` / `CompanionOperation` 上新增可选字段，全部不含内容：

| 字段      | 含义                                                                                | 来源                                                |
| --------- | ----------------------------------------------------------------------------------- | --------------------------------------------------- |
| `pid`     | 目标进程                                                                            | 工具参数                                            |
| `window`  | 目标窗口的全局框（逻辑点）                                                          | `get_window_state` 响应里的窗口框（tracker 已解析） |
| `element` | 目标控件**类别**：`text`/`button`/`link`/`menu`/`list`/`scroll`/`other`，以及控件框 | 元素令牌对应的快照几何与角色                        |
| `appId`   | 档案 id（不是 bundle id 原文也可以）                                                | 主进程 AppIdentity 解析后附加                       |

服务端解析器继续逐字段白名单校验；`update` 阶段规则不变（只认原生光标位置）。

### 5.5 舞台模型 StageModel（新，纯函数）

输入：显示器列表、当前目标窗口框、目标点与控件框、角色尺寸、档案舞台提示、用户活跃状态。
输出：锚点（角色应该在的位置）和朝向（看向哪里），以及"是否该让开/隐藏"。

锚点类型：

- `title-bar`：坐在目标窗口标题栏上沿，靠近目标一侧；
- `beside-target`：现有逻辑（目标旁、避让输入框），作为默认和兜底；
- `screen-corner`：远离一切，`quiet` 应用或找不到安全位置时使用。

规则：永不遮挡目标点和 `keepClear` 类别的控件框；窗口框变化时锚点跟着窗口走；跨显示器时选目标所在显示器。现有 `companion-layout.ts` 演进成这里的 `beside-target` 实现。

### 5.6 编排器 Choreographer（新，纯状态机）

把场景事件变成"行为时间线"，时钟由外部注入，便于测试。

- **接近**：距离近时走过去（时长随距离，有上限）；距离远或跨屏时"消失—出现"。目标是**动作开始后 300ms 内到位**，保证看起来是"它在做"而不是"它在追"。
- **动作**：按 动作 × 控件类别 选择手势：输入框上打字、按钮上按下、页面上滚动、拖动时搬运、读屏时观察。
- **运行弧线**：开始（准备）、进行中（专注）、完成（小庆祝）、失败（担心）、取消（停下）。沿用现有"运行级结果才算任务结果"的规则。
- **让位**：用户活跃时走到边上并降低存在感；聊天打开时转向聊天。
- **截图**：截图开始前隐藏（已有），结束后在原锚点恢复，不重放手势。

现有 `mimi-companion-host.ts` 里的 700ms 收尾、完成/失败停留等计时逻辑迁入这里。

### 5.7 角色渲染 Actor（扩展）

- `MimiCompanionState` 增加 `behavior`（当前行为名、开始时间、朝向、锚点类型）；旧字段保留一段时间兼容。
- 每种外观（sprite / live2d）声明自己支持的行为；不支持的行为退回到最接近的已有姿态（沿用 `EffectSet` 回退思路）。
- 新增 IPC 为零：仍然走现有的状态推送。

### 5.8 宿主拆分

`mimi-companion-host.ts` 拆成：

- `companion-window.ts`：窗口创建、可见性、截图隐藏屏障、置顶层级；
- `stage-model.ts`、`choreographer.ts`：上面两节的纯模块；
- `app-profiles.ts`、`app-identity.ts`：档案注册表与 pid 解析；
- `mimi-companion-host.ts`：只做组合与偏好读写。

## 6. 真实感清单

按阶段落地，每条都能在预览实验室里单独演示：

1. 走到目标窗口并坐在标题栏上，窗口移动时跟着动。
2. 视线跟随驱动的虚拟光标，而不是只看最终目标点。
3. 在输入框旁做打字动作，在按钮上做按下动作，在页面上做滚动动作。
4. 截图瞬间隐藏，截图后原地出现，不"跳一下"。
5. 你动鼠标时它让开，你停下后它回来继续。
6. 任务完成有小庆祝，失败会担心，你按停止会立刻停下。
7. 跨屏时从一侧离开、从另一侧进入。
8. （后续）你把 Mimi 拖到某个窗口上，它会指着这个窗口并出现"让 Mimi 看看这个窗口"的提示；你确认后，把这个窗口的应用名作为上下文发到聊天里。这是用户发起的聊天上下文，不是电脑输入。
9. （后续）按档案的舞台提示做应用特有表现，例如 Chrome 里坐在标签栏、Slack 里永远不挡输入框、视频会议应用里保持安静。

## 8. 测试策略

- 纯模块（舞台、编排、档案解析）全部单测，时钟和显示器注入。
- proxy：沿用现有夹具；新增"注入只出现一次""补读只读且只一次""调用方 timeout 不被改写"。
- 真机：P1 的诊断脚本走 CodeShell 自己的链路（辅助 App → 驱动 → 闸门 proxy），只用临时配置的 Chrome for Testing，不碰用户的浏览器。
- 视觉：预览实验室加脚本化场景（不依赖模型），逐条对照 §6。
- CI：Computer Use 测试已在独立 Bun 进程（ci.yml）；新增测试文件放在同目录即可。

## 9. 风险与开放问题

1. Chrome 读不到网页结构的根因未定（预算、首次稀疏、还是驱动不开开关）。P1 的验证决定方案，可能需要在辅助 App 里加一个小的只读步骤。
2. 辅助 App 是 ad-hoc 签名，重新构建或升级后系统授权可能失效，需要在列表里删除后重新添加。开发验证时优先用已安装版本的辅助 App。
3. 档案注入会增加上下文：每会话每应用一次，正文长度设上限（候选 1,500 字符）。
4. 窗口框只在读窗口时更新；窗口在两次读取之间移动，角色会短暂错位。P5 可在运行期间低频刷新（只读、有上限），先观察是否需要。
5. 预算测试：本设计不新增 IPC 路由和 preload 方法。

## 10. 与 Codex 的对照

| 方面              | Codex                                                                          | 本设计                                                   |
| ----------------- | ------------------------------------------------------------------------------ | -------------------------------------------------------- |
| 网页              | 专门的浏览器插件（扩展 + 本机程序、按标签认领、按网站授权、`tab.ax` 编号操作） | CodeShell 内置浏览器与 Chrome 扩展为补充；主线是电脑操作 |
| 电脑操作在 Chrome | 读整棵辅助功能树、按编号操作、动作后自动等待稳定、看不清再截图                 | 同思路；稀疏树补读与读取预算在 proxy 里做（P1）          |
